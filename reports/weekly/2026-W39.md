## 关键洞见

1. **两篇入库论文共同指向同一个平台能力缺口：高频、低成本的批量诊断式沙箱调用**。[[2609.23377]] 的 Refresh-Repair-Expand 循环需要每轮对全量训练集重新评估通过率；[[2609.27321]] 的环境生成期需要反复短生命周期起停做三重自动校验。两者都不是"训练期高吞吐 rollout"，而是"诊断/校验期高频短生命周期执行"——这是和我们现有沙箱使用模式不同的第二种负载形态，值得单独评估冷启动和并发密度需求。
2. **两篇论文都回避了最关键的生产数字：GPU/算力成本**。[[2609.23377]] 完全没披露训练卡数和时长；[[2609.27321]] 只公开了环境生成成本（$0.01–0.03/条），RL 训练阶段本身的算力开销只字未提。评估这两条技术路线能否落地我们平台前，这部分成本需要自己补测，不能直接引用论文数字。
3. **本周新上线的 reading-list 批量精读功能，第一次实战就是 DSec 沙箱论文的引用链**：一天内（09-26）产出 15 篇文献笔记，覆盖 microVM 全谱系（Firecracker、gVisor、Kata Containers、PVM、LightVM、QEMU）、放置调度（FirePlace）、镜像按需加载、快照唯一性等，直接对应"沙箱平台"这个本职方向。但这批产出全部停在未合并的本地分支（`batch/21-1`、`batch/22-1`、`batch/23-1`），是本周最大的一块"隐藏产能"。
4. **dsec-refs 清单的 G（WebAssembly 与其它隔离）、H（LLM 沙箱与 RL 训练框架）两个分类的 tracking issue（#29、#30）本周被关闭，但仓库里找不到对应的笔记或分支产出**。同期刚好合并了 reading-list 幂等性修复（#31 fix(reading-list): idempotent create via committed state file），而本地 state 文件记录 G/H 对应的原始 issue 号其实是 #27/#28，不是被关闭的 #29/#30——这两个分类很可能在修复前被重复创建了 issue，#29/#30 是重复项被清理，#27/#28 才是真正需要处理（或已经处理但没留痕）的分类。这一点不确定，需要人工核实，避免 G/H 被误判为"已完成"而实际从未精读。
5. **agent harness 成本工程本周是高频出现的主题，但目前都停留在推送阶段、还没精读**：SoL-Pi（harness token 降 45–49%）、CliffCompaction（压缩成本降 50%）、Control the Harness（企业级模型路由，万人场景年省 $3.3–5.0M）、Jev-Mobile（规划-执行解耦，API 成本降 73.4%）。这条线和沙箱线并列，是"平台要补什么能力"这个视角下另一个值得专门跟进的方向。
