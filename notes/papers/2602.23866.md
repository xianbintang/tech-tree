# SWE-rebench V2: Language-Agnostic SWE Task Collection at Scale

> 用"挖掘 GitHub PR 历史 + 交互式 setup agent + LLM 裁判集成过滤"的全自动流水线，把可执行 SWE 训练任务的规模化构造扩展到 20 种语言、3,617 个仓库、32,079 个任务。

## 元信息

- 机构：Nebius（Amsterdam）
- 发表：2026-02-27（v1），2026-06-01（v2，当前版本，ICML 2026）
- 链接：[arXiv](https://arxiv.org/abs/2602.23866) · [HTML](https://arxiv.org/html/2602.23866) · [数据集: nebius/SWE-rebench-V2](https://huggingface.co/datasets/nebius/SWE-rebench-V2) · [PR 扩展集: nebius/SWE-rebench-V2-PRs](https://huggingface.co/datasets/nebius/SWE-rebench-V2-PRs)
- 对比基线 / 相关工作：[[swe-bench-multilingual]]（Multi-SWE-bench，7 语言，人工验证）、SWE-PolyBench（4 语言，自动化评测 harness）、SWE-bench-Live、SWE-Factory（4 语言自动管线）、SWE-Bench++、RepoForge

## 要解决的问题

Agentic RL 训练软件工程 agent 需要大量"可执行、reward 稳定"的任务环境，但构建这类环境的瓶颈是**依赖安装 + 测试执行 + 自然语言描述与测试 oracle 对齐**这三件事在单一语言生态里就很贵，跨语言更是随构建系统、依赖管理器、测试 runner 的异构性急剧变差。已有多语言基准（Multi-SWE-bench、SWE-PolyBench）靠大量人工验证换取高置信度，规模和覆盖面受限；已有自动化管线（SWE-rebench v1、SetUpAgent、SWE-Factory、SWE-Bench++）虽然提升了规模化能力，但普遍是"评测优先"而非"训练优先"（缺预构建镜像、缺细粒度实例级诊断元数据），而且"语言无关"在实践中往往只覆盖少数生态，长尾工具链的鲁棒性不明确。

## 方法

一条五阶段全自动流水线（外加一个 PR 扩展阶段），核心原则是**每个仓库只推断一次安装/测试脚本，复用到该仓库挖出的所有任务**：

1. **Preliminary Data Collection**：用 GitHub Archive 聚合公开活动，分布式 map-reduce 克隆仓库、直接从本地 git 历史抽取 PR patch（绕开 API 限速）。按测试文件正则 `(?i)(test(?:ing|s)?|e2e)` 把 diff 拆成 solution patch / test patch。高资源语言（Python/Java/Go）用严格阈值（≥25 星、≥15 关闭 issue）筛仓库，长尾语言放宽到 ≥10 星、≥1 关闭 issue，以保留多样性。
2. **Setup Synthesis**：每种语言预构建基础 Docker 镜像（大生态提供多个工具链版本，如 Java 分 JDK 11/17/21）；用 mini-SWE-agent v1.14.4 + Qwen3-Coder-480B-A35B-Instruct 作为**交互式 setup agent**，闭环调试（装依赖、跑测试、看报错迭代脚本），只在仓库最新任务快照上跑一次并复用。同时从成功日志自举**仓库专属日志解析器**（同一模型生成，最多 5 轮重生成迭代）。
3. **Execution-based Validation**：多阶段 Docker 构建分离可复用 base 层与仓库专属安装/测试层；先打 test patch 跑一遍全量测试，再打 solution patch 跑一遍，产出修复前后成对的执行轨迹；只保留至少有一个 fail-to-pass 测试的实例；每个候选任务重跑 3 次、结构化测试结果不变才保留（过滤 flaky）。
4. **Filtering by Issue Clarity**：沿用 SWE-bench Verified 的标注 rubric 改写成 LLM 友好 prompt，用 **gpt-oss-120b / GLM-4.7 / DeepSeek-V3.2 三个独立 LLM 裁判**打分，三者全部判定"specification adequate"才保留。
5. **Metadata Enrichment**：基于对 7 个前沿模型运行轨迹的分析（见下）写 meta-prompt（用 gpt-oss-120b 执行），给每个任务标注潜在局限与特征标签；并自动从 patch 中抽取测试实际覆盖到的接口（方法/类签名 + 简介）。
6. **PR-based Task Expansion**（扩展阶段）：对已成功构建执行环境的仓库，复用同一套安装/测试脚本，把**未链接 issue 的普通 PR**也纳入——问题描述由 LLM 基于 PR 描述+patch **合成**（而非直接用原始 PR 文本，以降低"答案泄漏"风险），并做额外后处理检测可疑泄漏案例。

## 实验与结果

**端到端漏斗（Table 1）**：2951.2 万 PR / 14.5 万仓库 → 含测试的 PR 859.4 万 / 10.2 万仓库 → 关联 issue 且含测试 80.6 万 / 5.08 万仓库（issue 链接是仅次于"要求含测试"的第二大瓶颈，约缩减一个数量级，也是引入 PR 扩展阶段的直接动机）→ 仓库级过滤后 58.4 万 / 2.17 万仓库（策略上只对 ~20% 的仓库做昂贵的 setup synthesis，但覆盖 ~80% 的任务，setup 工作量降到 1/5）→ 成功产出 F2P 任务 4.13 万 / 4,006 仓库（即使有交互式 agent，单次 setup 尝试的仓库成功率也只有约 20%）→ issue 清晰度过滤后 3.30 万 / 3,701 仓库 → 3 次验证稳定 **32,079 任务 / 3,617 仓库**。

**Setup synthesis 消融（4.1 节，Table 2，103 个来自 SWE-bench/SWE-bench-multilingual/Multi-SWE-Bench、覆盖 10 种语言的仓库子集，各配置跑 10 次）**：交互式 agent 全面优于非交互式三步管线，甚至**交互式 Qwen3-Coder-30B-A3B 能超过非交互式的 Qwen3-Coder-480B-A35B-Instruct**；32K 上下文对多数仓库已足够，更长上下文有时反而让 agent 陷入循环；setup 尝试次数从 1 次增到 10 次，成功率接近翻倍。常见失败模式：工具链版本不兼容、系统/原生依赖缺失、monorepo 根目录选错、私有 registry 凭据要求、测试 runner 输出格式异构、"看似合理但不完整"的过早收敛。主流水线出于成本-产出权衡只跑**单次** setup。

**Issue 清晰度过滤消融（4.2 节）**：用 SWE-bench Verified 的 1,699 条人工标注（每条 3 名标注员打分：well-specified / valid evaluation criteria / difficulty）做校准。不同 prompt/ensembling 组合里，"Verified+"配置 F1 最高，但**"Verified-E"精确率最高**——因为过滤阶段更看重精确率（宁可漏掉、不可放过 underspecified 任务），流水线最终采用 Verified-E。Ensembling 对比了同模型多次打分聚合、以及三模型 average/consensus 聚合两种策略（Table 5）。

**任务诊断研究（4.3 节，Table 6）**：300 个任务子集（Python/JS/Go/Rust/Scala 各 60 个），7 个前沿模型（DeepSeek-V3.2、Gemini3-Flash、GLM-4.7、GPT-5.2 medium、gpt-oss-120b、MiniMax-M2.1、Claude Opus-4.5）用 mini-SWE-agent 跑 3 次。pass@1/pass@3 最高的是 Claude Opus-4.5（25.2% / 32.7%），其次 GLM-4.7（21.3% / 26.7%）、MiniMax M2.1（19.2% / 27.0%）、Gemini 3 Flash（18.1% / 27.7%）——建立了一个 SOTA 模型的基线水位。分析执行轨迹发现三类系统性混淆因素：
- **Test Suite Coupling**：模型修对了目标 issue，但因无关代码路径的回归而失败——作者认为这不一定是缺陷，往往是 P2P 测试套件正确捕获了真实回归，提供了"避免破坏既有功能"的有效信号。
- **Implicit Naming Requirements**：测试对实现细节（方法名、接口签名）有隐式要求，字面实现规范也会失败；缓解办法是把测试期望的命名约定作为提示注入问题描述（即元数据增强阶段做的事）。
- **External Dependencies**：部分任务问题描述引用外部 URL（GitHub issue、API 文档、设计文档），这些资源在评测时可能不可访问、会变化或需要鉴权。

**PR 扩展集的泄漏检查**：用 509 个从 SWE-bench Pro PR 构造的 PR-derived 任务做抽样，LLM 裁判比对生成的问题描述与参考 problem statement/需求/接口，判断是否引入超出参考文本的实现细节：392/509（77.0%）干净，117/509（23.0%）存在一定泄漏，12/509（2.4%）存在明确的解答泄漏。作者据此把 PR-derived 集定位为"更大规模但置信度更低"的训练资源，配套元数据供下游筛选。

**规模与成本（3.7 节）**：最终数据集覆盖 2014–2025，中位数每任务修改 3 个文件 / 34 行（90 分位数 9 文件 / 181 行，长尾里有很多更难的任务）；20 种语言，Python 21.6%、Go 20.6% 领跑，其后 JS/TS/Rust；覆盖多达 12 类 PR 类别（bug fix、regression、documentation、dev-ops、performance、integration、UI/UX、security 等）。Setup agent 处理 21,692 个仓库，平均每仓库 24.67 轮交互，共约 53.5 万次模型 API 调用；每条仓库轨迹平均输入 ~21.4 万 token、输出 966 token，按商用 API 定价折算约 **$0.0873/仓库**，setup 推理总成本约 **$1.9K**。任务级验证需要 583,809 次 Docker 构建，平均单次构建 2.71 分钟，累计约 **26,400 job-hours**。最终 32,079 个保留环境的 Docker 镜像总量 **26.36 TiB**。

## 局限与疑点

- **没有端到端 RL 训练消融**：论文明确说明这不是一份"训了 RL 证明有效"的论文，只验证了训练所需的前置属性（任务可执行、非平凡、模型间有 pass@k 提升空间、元数据能区分"干净"与"混淆"任务）——过滤后 vs 未过滤课程的直接对比效果留作未来工作，作者自己承认一次有说服力的多语言 RL 训练需要大量额外基础设施。
- **Docker 镜像对仓库演化鲁棒，但不能消除所有漂移**：外部包仓库、系统包、网络托管资源仍可能变化或消失（论文对此只做了定性说明，未给出量化的"漂移率"或长期可复现性数字）。
- **单次 setup 尝试的取舍**：消融已证明多次重试能显著提高 setup 成功率（接近翻倍），但主流水线出于成本只跑一次——这意味着当前 32,079 任务/3,617 仓库的规模本身还留有明显的产出空间，只是被成本权衡卡住了，而不是技术上限。
- **过滤策略偏保守（高精确率、非最高 F1）**：Verified-E 配置被选中是因为精确率优先，这意味着一部分本来可用的、被判定"不够清晰"的任务被牺牲掉了，具体丢弃率未披露。
- **诊断研究规模有限**：300 个任务（5 语言 × 60）× 7 模型 × 3 次跑，相对 32,079 的总任务规模是很小的抽样，三类混淆因素的整体占比（而非仅有的定性描述）未给出精确数字。

## 对我们的启发

1. **"每仓库只 setup 一次、复用给所有任务"是规模化构造可执行 SWE 环境的关键成本杠杆**：把 21,692 个仓库的 setup 成本控制在约 $1.9K（平均 $0.0873/仓库），是这条流水线能把仓库覆盖面推到 3,617 个、20 种语言的直接原因。如果我们要给内部沙箱平台喂类似规模的多语言可执行任务，"仓库级缓存 setup 结果、任务级复用镜像"应该是设计的第一原则，而不是逐任务重新构建环境。
2. **26.36 TiB / 32,079 环境（约 840MB/环境）的镜像体量和 583,809 次 Docker 构建、26,400 job-hours 的构建开销，是我们评估"自建同类多语言 SWE 训练环境"基础设施成本的一个可直接参照的量级**；论文用多阶段构建分离可复用 base 层与仓库专属层，这与我们已经在关注的 [[sandbox-image-distribution]]（可组合镜像层、按需加载）思路是同一方向,值得对照评估我们自己的镜像分层策略能否覆盖这种"仓库专属层"场景。
3. **LLM 裁判集成 + 针对人工标注校准（而非直接信任单一裁判）是过滤流水线里值得复用的模式**：三裁判一致同意才保留、拿 SWE-bench Verified 的 1,699 条人工标注做校准、显式在 F1 和 precision 之间选边站（precision-first）——这套方法论可以直接搬到我们自己筛内部可验证奖励环境时的"任务清晰度/可行性"审核环节。
4. **诊断出的三类混淆因素（测试耦合、隐式命名要求、外部依赖）是训练可验证奖励环境时的通用踩坑清单**，与 [[benchmark-item-validity-audit]] 里"区分真难/环境坏/verifier 漏洞"的分类思路是同一个问题在不同阶段（训练环境构造 vs. 评测基准审计）的呼应——如果我们要建自己的可验证奖励环境质检流程，这两套诊断维度可以合并成一份更完整的检查清单。
5. **跟进 follow-up**：① PR 扩展集的泄漏检查（77% 干净 / 23% 有泄漏 / 2.4% 明确泄漏）给出了"用 PR 描述合成问题陈述"这种扩展手段的量化风险基准，值得在我们自己做类似合成问题陈述时复用同样的 LLM 裁判泄漏检测协议；② "单次 setup vs 多次重试"的成本-产出曲线（消融显示 10 次重试接近翻倍成功率）没有给出完整的边际成本曲线，如果我们要复现类似流水线，值得先在小规模仓库集上自己测一遍这条曲线，找到适合自己预算的重试次数。
