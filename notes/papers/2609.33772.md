# Skill2Env: Capability-Oriented Environment Synthesis from Skills for General Agents

> 从 agent 能力需求（而非模板）出发，用可复用的"难度模式"生成任务蓝图，再用执行证据驱动的 Iterative Task Hardening 持续把任务改难。

## 元信息

- 机构：AllSpark Team（论文未给出高校/公司归属信息）
- 发表：2026-09-27（v1），2026-09-29（v2，当前版本）
- 链接：[arXiv](https://arxiv.org/abs/2609.33772) · [Code](https://github.com/AllSpark-Research/AgentEnv)
- 对比基线：闭源前沿模型（GPT-5.4、Claude Opus 4.6、Gemini-3.1 Pro）、开源模型（DeepSeek-V4-Flash、GLM-5.2、Kimi-K2.6、Qwen3.8-27B、Qwen3.5-397B-A17B）、backbone Qwen3.6-35B-A3B（SFT 前后对照）、同为 skill-based 环境合成的 FACET（[[skill-to-task-pipeline]] 笔记里也提到的同类工作）

## 要解决的问题

Skill（结构化工作流说明 + 脚本/模板等配套资源）能给任务与环境构造提供领域知识和工具操作的"接地"，但从一份 skill 到一个"具体、有挑战性、配齐执行环境"的任务之间存在明显 gap：现有工作（SkillSynth、Terminal-World、FACET）已经在探索怎么从 skill 生成环境，本文进一步追问——**给定一个 skill，如何依据 agent 的能力需求来构造任务和环境**，而不是仅靠场景重建或跨 skill 一致性来生成。

## 方法

Skill2Env 是一条"skill → 能力需求 → 难度模式 → 任务蓝图 → 环境"的合成管线（Figure 2）：

1. **Skill Curation**：从 ClawHub 下载 47K+ 公开 skill 文件夹，按 Practical Utility（是否有明确实用目的）、Runtime Compatibility（软硬件/权限/算力是否匹配目标 Linux 沙箱）、Setup Feasibility（依赖/数据/服务是否可行provision）三条标准筛选，保留 3K+ 个 skill。
2. **能力需求 → 难度模式（Difficulty Patterns）**：把完成复杂任务所需的能力归纳为 5 个维度——环境理解（Environment Understanding）、规划（Planning）、技能使用（Skill Usage）、长程一致性（Long-Horizon Consistency）、错误恢复（Error Recovery）（Table 2）。每个维度下用多条可复用的"难度模式"具体化挑战的构造方式，例如环境理解维度下的 **Distributed Evidence**（把互补事实拆散到多个来源，单一来源不足以支持完整答案）、**Implicit Constraints**（规则可从配置/示例中推断但不直接写在指令里）；规划维度下的 **State Dependencies**（后续操作依赖特定早期结果，形成依赖图）、**Coupled Constraints**（若干独立可行的需求共享决策变量，必须联合求解）。初始难度模式池 $\mathcal{P}$ 有 **100 条**，按 5 个能力维度组织（Appendix B）。每条模式都带有可调的"强度控制项"（如 source count、dependency depth、budget tightness），便于后续加固。
3. **任务蓝图（Task Blueprint）驱动构造**：给定 skill $\kappa$，合成 agent 先挑出与该 skill 兼容的难度模式子集 $\mathcal{P}_\kappa$，草拟任务蓝图 $B$——作为"作者侧契约"，把目标、挑战、环境事实、验收标准、执行需求（工具能力/运行时依赖/初始资源状态）和信息边界（指令给什么、workspace 里要发现什么、需要推断什么）绑定在一起。蓝图再驱动任务指令 $g$、执行substrate $\mathcal{X}$、初始 workspace $W_0$、rubric 评估器 $\mathcal{V}$ 的联合构造：$(\kappa, B) \xrightarrow{\text{synthesis}} T=(g,(\mathcal{X},\kappa,W_0),\mathcal{V})$。
4. **Rubric 评估**：验收标准被拆成一组带权重的 rubric 条目 $c\in\mathcal{C}$（权重和为 1），可程序化校验的条目走确定性验证（多为二值），其余走 LLM judge（可给连续分），最终 reward 是加权平均 $r=\sum w_c q_c$。
5. **一致性校验**：solver rollout 后，validation agent 对照蓝图与执行证据检查任务条件和 rubric 结果是否一致；需要改契约的问题联动更新蓝图，纯实现问题就地修；被判定为任务条件错误/评估器错误的证据会被排除出后续的能力诊断，避免"脏数据"污染难度加固的判断依据。
6. **Iterative Task Hardening**：这是本文与 [[skill-to-task-pipeline]]（SkillGym）最大的方法论差异——不是一次性生成后靠对比测试筛掉太简单的任务，而是**持续把偏简单的任务改难**：在迭代 $j$，solver 执行任务 $T^{(j)}$ 得到轨迹 $\tau^{(j)}$ 和 rubric 结果 $q^{(j)}$；reward 超过预设阈值（本文取 0.7）的任务被送入诊断 agent，对照蓝图检查 solver 是否走了捷径绕过了本该有的挑战、哪里还有残余失败点；诊断中发现的、当前模式池里没有的可泛化挑战会被抽象成新难度模式加入 $\mathcal{P}$。据此提出加固方案 $H^{(j)}$（提高现有模式的强度控制项，或引入池中兼容的新模式），修订蓝图 $B^{(j+1)}$，再联动重建任务 $T^{(j+1)}=\text{Construct}(\kappa,B^{(j+1)})$。整条管线最终产出 **2,963 个可执行任务**。

**训练**：用 DeepSeek-V4-Flash 在合成任务上生成轨迹，按 SFT 质量过滤 $r>0.9$ 只保留 **1.5K 条**高分轨迹，对 backbone Qwen3.6-35B-A3B 做全参数 SFT（Megatron，5 epoch，全局 batch 32，peak lr $10^{-5}$，min lr $10^{-6}$，cosine decay，10% warmup）。环境合成本身用 Kimi-K3 负责合成与诊断，Qwen3.6-35B-A3B 作为 Iterative Task Hardening 期间固定的 solver，Qwen3.5-397B-A17B 做 LLM rubric 判分。

## 实验与结果

**主结果（Table 1，七个 benchmark：Terminal-Bench 2.1、SWE-bench Multilingual、SkillsBench、Claw-Eval、AutomationBench、τ³-Banking、VitaBench）**：Skill2Env 把 Qwen3.6-35B-A3B 的七基准均值从 36.6 提升到 45.0（**+8.4pp**），仅用 1.5K 条 SFT 轨迹。正文明确给出各基准增幅：SkillsBench **+14.34pp**、Terminal-Bench 2.1 **+13.5pp**、SWE-bench Multilingual **+7.7pp**、AutomationBench **+7.34pp**、VitaBench **+5.87pp**、Claw-Eval **+5.51pp**、τ³-Banking **+4.47pp**——全部七个基准都涨，且论文强调 Skill2Env **不针对任何单一下游基准做优化**，环境是围绕通用能力维度组织的，这种跨领域一致提升被作者当作"围绕共享能力需求构造的监督信号具有可迁移性"的证据。

Skill2Env 也在六/七个基准上超过参数量大得多的 Qwen3.5-397B-A17B（仍落后闭源前沿模型 GPT-5.4/Claude Opus 4.6/Gemini-3.1 Pro），并在 Terminal-Bench 上明显优于同为 skill-based 环境合成路线的基线 FACET-Terminal-Qwen3.5-27B（47.6 → 58.4）。

**跨 harness 的泛化性（Section 5.4，Figure 4）**：Terminal-Bench 2.1 上，SFT 后模型在 pi（46.1→57.3，+11.2）、Terminus-2（44.9→58.4，+13.5）、OpenCode（38.2→55.1，+16.9）、Claude Code（40.5→52.8，+12.3）四种 harness 下均有提升，说明能力提升不依赖特定 scaffold。

**SkillsBench 细分（Section 5.3，Figure 3）**：skills-on 条件下 8 个领域里 7 个有提升（金融领域无变化），媒体（+46.7pp）、数学与运筹（+26.9pp）、软件工程（+23.4pp）领涨；skills-off（不给 skill 文本，但 skill 文件仍在环境里可访问）条件下 8 个领域全部提升，且整体增幅（+10.4pp）也不小，作者据此认为提升的是可复用的执行能力而非单纯"更会读 skill"。

**Iterative Task Hardening 的量化验证（Section 5.5，Figure 5）**：用 500 个"两轮都被加固"的配对任务，在迭代 0→1→2：
- DeepSeek-V4-Flash（pi harness）的满分率（$r=1$）从 48.40% 降到 24.80%、15.40%（0→2 共降 33.0pp），平均 assistant turns 从 25.91 升到 36.54、38.85（约多 50% 交互步）——证明加固确实在让任务变难；
- 固定训练数据规模（每次都是 500 条满足 $r>0.9$ 的随机采样轨迹）和质量阈值，仅替换成对应迭代版本的任务，七基准均值从迭代 0 的 40.58 升到迭代 1 的 42.51、迭代 2 的 42.87（**+2.29pp**）——说明在同样的数据预算和质量筛选下，更硬的任务版本能提供更有效的训练监督，这是"持续加固"这一设计相对于"一次性生成"最直接的量化收益证据。

**环境多样性统计（Appendix C，工程细节）**：2,963 个任务中 2,613 个带 SKILL.md 之外的配套资源（19,649 个文件，覆盖 13 种编程/标记语言，Python 和 Shell 最多）；执行 substrate 层面识别出 **4,242 个不同依赖包**（跨 8 个生态，npm 最多，其次 pip、Cargo、apt、Go、Maven、Gems、Conda）和 **823 个不同 CLI 名称**；初始 workspace 共 46,295 个文件、113 种扩展名、12 类资产族，91.4% 的任务 workspace 里混有 ≥2 类文件；技能领域覆盖 25 个，最大是软件工程与代码质量（320 个任务，10.8%）。

## 局限与疑点

- **只做了 SFT，没做 RL**：rubric reward 天然是可训练信号，但论文和 [[skill-to-task-pipeline]]（SkillGym）一样，只验证了"离线拒绝采样 + SFT"，RL 效果留白。
- **Iterative Task Hardening 的诊断 agent 本身没有被单独验证**：论文没有报告诊断/加固提案的误诊率——如果诊断 agent 判断错误（把本该保留的合理任务标记为"太简单"强行加固），可能把任务改得不公平或不可解，而不仅仅是更难；一致性校验只处理"任务条件/评估器错误"，并不覆盖"加固方向本身是否合理"这一层。
- **执行 substrate 的隔离/并发细节完全没披露**：只在 Figure 2 提到用 Docker，Appendix C 的依赖包/CLI 统计说明单个环境的软件栈相当异构（8 个包生态、823 个 CLI），但论文没给出镜像构建方式、单任务冷启动时间、并发执行规模——这些恰恰是我们最关心的工程数字，需要去读代码仓库补充。
- **基线覆盖有限**：唯一直接对比的 skill-based 环境合成基线 FACET 只报告了 Terminal-Bench 一项分数（source-reported，非同一评测流水线复现），其余六个基准没有 FACET 对照。
- **规模与阈值未做敏感性分析**：hardening-trigger 阈值（0.7）和 SFT 质量过滤阈值（$r>0.9$）都是直接设定，没有消融说明为什么是这两个值。

## 对我们的启发

1. **Iterative Task Hardening 提供了一个"环境规模化"里少见的量化闭环证据**：静态生成的任务很容易被更强 solver "水过"，而用执行证据驱动的诊断→加固→重建循环能在同预算下实测提升下游训练效果（+2.29pp）。如果我们要自建 agent 训练环境生成流水线，这是一个比"生成完就完事"更值得借鉴的设计模式，与 [[agentic-rl-environments]] 笔记里提到的"自动化课程生成"（EnvGen 一类）是同一思路的一个具体、可量化的实现。
2. **执行 substrate 的异构统计（8 个包生态、4,242 个依赖包、823 个 CLI）说明这类"从公开 skill 库批量合成执行环境"的场景，对沙箱平台的诉求不是单一固定镜像，而是能快速按需拼装多语言/多依赖运行时的能力**——这和我们已经在跟踪的 [[on-demand-image-loading]]、[[sandbox-image-distribution]] 关注点直接相关，但论文完全没有回答"这套异构环境怎么打包、复用、隔离"，是需要我们自己去读代码仓库或类比其他工作补的空白。
3. **Skill2Env 和 [[skill-to-task-pipeline]]（SkillGym）几乎同期（相差 4 天）独立地把同一类原始语料（ClawHub/OpenClaw 公开 skill 库）转成训练环境，但选择了两种不同的质量控制哲学**：Skill2Env 是"能力需求驱动的难度模式 + 持续执行反馈加固"，SkillGym 是"按 skill 子类手工设计模板 + 一次性的对比 skill 依赖性测试"。两者不是互斥选择，而是同一问题的两种可复用设计：如果我们自建类似管线，"用能力维度组织难度控制项"和"用对比测试做准入过滤"可以结合使用（先用对比测试筛掉不依赖 skill 的任务，再用能力驱动的难度模式做持续加固）。
4. **Follow-up**：
   - 去读 [AllSpark-Research/AgentEnv](https://github.com/AllSpark-Research/AgentEnv) 代码仓库，确认 Docker 执行 substrate 的具体隔离方案、镜像构建/复用机制、并发规模——论文正文完全没有这块工程细节。
   - 评估 Iterative Task Hardening 诊断 agent 的误诊率/是否会把任务改坏：如果我们要复用这个"执行反馈驱动加固"的机制，需要先补一个专门验证诊断准确性的实验，而不是直接信任论文里报告的"变难了"就等同于"变得更合理地难"。
   - 对比 1.5K（Skill2Env）vs 8,364（SkillGym）条 SFT 轨迹规模下产生相近幅度的提升：这提示"加固后的少量高质量数据"可能比"大规模但难度分布固定的数据"更有性价比，但两者 backbone、基准、评测口径都不同，不能直接下结论，值得用我们自己的环境和数据做一次受控对照实验。
