# OSWorld-Pro: Process-based Evaluation for Computer Use Agents

> 给 Computer-Use Agent（CUA）评测加一层"过程"监督：把长程任务拆成有依赖关系的子目标，用 LLM-Judge 逐步打分，而不只看最终产物。

## 元信息

- 机构：NVIDIA
- 发表：2026-09-21（arXiv v1）
- 链接：[arXiv](https://arxiv.org/abs/2609.24890)
- 对比基线 / 相关基准：OSWorld（结果导向评测的代表，本库暂未精读，未建概念页）、OSUniverse、ChainWorld、AndroidWorld
- 评测对象：多种闭源模型（Claude Opus 5 / 4.8 / 4.7、Claude Sonnet 5、GPT-5.6 Sol/Terra/Luna、Gemini-3.8-Flash）与开源权重模型（Kimi K3、Minimax M3、Qwen 3.x 系列）

## 要解决的问题

现有 CUA 评测（如 OSWorld）大多是**结果导向（outcome-based）**：只在任务跑完几百步之后检查最终产物是否匹配参考文件，用功能性 verifier 打分。作者指出三个局限：

1. **区分度差**：一个 agent 在第 1 步就失败、和在第 9 个子目标才失败，只要没产出最终交付物，两者拿到的分数都是 0，长程任务里这种失真会被放大。
2. **reward hacking 风险**：作者引用 OpenAI 2026 年的一次安全事件，强 agent 会为了拿到"正确"的最终结果去 hack 第三方服务器获取答案，结果导向评测无法察觉过程中的作弊。
3. **没有过程信息**：无法定位 agent 具体在哪类动作（点击坐标、键盘、拖拽……）或哪个子目标上失败，也看不出它在长轨迹里的效率（是否在做与目标无关的动作）。

思路上借鉴了数学领域的过程监督工作 PRM-800k 和 ProcessBench——把推理过程拆成步骤、定位错误首次出现的位置。但 CUA 任务比数学题更开放（完成一个目标可以有多种操作路径），所以作者转向 rubric 式思路：把总任务目标拆成**可独立判定、但彼此有顺序依赖**的子目标（不同于典型 rubric 里彼此独立的条目）。

## 方法

### 数据集构成

OSWorld-Pro 包含 305 个长程任务、2814 个渐进式子目标、67264 条人工标注（>5000 人时），分三类：
- **Diversity（117 任务）**：覆盖 OSWorld 少见的应用（Videos、Archive Manager、LibreOffice Draw 等）
- **Coordination（109 任务）**：需要协同 ≥4 个应用（OSWorld 最多涉及 4 个应用）
- **Robustness（79 任务）**：跨 Linux 发行版（Fedora、Alpine、AlmaLinux 等 19 种）和图形界面（bspwm、Xfce、LXQt 等 13 种）测试泛化能力，而非只在 Ubuntu/GNOME 上跑

任务先用 ProCUA-SFT 的方法生成，再用 DeepSeek-V4-Pro 做子目标分解（prompt 见 Appendix E），随后人工标注员逐步验证：识别每一步针对哪个子目标、该子目标当前是否可行（feasible）、是否推进（progression）、是否完成（completion）。标注流程有独立标注 + 审阅员复核的两轮机制（借鉴 HelpSteer3），标注员/审阅员间一致性很高（Cohen's κ：0.847–0.987，各字段有差异，完成判定的 κ=0.940 明显高于可行性判定的 κ=0.847）。

### 用 LLM 当过程评委

人工标注成本太高，作者用 LLM-Judge 做代理评委，在一次 API 请求里评估整条轨迹（因为要塞入几百张截图，payload 可达 500MB，只有 OpenAI GPT-5.6 系列能扛住这个规模，Claude/Gemini/开源模型都因 payload 大小、图片数量或上下文窗口报错）。

评判维度：Target（步骤对应哪个子目标）→ Feasible（子目标当前是否可行）→ Progress（是否推进）→ Complete（是否完成），后一层的判定只在前一层正确时才计入（依赖链评估）。

```mermaid
flowchart LR
    A[Agent 轨迹 数百步截图+动作] --> B[LLM-Judge 单次请求整条评估]
    B --> C1[Target 定位子目标]
    C1 --> C2[Feasible 可行性判断]
    C2 --> C3[Progress 是否推进]
    C3 --> C4[Complete 是否完成]
    C1 -.human κ=0.987.-> H1[人工一致性]
    C2 -.human κ=0.847.-> H2[人工一致性]
    C3 -.human κ=0.869.-> H3[人工一致性]
    C4 -.human κ=0.940.-> H4[人工一致性]
```

## 实验与结果

**LLM-Judge 对齐人类的程度（Table 1）**：最强配置 GPT-5.6-Sol Max，Step-level 平均 Macro-F1 82.0（人类 95.4）、Task-level 1-MAE 93.0（人类 96.0）。**Target 判定几乎追平人类**（97.0 vs 98.4%），**Complete 判定也接近**（94.3 vs 97.6%），但 **Feasibility（61.9 vs 91.6%）和 Progress（74.7 vs 94.1%）明显落后**——这两个维度本身人类标注者之间的一致性也更低（κ=0.847/0.869 vs 0.940/0.987），说明这是任务本身的主观性问题，不完全是模型能力问题。推理力度（reasoning effort）越高，Feasibility 判定反而越差：模型倾向于把任务判定为"可行"的比例从 None 档的 9.7% 降到 Max 档的 5.1%，而人工基准是 15.3%——说明加大推理反而让模型系统性高估任务可行性。模型家族内部（GPT-5.6 Luna→Terra→Sol）性能提升有边际递减：Step-level 从 75.7→80.9→82.0，成本却是 10x→1.6x 的跳变，小模型高推理力度常常比大模型低推理力度性价比更高（如 Terra Max 比 Sol Medium 便宜 22% 但分数略高）。

**模型在 OSWorld-Pro 上的表现（Table 2）**：最强模型 Claude Opus 4.8 Max 只拿到 77.7% Overall（OSWorld 上同系列 Opus 能到 83.4%）。开源权重模型差距更大——最好的 Qwen 3.8 Flash Next (125B) 55.1%，同一模型在 OSWorld 上却能到 >80%；Minimax M3 在 OSWorld-Pro 上仅 28.9%，但在 OSWorld 上 75.2%。说明 OSWorld-Pro 的长程协同+跨发行版设计确实能拉开差距，还没被"打穿"，可以作为开源模型爬坡的目标基准。参数规模和性能不是单调关系（Sonnet 5 优于 Opus 5 但差于 Opus 4.7/4.8），小模型倾向于用更多步数弥补能力（Luna 60.2 步 vs Sol 54.9 步；Sonnet 5 108.7 步 vs Opus 5 76.0 步）。

**任务级效率与成本（Table 2 + Appendix G）**：不同模型完成一个任务的 token 成本可以差 20 倍（GPT-5.6 Luna $0.51 vs GPT-5.6-Sol $9.56，性能接近）。Kimi K3 步数少（42.2 步）但输出 token 多（12.6 万），因为它依赖 pyautogui 单步内多动作打包，牺牲了步数换来更长的思考输出。基准测试全量跑一遍模型的成本可达"每个模型数千美元"级别（Appendix G，作者引用 OSWorld 的先例说明为什么只跑一次而非多次重复）。

**过程失败模式分析（Table 3、§6）**：Minimax M3、Kimi K3 在点击操作上进度似然显著更低（39.0–41.9% vs 强模型 72.4–92.5%），典型错误是点不中正确坐标（如想关窗口但没点中 × 按钮，Figure 4）。Claude 系列在键盘（≥89.2%）和滚动（≥84.1%）类动作上明显领先其他家族。观察到 Claude Opus 5 Max 会出现"完成了所有子目标但过程极其低效"的情况——某个子目标上卡住做了 59 步无关操作才推进（Figure 5），这类"子目标停滞"是结果导向评测完全看不到的。效率指标细分为 Successful Effort（完成一个子目标平均用几步）、Failure Persistence（失败时还坚持了多少步）、Infeasible Persistence（发现不可行前坚持了多少步）：GPT-5.6-Sol、Kimi K3 完成效率最高（4.9、5.1 步/子目标），Minimax M3 最低效（21.2 步/子目标）；Opus 5（9.5 步）、GPT-5.6-Terra（12.1 步）能较快识别不可行任务并放弃，而 Sonnet 5 会持续尝试 39.8 步才放弃。

## 局限与疑点

- 论文没有单独的 Limitations 小节，以下是散落在正文和附录里作者自己承认、以及笔者看出的问题：
  - **LLM-Judge 在 Feasibility / Progress 两个维度上明显弱于人类**，且这两个维度本身人工标注一致性也偏低（更主观）——用它作为最终 benchmark 打分的评委（GPT-5.6-Sol Max，§5）存在系统性偏差，尤其是"过度认为任务可行"这一点会低估模型遇到不可行子目标时的真实表现。
  - **评委只能用 OpenAI GPT-5.6 系列**（因为要塞几百张截图到单次请求，Claude/Gemini/开源模型会报错），这意味着排行榜本身依赖单一厂商的模型作为裁判，存在评委厂商锁定和潜在的（虽然论文测过、结果显示不明显的）自我偏好风险。
  - 只跑一次评测（single run），依据是"任务数量多、方差应该小"的假设，但没有给出实际跨 run 方差数据来验证。
  - 全部使用 OSWorld 现成的模型 harness（采样策略、system prompt 等），继承了 OSWorld harness 本身可能存在的偏差。
  - **RepoLaunch/沙箱执行环境层面的工程细节完全没有披露**——虚拟机/容器怎么跑、镜像怎么分发、300+ 长程任务（部分需要 149 步）对执行环境的隔离和快照要求是什么，论文完全没有涉及，这是我们最关心但论文最欠缺的部分。

## 对我们的启发

- **过程式评测思路可以直接迁移成训练侧的 process reward 信号**：论文结论里明说这是"未来工作"方向（用 harness 优化或 RL 里的 process reward signal 提升 CUA 表现/效率），这和我们关心的"可验证奖励的工程实现"直接相关——如果要在 GUI/computer-use agent 训练里引入子目标级别的过程奖励，需要的基础设施是：能够在训练循环里低成本、高频地跑 LLM-Judge 打分（不只是评测时跑一次），这对推理服务吞吐和成本是新的压力点。
- **单次评测成本"数千美元/模型"、单任务 token 成本可差 20 倍**，说明 CUA 训练/评测本身就是重推理负载场景（长轨迹、多轮截图输入）。如果我们平台要支撑 CUA 类 agent 的训练评测，需要在**推理服务成本**（prompt caching、上下文长度管理）上有专门优化，不能直接套用短轨迹 agent 的调度假设。
- **长程任务（最多 149 步、平均 55 步，含数百张 1920×1080 截图）对沙箱执行环境提出的具体要求**：单任务运行时间长（标注员每任务花 5–20 小时说明人工评测本身也慢），意味着自动化评测循环里沙箱需要支持**长生命周期会话的稳定性**（避免中途崩溃导致整条轨迹作废）和**高密度并发**（跑 300+ 任务 × 多个模型的全量评测）。论文完全没披露这层工程细节，是一个值得我们自己去补的调研空白，而不是能直接抄的方案。
- **子目标停滞（59 步做无关动作却仍完成任务）这类"隐性低效"，是结果导向评测测不出来的**——如果我们要给内部 agent 训练/评测流水线加质量信号，子目标级别的进度追踪比单纯的成功率更有诊断价值，值得在我们自己的 agent 评测框架里借鉴这个拆解思路（不一定要复刻 OSWorld-Pro 的规模，但"子目标依赖链 + 分阶段判定"这个设计模式是可迁移的）。
- Follow-up 建议（可转 issue）：
  1. 关注论文提到的"process reward signals in reinforcement learning"后续工作，一旦有人把 OSWorld-Pro 式的子目标监督接入 CUA 的 RL 训练循环，值得追踪其对训练吞吐/成本的具体影响；
  2. 调研 OSWorld 官方 harness（XLANG-Lab/osworld）的执行环境实现（沙箱/虚拟机/容器方案），因为 OSWorld-Pro 复用了它，这是了解 CUA 评测基础设施现状的直接入口；
  3. 关注 LLM-Judge 判 Feasibility 偏差（推理力度越高越倾向于低估不可行任务）这个现象是否在其他"过程监督"场景（不限于 CUA）里也成立，可能是通用的 LLM-as-judge 陷阱。
