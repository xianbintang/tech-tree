# TraceDance: An Automated System for Building Agent Behavior Benchmarks from Real-World Agent Deployment Traces

> 从 25 万+ 条真实部署会话里自动挖出"某种不良行为"的决策点，直接生成可复用的行为测试基准，前沿模型平均通过率仅 26.7%。

- 对比基线：无直接对比系统（新系统），但与任务结果型基准 [[swe-bench-pro]]、[[terminal-bench]]，以及流程/安全型基准 AgentHarm、SHADE-Arena 做定位对比。

## 要解决的问题

现有 agent 基准（[[swe-bench-pro]]、[[terminal-bench]] 等）主要评估**任务是否完成**，但一个 agent 完全可以"把任务做完"的同时表现出不该有的行为——泄露访问令牌、为了让测试变绿而禁用失败的测试、未确认就执行破坏性命令等。这类问题：

1. 固定的安全/流程测试套件覆盖不到新部署场景里冒出来的新问题；
2. 部署轨迹（deployment trace）本身记录了这些真实发生过的问题，但缺一套系统把"轨迹里的一次具体事故"转成"可重复运行、可打分的测试用例"。

TraceDance 要解决的正是这个"轨迹 → 可复用基准"的转化问题。

## 方法

### 决策点延续（Decision-Point Continuation）

不重放整条轨迹、不需要参考答案，只在轨迹里定位一个"决策点"，从这个点切一刀，让被测 LLM 接上写下一步，再用行为专用 rubric 打分。三种切法（Section 3.1，附录 A.1，表 3）：

- **Action 帧**：切在目标行为发生**之前**，考察"接下来应该采取什么行动"；
- **Failure 帧**：保留观察到的失败信息，但删掉源轨迹里 LLM 对失败的响应，考察"该怎么响应这个失败"；
- **Claim 帧**：保留已完成的工作和结果，删掉源轨迹里 LLM 的结论性声明，考察"该基于这些结果做出什么声明"。

这个设计的工程价值在于：**评测不需要环境重放**（不用把整个沙箱/工具环境状态还原出来跑一遍），只需要截断后的上下文 + rubric，大幅降低了单条基准实例的运行成本。

### Anchor-and-Confirm 检索（Section 3.3）

两阶段过滤，为的是从几十万会话里高效捞出真正匹配目标行为的片段：

1. **可编程锚点（CPU 端）**：用工具报错类型、调用参数、事件顺序、关键词等结构化规则扫描候选（论文里平均扫描约 12.8 万会话/查询，产生约 706 个候选）；
2. **Fast LLM 确认**：用一个轻量模型（DeepSeek-V4-Flash）对候选做语义级复核，确认轨迹确实转向了目标行为，且上下文里有足够证据支撑判定。

### Anchor Synthesis Loop（Section 3.2）

当用户想要的行为没有预置规范时的自适应生成流程：强模型先生成四件套规范（锚点定义、确认准则、切割契约、rubric）→ 程序化安全检查 + 审查员模型代码审查 → 在真实轨迹上试跑验证（检查运行时错误、事件位置是否合理）→ 根据 Fast 模型的采样确认率反向调整锚点范围（确认率太低说明定义太宽，候选太少说明定义太窄）→ 最多迭代 5 轮（表 4），要求确认率 ≥25% 且至少 8 个确认样例才收敛。

### 基于 Rubric 的分级（Section 3.4）

三个 LLM 组成裁判小组（GPT-5.6-Sol、Gemini-3.5-Flash、Claude Opus 4.8），每条实例 0–5 分打分，平均分 ≥4 判为通过，取三者平均分作为最终结果。

## 实验与结果

- **数据规模**（Section 4.1，表 1）：Claude Code（编码场景）75,076 个会话（10,000 用于发现规律，65,076 用于构建）+ OpenClaw（通用工具使用）177,481 个会话，同样划分，合计 252,557 个会话。
- **构建成功率**（Section 5.2，图 3）：107/107 目标基准里 102 个成功构建（95.3%），共 4,125 个实例，平均 40.4 实例/基准；平均每个成功查询消耗约 552 次 LLM 调用（被拒绝的查询平均只需 1.3 次调用，说明"确认该行为在数据里根本不存在"本身很便宜）。
- **人类验证**（Section 5.3，图 3c）：抽样 100 条实例，两名标注者都确认源轨迹表现了所请求行为的比例为 84%；rubric 质量评分均值 4.75/5（90% 实例 ≥4/5）；自动分级器与人类 pass/fail 一致率 81.0%，与两名人类标注者之间的一致率（κ=0.40 vs 0.31）相当——即**自动裁判的可靠性没有明显劣于人类标注者互相之间的可靠性**。
- **前沿模型表现**（Section 5.4，表 2，图 4–5）：九个前沿 LLM 平均通过率仅 **26.7%**。总榜：Claude Opus 4.8 33.5%（第一）> DeepSeek-V4-Pro 29.3% > GLM-5.2 28.6% > GPT-5.6-Sol 27.2% > … > Qwen3.7-Max 22.9%（最低）。
  - 按行为大类（图 4a）：有效工具调用 67.9%、处理失败 33.5%、诚实声明 28.9%，**"先检查再动手"（check first）只有 8.1%**——这是当前模型最薄弱的一类行为。
  - 具体行为族（图 5，28 个预定义行为）：最强 命令有效性 72.0%、参数有效性 65.1%；最弱 提交卫生（commit hygiene）0.9%、故障日志检查 0.6%、秘密保护 6.9%。
  - 首个行动分析（图 4b）：以 TodoWrite 开头的响应通过率仅 4.6%，远低于其他开局方式的 30.8%。
  - 排名反转（图 4c）：总榜第一的 Claude Opus 4.8 在"错误引导修正"这一具体行为族上反而不敌 Kimi-K3（27.8% vs 57.8%），说明**总分排名会掩盖具体行为维度上的强弱反转**，这对"只看一个综合分挑模型"的做法是个提醒。
- **自动分级偏差**（附录 C.2，表 14–16，图 6）：三评委平均打分 2.46 分，比人类标注者的 1.68 分更宽松；GPT-5.6-Sol 对自己的输出有轻微自偏好（+0.22 分，95% CI [0.19, 0.25]），但没有改变模型间的相对排名；Claude Opus 自偏好 -0.01，无显著证据。

## 局限与疑点

- **范围限制**（Section 3.1 "Scope" 段）：目标行为必须有可观测信号支撑可编程检索；需要逐会话人工/LLM 细读才能识别的隐蔽行为超出这套系统的覆盖范围。
- 部署轨迹本身因保密协议无法公开发布，第三方无法拿完全相同的数据复现精确基准（只能复现方法论，换自己的轨迹跑）。
- 标注者反馈 rubric 相邻分数等级之间边界不清晰（表 13，21 条相关提及），说明打分细粒度本身还有改进空间。
- 自动分级器系统性比人类更宽松（+0.78 分），意味着直接拿自动分级结果去做模型选型/排行榜，可能高估模型实际表现。
- 没有对比基准（不是同类系统的头对头比较），"95.3% 构建成功率"这类数字目前只能自证，缺少第二个系统做交叉验证。

## 对我们的启发

1. **"决策点延续、不做环境重放"这个评测设计对我们平台是个成本信号**：如果我们要支持内部的行为类回归测试（比如"agent 是否会在未确认时执行破坏性命令"），不需要把整套沙箱环境状态完整还原重放，只要能从历史轨迹里稳定截出"决策点前的上下文"，评测成本可以降低一个量级——这对我们沙箱平台的启发是：**轨迹存储粒度要能支持任意点的上下文截断回放**，而不是只存最终结果或整段录像。
2. **Anchor-and-Confirm 的两阶段过滤（CPU 规则粗筛 + Fast LLM 精确认）是一个通用的"从海量生产日志里挖异常/目标行为样本"的模式**，直接可以借鉴到我们自己的 agent 生产轨迹分析里（比如挖"OOM 前的行为模式""沙箱逃逸尝试"之类的信号），成本结构（706 候选 → 552 次 LLM 调用/成功查询）给了一个大致的规模参考。
3. **自动裁判（LLM-judge）系统性比人类宽松、且自偏好效应存在但幅度可控（±0.22 分不改变排名）**，这条经验和 [[benchmark-item-validity-audit]] 里"verifier 可信度需要显式审计"的结论互相印证——如果我们内部用 LLM-judge 给沙箱里跑出来的行为打分（无论是训练用的 reward 还是评测用的 pass/fail），应该预留"和人类标注抽样对齐一次"这道工序，而不是默认信任裁判分数。
4. Follow-up 建议（可转 issue）：
   - 调研我们自己的 agent 生产轨迹里，是否已经具备"按决策点截断上下文"所需的存储结构；如果没有，评估改造成本。
   - 小规模复现 Anchor-and-Confirm 两阶段过滤，在我们自己的沙箱执行日志上试跑，看粗筛+精确认的召回率/成本比是否和论文数字量级相符。
   - 关注 TraceDance 提到的"check first"（先检查再动手）这类行为通过率极低（8.1%）是否在我们自己观测到的 agent 行为里也存在同样的薄弱环节，可能是我们平台侧要补的护栏（比如强制要求破坏性操作前的确认步骤）。
