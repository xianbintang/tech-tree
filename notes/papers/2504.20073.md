# RAGEN: Understanding Self-Evolution in LLM Agents via Multi-Turn Reinforcement Learning

> 多轮 agent RL 训练会规律性地陷入"Echo Trap"（奖励方差骤降+梯度尖峰+推理退化）；用不确定性过滤+梯度整形的 StarPO-S 可以延后/避免崩溃，rollout 的多样性/粒度/新鲜度和推理奖励设计同样关键。

## 要解决的问题

此前 LLM RL 训练（DeepSeek-R1、DeepSeek-Coder 等）几乎都是单轮、静态任务：一个 prompt 对应一次生成，奖励只看这一次输出。但 agent 场景要求模型做长程序贯决策、维护跨轮记忆、应对随机环境反馈——这类"多轮、trajectory-level"的 agent RL 训练当时基本没有被系统研究过。核心开放问题：**什么设计因素能让自我演化的 LLM agent 学得稳定、学得好？**本文把 PPO/GRPO 这类单轮方法直接套到多轮 agent 任务上做基线，观察其失败模式，再针对性设计稳定化方案。

## 方法

### StarPO：轨迹级策略优化框架

把 agent 训练形式化为 MDP $\mathcal{M}=\{S,A,P\}$：状态 $S$ 是观测/交互历史，动作 $A$ 通常是 token 序列，$P$ 是环境转移与奖励生成过程。动作按 $a_t \sim \pi_\theta(\cdot|s_t,\tau_{<t})$ 生成，环境返回 $(r_t, s_{t+1}) \sim P(\cdot|s_t,a_t)$。

与单轮方法「只优化 $J_{\text{step}}(\theta)=\mathbb{E}_{s\sim\mathcal{D},a\sim\pi_\theta}[R(s,a)]$（给定输入 $x$ 优化单次输出 $y$）」不同，StarPO 把**整条轨迹**——观测、推理痕迹、动作、反馈——当作一个整体做 rollout 和优化，目标是 $J_{\text{StarPO}}(\theta)=\mathbb{E}_{\mathcal{M},\tau\sim\pi_\theta}[R(\tau)]$。策略概率分解到 token 级似然，因此与自回归 LLM 直接兼容。

每一步，agent 产出结构化输出 $a_t^T=\texttt{<think>}\dots\texttt{</think><answer>}a_t\texttt{</answer>}$，其中 $a_t^T$ 是含推理痕迹的完整输出，$a_t$ 是环境可执行的子动作。完整轨迹 $\tau=\{s_0,a_0^T,r_0,\dots,a_{K-1}^T,r_{K-1},s_K\}$ 作为学习材料——即 StarPO 把一整条多轮交互拼接成一条长序列，用 PPO/GRPO 的 token 级更新公式在这条序列上跑（[[agent-rl-credit-assignment]] 里描述的 turn-concatenation + masking 路线，本篇是该路线的一手来源，此前该概念页只能从 Agent Lightning [[2508.03680]] 的 Related Work 转引）。

StarPO 可以套用不同 token 级优化算法：PPO（学习 critic 估计 token 级 value/advantage）或 [[grpo]]（对同一初始状态采样 $G$ 条轨迹，组内按均值/标准差归一化轨迹奖励得到 advantage，critic-free）。

### RAGEN 系统与实验设置

RAGEN 是实现 StarPO 的模块化训练/评测系统，支持结构化 rollout、可定制奖励函数、可插拔环境。四个环境覆盖不同复杂度：Bandit（单轮、随机反馈，测试风险敏感推理）、Sokoban（多轮、确定性，不可逆符号规划）、FrozenLake（多轮、随机转移）、WebShop（多轮、开放域，真实语言理解）。主实验用 Qwen-2.5-Instruct 0.5B（三个符号任务）和 3B（WebShop），H100 上训 100–200 轮 rollout-update 迭代；每批 $P=8$ 个 prompt、每个采样 $N=16$ 条轨迹，最多 5 轮、每轮最多 10 个动作；GRPO/PPO + GAE（$\gamma=1.0,\lambda=1.0$）、entropy bonus $\beta=0.001$、格式惩罚 $-0.1$。

### 发现一：多轮 RL 引入新的不稳定模式——Echo Trap

朴素套用 PPO/GRPO 在 Bandit、Sokoban 上早期有提升，但训练中期几乎必然崩溃；PPO 因为 critic 能给出更平滑的奖励估计，崩溃通常更晚、性能更高，但 FrozenLake 上 GRPO 反而更稳（该任务状态值难估计，可能反过来拖累 PPO 的 critic）。作者对比早/晚期轨迹发现：早期推理丰富多样，训练后期收敛为重复、确定性的固定话术——模型把局部被奖励的推理捷径过度放大，训练在自生成轨迹上反而抑制了探索，作者称这一失败模式为 **Echo Trap**（呼应 Shumailov et al. 2024 关于模型在自生成数据上重复训练导致多样性坍塌的发现）。

监测指标：平均奖励（Average Reward）和梯度范数（Gradient Norm）直接反映崩溃；奖励标准差（Reward Std）和输出熵（Entropy）作为**早期预警信号**——三个任务里，奖励标准差都在奖励均值真正下滑之前就先跌到谷底（如 FrozenLake-PPO std 在 step 40 骤降，reward mean 到 step 90 才崩），梯度范数骤增（Bandit step 170、Sokoban step 110、FrozenLake step 90）则标志不可逆崩溃的临界点。

### 发现二：StarPO-S——不确定性过滤 + 梯度整形

针对"奖励标准差下降先于崩溃"这一观察，作者提出核心假设：**该在方差高（结果不确定）的样本上更密集训练**（借鉴 Active Learning 的"不确定样本信息量最大"原理）。具体做法：

- **轨迹级不确定性过滤**：定义 $U(\pi_\theta,\mathcal{M},s_0)=\text{Std}_{\tau\sim\pi_\theta(\cdot|s_0)}[R(\tau)]$，每步训练只保留标准差 top-$p\%$ 的 prompt；PPO 上效果显著——保留 75% 可把 FrozenLake 崩溃点从 step 100 推迟到 140，保留 50% 直接避免崩溃；GRPO（无 critic）改善更温和。默认 $p=25\%$，但作者强调这个激进值不一定对所有场景最优。
- **梯度整形**：借鉴 DAPO 的 KL Term Removal（去掉 KL 惩罚项）和 Clip-Higher（非对称裁剪），两者都能提升成功率、延长稳定训练阶段。

StarPO-S（不确定性过滤 + 两个梯度整形技巧）相对 vanilla StarPO 在全部四个任务上都延后崩溃、提升最终性能。

### 发现三：Rollout 质量的三个可调维度

- **任务多样性 vs 每 prompt 响应数**：固定批大小下两者互相权衡；每 prompt 4 条响应（相对 32/16/8/2/1）在泛化性上最优，但前提是每个 prompt 仍要有多条 rollout 才能对比不同结果（Table 1：SokobanNewVocab 上 4 条响应达 25.39%，明显高于 32 条的 20.22%）。
- **每轮动作预算**：允许 5–6 个动作/轮时表现最好（Sokoban 33.59% @6，Table 2），预算太小无法规划、太大（7个）引入噪声转移、稀释奖励信号，性能反而下降。
- **rollout 新鲜度（Online-$k$）**：一组 rollout 被复用 $k$ 次策略更新，$k$ 越小越"在线"。Online-1（每次更新都用最新 rollout）收敛更快、泛化更好；这与 [[async-rl-training]] 讨论的 staleness/policy lag 权衡是同一枚硬币的两面——本文从"训练质量"角度独立验证了新鲜 rollout 的价值，而 async-rl-training 页面关注的是"用陈旧数据换吞吐"的系统侧权衡。

### 发现四：推理在多轮任务中会随训练衰退

单轮 Bandit 任务上，显式推理（`<think>` 痕迹）明显提升泛化——即使在语义反转的 BanditRev（专业与风险的对应关系被颠倒，推理更难）上，带推理的模型依然稳定优于无推理版本（Table 3）。但在多轮 Sokoban/FrozenLake 上，去掉 `<think>` 段（NoThink 变体）效果往往持平甚至更好；作者追踪推理痕迹长度（Table 4）发现它随训练持续缩短——模型在压抑自己的思考过程。案例分析（Appendix L）显示模型甚至会生成前后不连贯、幻觉式的推理却依然拿到高奖励，说明稀疏、延迟的多轮奖励结构无法区分"连贯推理"与"歪打正着"。作者提出一个可能方向：像 Shao et al. (2024b) 一样对缺少合法 `<think>-<answer>` 结构的输出加格式惩罚，解耦动作正确性与推理质量,但坦言更精细的奖励设计（如奖励部分正确性）仍是未来工作。

## 实验与结果

- Table 1（任务多样性）：SingleSokoban/SokobanNewVocab/FrozenLake 三个环境上，4 responses/prompt 综合最优（20.70% / 25.39% / 21.48%），明显好于极端的 32 responses/prompt（21.09% / 20.22% / 17.97%）或 1 response/prompt（19.53% / 22.27% / 12.50%）。
- Table 2（动作预算）：Sokoban 从 1 到 6 个动作/轮单调提升（12.11%→33.59%），7 个动作时回落到 22.27%；LargeSokoban 同样在 6 时达峰值 6.64%。
- Table 3（推理消融）：StarPO-S 训练 Bandit 时，Bandit 100.00% / Bandit-Rev 67.58%，NoThink 变体降到 81.25% / 56.25%；但训练 Sokoban 时 StarPO-S（21.48%）与 NoThink（20.73%）的差距很小，SokobanNewVocab 上 NoThink（26.17%）反而更高。
- Table 4（推理长度随训练衰减）：Bandit 的 `<think>` 长度从 step 0 的 66.0 token 降到 step 200 的 17.6 token；Sokoban 从 307.1 降到 89.5。BanditRev（语义反转、推理更必要）的衰减更慢（68.8→30.7），侧面印证"上下文越有挑战，推理保留得越久"。
- Echo Trap 的梯度尖峰临界点：Bandit step 170、Sokoban step 110、FrozenLake step 90（PPO 设置下）。
- 规模：主实验只在 0.5B/3B 级别小模型上跑；72B 级别及 GPT-4o/Qwen-2.5-72B 对照放在附录 D，正文未展开讨论其量化结果。

**成本/吞吐**：论文未报告 GPU 小时、墙钟时间或每次迭代成本，只给出训练迭代数（100–200 轮）与批配置（$P=8$、$N=16$、H100），没有工程规模化的资源数字。

## 局限与疑点

- 作者自己承认的局限：只在相对小规模任务上验证（0.5B–3B 为主）；没有引入成熟 RL 实践里的 replay buffer；未涉及多模态任务。
- StarPO-S 的关键超参数（保留 top-25% 高方差 prompt）是经验选择，论文明确说"这个激进值不一定对所有场景最优"，没有给出选择 $p$ 的系统性方法或跨任务的敏感性分析。
- Echo Trap 的诊断指标（奖励标准差、熵）在论文四个环境+两种算法组合里普遍成立，但四个环境都是相对简单、动作空间小的符号/半符号任务（Sokoban/FrozenLake 状态空间有限，WebShop 虽是真实场景但任务本身较短），未验证在 SWE-Bench 级别长程（20+ 轮）、动作空间巨大的编码 agent 场景下这套早期预警信号是否依然有效。
- 没有给出与 [[async-rl-training]] 里 staleness/policy lag 相关的量化交互——Online-$k$ 的发现是"新鲜度对最终质量有帮助"，但没有像 [[async-rl-training]] 那些论文一样给出"lag–质量"曲线或具体吞吐/质量权衡数字。
- 推理衰退的解释（"稀疏延迟奖励无法区分连贯推理和歪打正着"）是合理的假设，但论文没有做对照实验（例如显式设计能区分两者的奖励函数并重新训练）来直接验证因果关系，目前停留在观察+假设层面。

## 对我们的启发

1. **早期预警指标可以直接搬进我们的训练监控**：奖励标准差和输出熵在奖励均值/性能真正下滑之前就会先出现异常，如果我们的平台要给用户提供 agent RL 训练的可观测性/告警能力，这两个指标（而不只是常见的 loss/reward 曲线）应该作为标准仪表盘项，能在梯度真正炸掉之前触发人工介入或自动降级（如切换更保守的超参、缩小学习率）。
2. **不确定性过滤（StarPO-S）本质上是"按 prompt 的学习价值做调度"，可以映射成我们调度系统的一个具体策略**：训练框架如果能把"这批 rollout 的组内奖励标准差"暴露给调度层，我们的平台可以据此做"高价值样本优先重跑/复用、低方差样本降低预算或跳过"的资源分配，这和我们已经在关注的 rollout selection/prompt filtering（见 [[rollout-efficiency]]）是同一类杠杆，RAGEN 给出了一个具体、可复现的阈值化实现（top-p% 标准差过滤）。
3. **rollout 新鲜度（Online-1 最优）是对我们异步调度设计的一个直接约束信号**：如果我们的平台想通过延迟 rollout 复用（更大的 $k$）换取吞吐，RAGEN 提供了独立于系统吞吐论证之外的"训练质量"证据——延迟越大收敛越慢、泛化越差，这应该和 [[async-rl-training]] 里纯系统侧的加速比数字放在一起，作为设定 staleness 上限时的双重约束（不能只看吞吐，还要看训练质量退化）。
4. **每轮动作预算存在"甜蜜点"（5–6 个）**，对我们设计 agent-环境交互协议（一次 LLM 调用允许提交几个动作再让环境执行/返回）有直接参考价值：预算太小限制规划、太大引入噪声转移——这是一个我们在设计沙箱/执行环境的"每步反馈粒度"时可以直接借鉴的经验区间，虽然论文只在 Sokoban 类符号环境验证过，迁移到代码/终端场景需要重新测。
