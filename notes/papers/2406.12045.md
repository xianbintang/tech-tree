# τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains

> 用 LLM 模拟真实用户，让 agent 在多轮对话里一边用工具查改数据库一边遵守领域政策，发现 gpt-4o 也只能解出 <50% 任务，且同一任务反复跑的一致性（pass^8）在 retail 域跌到 <25%。

## 元信息

- 机构：Sierra（提出方，AI 客服 agent 公司）+ Princeton University
- 发表：2024-06-17（arXiv v1）
- 链接：[arXiv](https://arxiv.org/abs/2406.12045) · [代码 github.com/sierra-research/tau-bench](https://github.com/sierra-research/tau-bench)
- 对比基线：BFCL、ToolBench 等单步/静态工具调用基准；τ-bench 之后被 [[terminal-bench]]（2601.11868 笔记里列为对比基线）、AgentScaler（见 [[gef-loop]]）等多篇后续工作用作 function-calling 一致性的评测集

## 要解决的问题

已有 agent 基准大多是简化的"指令-执行"单步设置：没有真人参与的多轮交互，也不测 agent 能否遵守特定领域的复杂政策规则。但真实部署（如客服）要求 agent 同时满足三件事：长程地跟人和 API 无缝交互、精确遵守领域政策、在大规模重复调用下保持一致可靠——现有基准都没有同时覆盖这三点。

## 方法

### 任务形式化：POMDP + 双状态空间

把一次对话建模为 POMDP，状态空间 𝒮 = 𝒮_db ⊗ 𝒮_user（数据库状态 ⊗ 用户状态的组合）。每个任务由模块化组件构成：JSON 数据库、Python API 工具集、Markdown 写的政策文档、JSON 任务实例（含用户目标和标注的期望最终数据库状态）。

### 两个领域：retail 与 airline

- **τ-retail**：500 用户、50 商品、1,000 订单；7 个写操作 API + 8 个只读 API；115 个任务。
- **τ-airline**：500 用户、300 航班、2,000 订单；6 个写操作 API + 7 个只读 API；50 个任务。

### 用户模拟器

用 gpt-4-0613 根据任务指令生成用户话术（用户侧 temperature=1.0 引入随机性，agent 侧 temperature=0.0）。政策约束一部分被硬编码进 API（如库存不足直接拒绝退货），一部分要求 agent 自己从政策文档里推理（如根据会员等级和舱位判断行李额度）——这是**软约束**，agent 必须真正"读懂政策"而非只调用 API 就能通过。

### 评测方式：终态数据库比对

对话结束时比较数据库实际状态与人工标注的目标状态是否一致，不检查中间过程（对话轮次、具体工具调用序列），只看结果是否达成——这个"结果驱动"评测思路后来在 [[terminal-bench]] 里被系统化为"终态测试"标准。

### pass^k 指标

pass^k 定义为同一任务独立重复 k 次试验、k 次**全部**成功的期望概率：

$$\text{pass}^k = \mathbb{E}_{\text{task}}\left[\frac{C(c,k)}{C(n,k)}\right]$$

其中 n 是总试验数、c 是成功次数。与代码生成常用的 pass@k（k 次里**至少一次**成功，衡量"能不能发现一个解"）方向相反：pass^k 衡量的是"同一个 agent 反复面对同一任务时是否稳定可靠"，专门用来揭示 LLM agent 的非确定性行为风险。

## 实验与结果

- **主结果（Table 2，pass^1）**：gpt-4o 在 retail 61.2%、airline 35.2%（平均 48.2%）；gpt-4-turbo 57.7%/32.4%；claude-3-opus 44.2%/34.7%；gpt-3.5-turbo 仅 20.0%/10.8%——最强模型也在近半数任务上失败。
- **pass^k 随 k 快速下滑（Figure 4）**：gpt-4o function-calling 在 retail 上 pass^1 61.2% → pass^8 约 25%，说明单次成功率之外，"能不能稳定复现"是独立且更严峻的问题。
- **function calling 显著优于文本格式 ReAct**（Figure 3）：给 function-calling agent 加推理轨迹没有额外提升，但 ReAct 式文本工具调用普遍更弱。
- **政策消融（Table 3，去掉政策文档后）**：gpt-4o 在 airline 上从 35.2% 暴跌到 10.8%（-22.4pp），retail 上从 61.2% 到 56.8%（-4.4pp）——airline 域的政策约束显著更"硬"，agent 更依赖读懂规则而非常识推断；gpt-3.5 两域降幅相对更均匀（-5.5pp / -1.2pp）。
- **失败模式分析（36 个 gpt-4o 在 retail 上的失败案例）**：约 44% 是参数/信息错误（复杂数据库推理出错）、约 25% 是决策错误（没遵守规则）、约 19% 是复合请求只完成一部分。

## 局限与疑点

- 用户模拟 LM（gpt-4-0613）本身可能产生打字错误、歧义表达或有限的推理能力，这些"用户端噪声"会和"agent 能力不足"混在最终分数里，论文未做区分实验。
- 任务筛选/校验用 gpt-4-turbo 辅助，可能引入模型偏好导致的隐性筛选偏差。
- 领域政策相对真实业务仍偏简化；标注人工成本高，任务规模（165 个）远小于后续基准（如 [[terminal-bench]] 的 89 个精审任务对比，量级接近但覆盖领域窄得多，只有客服两个垂类）。
- 仅覆盖零售/航空客服场景，医疗、法律、税务等更高风险的政策密集型领域完全未测试。

## 对我们的启发

1. **pass^k 是我们评估"agent 能否上生产"的关键指标，而不只是 pass@1**：客服类场景一旦部署就要被成千上万用户反复触发同一类任务，pass^8 在这里从 61% 掉到 25% 说明"单次演示成功"和"生产环境稳定可用"是两回事。我们内部评测/验收流水线如果只看一次性通过率，可能会严重高估 agent 在真实反复调用场景下的可靠性——这与 [[benchmark-item-validity-audit]] 强调"pass rate 混淆了难度和可行性"是同一类"单一分数不可信"的问题，只是维度不同（一致性 vs 可行性）。
2. **"数据库终态比对"是一种低成本、高保真的评测范式，值得复用到我们自己的多轮工具环境**：不需要判断中间对话质量，只需要在环境里维护可比对的结构化状态（数据库/文件系统/配置），这比 LLM-as-judge 便宜且客观，也比纯规则匹配更贴近真实结果导向的验收标准。
3. **软政策约束（policy-as-context）是这类环境的独特隔离/沙箱需求**：政策文档本身是环境状态的一部分，需要和 API/数据库一起打包分发、版本化管理；如果我们要搭建面向"多轮用户+工具+政策"训练场景的沙箱环境，除了常规的代码执行隔离外，还要支持"随任务实例变化的规则文档"作为一等公民资源注入运行时。

可执行的 follow-up：
- 调研 τ2-Bench（[[gef-loop]] 笔记提到的后续版本）相对 τ-bench 在任务规模、领域覆盖、pass^k 定义上做了哪些改动，评估是否该建独立笔记。
- 查 AgentScaler（2509.13311）论文里具体在 τ-bench/τ2-Bench 上的分域成绩，核实 [[gef-loop]] 笔记里 "ACEBench-en Overall 75.7 vs 77.4" 这条数字是否也有 τ-bench 对应的具体分数可以补充。
- 评估把 pass^k 指标直接搬进我们内部 agent 验收流水线的可行性：需要多大的重复试验预算（k 取多少）才能可靠区分"运气好"和"真的稳定"。
