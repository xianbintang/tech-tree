# DHSched: Stateless Control for Stateful Real-Time Avatar Serving

> 用 (WorkerID, epoch) 生成号把"控制面分配"和"数据面执行权"拆开，让无状态的调度副本也能安全接管有状态、长生命周期的 GPU 会话。

## 元信息

机构：AiShiWeiLai（爱诗未来，数字人/实时 avatar 服务商）+ 四川大学计算机学院 / 发表：2026-09-22（arXiv cs.DC）/ 链接：[arXiv](https://arxiv.org/abs/2609.26363) · [HTML](https://arxiv.org/html/2609.26363v1)（无公开代码）
对比基线：Slicer（OSDI'16）、Orleans（SoCC'11，含 ActivationCountBasedPlacement）、Llumnix（OSDI'24）、TurboServe、vLLM/Orca/AlpaServe/Sarathi-Serve、Kafka consumer group epoch、Azure Service Fabric

## 要解决的问题

实时数字人（avatar）服务把持续文本流转成语音、面部动作、渲染视频、RTC 媒体，每个 live 会话是**长生命周期、有状态、GPU-backed**的执行单元：Worker 上保留推理上下文、渲染状态和 RTC 连接，一个 Worker 常同时托管数百个 live。

弹性调度会因为负载倾斜、Worker 故障、扩缩容、抢占、计划性 drain 不断把会话从一个 Worker 迁到另一个。问题在于：**重新分配（控制面）**和**执行权转移（数据面）**不是同一时刻发生的——Dispatch 把共享状态改成指向新 Worker B 时，旧 Worker A 的 GPU runtime 和 RTC 连接可能还活着；如果两边都继续收文本输入，就会产生**双主（dual-owner）冲突**，输出互相打架。

传统做法是让控制器（controller）自己保留每个会话的归属状态来串行化所有权变更——但这把会话生命周期绑死在控制器的扩缩容和 failover 路径上，控制器就不能是无状态的。论文要回答的问题是：**无状态的对等（peer）控制器副本，能不能安全地管理长期存活的有状态实时会话？**

这与经典 LLM serving 调度（vLLM/Orca/AlpaServe/Sarathi-Serve）不同：它们的调度单元是单次推理请求/执行上下文；Llumnix、TurboServe 这类"GPU 迁移"系统虽然处理长生命周期流式负载，但迁移路径要把执行状态（如 KV cache）从源端搬到目的端。DHSched 的会话则假设可恢复状态（元数据 + 待处理输入）已经在 Worker 之外，不需要源端参与即可重建。

## 方法

### 架构总览

系统分三条路径：Dispatch（创建/重分配/恢复的决策）、Infer-Controller（承载持续文本流的输入通道）、Worker（GPU 推理/渲染 + RTC 连接的实际执行体）。Dispatch 是**无状态对等副本**，没有 leader 选举，也没有副本间协调协议；权威的 ownership 和容量状态存在 Redis 里。

```mermaid
flowchart LR
  App[应用/文本流] --> IC[Infer-Controller\n持有 PushText 流]
  D1[Dispatch 副本 1] -->|CommitGeneration\nCAS| Redis[(Redis\nlive_meta / worker_weight\n权威 ownership+容量)]
  D2[Dispatch 副本 2] --> Redis
  Redis -->|读取 generation| W[Worker\nGPU runtime + RTC]
  W -->|首次 PullText 携带 (liveID, WorkerID, epoch)| IC
  IC -->|Claim: 原子设置 active| Redis
  IC -->|每次状态推进都校验 generation| W
```

### 核心机制：generation = (WorkerID, epoch)

每个会话 s 的权威 ownership 记录是三元组

$$O(s) = \langle \mathsf{epoch}(s), \mathsf{selected}(s), \mathsf{active}(s) \rangle$$

- `selected`：控制面（Dispatch）选中的 Worker；
- `active`：数据面（Infer-Controller）确认"已完成认领"的 Worker；
- `epoch`：单调递增的世代号，区分同一 WorkerID 在不同时间点的两次执行（A→B→A 时，第一次的 A 和第二次的 A 是不同 epoch）。

输入释放规则（式 3）：`ReleaseInput(s, w, e)` 仅当

$$\mathsf{epoch}(s)=e \;\land\; \mathsf{selected}(s)=w \;\land\; \mathsf{active}(s)=w$$

三者同时满足才放行——单靠 WorkerID 判断不够，因为 Worker 身份会在 A→B→A 这种序列里复用。详见 [[epoch-fencing]]。

1. **CommitGeneration**（Dispatch）：选定目标 Worker、拿到容量准入后，做条件更新（CAS 语义）：epoch 递增、`selected` 设为新 Worker、`active` 清空。同一时刻只有一次基于旧 epoch 的提交能成功，其余返回 `STALE`。提交立刻完成，不等旧 Worker 的 runtime 真正下线。
2. **Claim**（Infer-Controller）：新 Worker 建好本地 runtime、加入 RTC 房间后，第一次 `PullText` 带上 `(liveID, WorkerID, epoch)`，原子性地把 `active` 从空设为该 Worker（仅当 `selected`/`epoch` 匹配）。
3. **逐条输入的持续校验**：之后每一次会推进会话状态的输入释放（不只是首次 claim）都要重新核对 generation。旧连接/旧 runtime 可以继续物理存活，但拿不到新输入——**执行权限的边界在"数据面持续校验"，而不是"控制面提交"或"仅认领一次"**。

### 单主（single-owner）安全性证明与形式化验证

论文给出不变式证明：对任意会话，任意时刻满足 `ReleaseInput` 条件的 `(w, e)` 至多一对（式 4），并逐一分析 CommitGeneration / Claim / ReleaseInput 三个操作如何维持这个不变式。进一步写了 **TLA+ 规约**，用 TLC 检查 5 条不变式：
- I0 MonotonicEpoch（epoch 只增不减）
- I1 UniqueGeneration（同一 epoch 下至多一个 selected Worker）
- I2 SingleOwner（任意可达状态下至多一个 (Worker, epoch) 满足释放条件）
- I3 NoResurrection（携带旧 epoch 的操作在会话推进之后不能再修改 ownership）
- I4 CapacitySafety：$\mathsf{committed}(w) + \mathsf{reserved}(w) \le \mathsf{capacity}(w)$

### 容量安全的会话调度（stale-view 下的 placement）

Dispatch 副本各自缓存 Pool 的成员/负载快照（刷新周期约 200ms–1s）。如果直接按缓存负载做 strict-min（贪心选最闲的 Worker），并发副本会在快照未刷新期间反复选中同一个"看起来最闲"的目标，造成负载倾斜和大量准入失败（"cache herding"）。详见 [[stale-view-placement]]。

DHSched 的解法是三层叠加：
1. **副本本地增量修正**：$\hat\ell_r(w) = \ell_{\text{snap}}(w) + \delta_r(w)$，$\delta_r(w)$ 是本副本自上次快照以来已提交的分配数，不需要副本间通信。
2. **跨 Pool 水位线**：先按 DigitalID 的 Pool 资格与配置优先级过滤，再在同优先级里选归一化水位线 $\mathrm{WL}_r(P) = (L_{\text{snap}}(P)+\Delta_r(P))/C(P)$ 最低的 Pool。
3. **Pool 内低负载分层随机采样**（bottom-tier sampling）：不是直接取 argmin，而是在"rank ≤ k(P) 且负载在最小值 τ 窗口内"的候选集合里**均匀随机采样**，把并发选择打散，而不是让所有副本挤同一个缓存最小值。
4. **原子容量准入兜底**：无论前面基于多"陈旧"的视图排出候选，最终能不能真正拿到这个 Worker 由存储侧原子 `Reserve` 操作决定（`committed(w)+reserved(w) ≤ C_w`），失败则换下一个候选（FULL 后继续尝试，预算内约 8+6N 次 Redis 操作，2–3 次尝试约 20 次操作）。

### 无源端依赖的恢复（source-independent recovery）

Worker 故障/超时会异步产生恢复条目，每条携带 `(liveID, sourceEpoch)`——检测到故障时的 epoch 快照。消费该条目前先比对当前 epoch：**只有 epoch 仍等于 sourceEpoch 时才继续**，否则说明别的操作已经推进过 ownership，直接丢弃这条延迟/重复的恢复工作（避免"复活"已经过期的所有权，即 NoResurrection）。

对当前有效的恢复：选新 Worker、拿容量准入、提交更高的 generation，目标 Worker **直接从共享的会话元数据和待处理输入重建执行状态**，不需要源端参与、不搬运 GPU/RTC runtime 状态——这是与 Llumnix/TurboServe（都要把 in-flight 的执行状态从源端搬到目的端）的关键区别。同一套 generation 转移机制同时服务于 Worker 故障、计划性 drain（drain 先准备好替换容量、等到合适的流边界再切换，限制单 Worker 并发切换数，避免一波 runtime 创建/RTC 建连风暴，有 60s 的有界等待防止长期占用的 live 无限期拖延 drain）、主动重分配三种场景。

## 实验与结果

**生产环境**：单日峰值 49,987 个并发 live 会话；2026-06-10 完成 9,927 次会话迁移，**零**双主冲突、**零**容量超卖；峰值时 CreateLive P99 延迟 98.3ms，PushText P99 延迟 16.5ms。

**执行权正确性（100,000 次随机化对照实验/协议，Table 2 附加了真实 Redis 参考实现的验证）**：
- Assignment-only / Epoch-at-commit：99.9% 的运行违反单主约束
- Claim-only：99.4% 违反
- 仅按 WorkerID 做逐条校验（不含 epoch）：整体 14.0% 违反，**但在 A→B→A 这类 Worker 复用的子集里高达 25.5%**——这正是论文强调"仅 WorkerID 不够，必须有 epoch"的关键证据
- DHSched（完整 generation 校验）：**0%** 双主冲突或过期 generation 释放
- 真实 Redis 参考实现（10,000 次 A→B→A）：generation 校验 0% 过期释放 vs. 仅 WorkerID 校验 20.2%；10,000/10,000 次"提交后连接丢失再重试"均正确返回已提交的 generation，无重复副作用

**调度质量（128 Worker，16,000 会话突发，16 个 Dispatch 副本，30 个随机种子）**：
- 每快照 1,000 次分配时：Strict-Min 的 max-min 负载差达 205.7、27,549 次候选被拒；Orleans-AC 模型 66.3；DHSched 63.6（与 Orleans-AC 相当，远好于贪心 Strict-Min）
- 8 个异构 Pool + 12 类 DigitalID 的层级workload：Orleans-AC 模型 45.4% 的会话落在非首选 Pool 层级、平均 609.9 次 Create 失败；加上 Pool 优先级后降到 14.1% off-tier 但仍有 365.3 次平均失败；Cached Least-Load 几乎能跑完但 84.0% 落在非首选层；**DHSched 12.3% off-tier，且 16,000 次 Create 全部成功（0 失败）**
- 额外用**真实发布的 Orleans 10.3.0**（未改动的 ActivationCountBasedPlacement）跑了对照：2–16 个本地 silo、128 万次激活全部完成，负载差为均值负载的 0.04%–1.1%

**容量准入并发安全**：非原子 read-check-write 在 2 个并发者时超卖 35.3%，16 个并发者时 93.7%，64 个并发者时 100%（最大超卖量 +1 到 +62）；原子 Reserve 在所有并发级别下超卖率均为 0%（真实 Redis 环境复现同样结论）。

**恢复正确性**：不做 sourceEpoch 校验时，延迟恢复条目在"延迟概率 0.10"下有 6.8% 会"复活"过期所有权，概率 0.50 时高达 34.9%；加上 epoch 校验后，所有测试概率下均为 0%。

## 局限与疑点

- **适用边界是论文自己划的**：方法要求"可恢复状态已经外部化"（会话元数据 + 待处理输入不依赖源 Worker），且状态推进的输入必须经过一个能校验 generation 的关卡（Infer-Controller）。如果恢复必须依赖只存在于源 runtime 里的执行状态（比如 LLM 推理里的 KV cache），这套无源端依赖的重建就不成立，退化成 Llumnix/TurboServe 那种必须搬运状态的场景——论文在 Discussion 里也承认了这一点。
- **权威存储（Redis）本身的可扩展性/可用性未评测**：论文明确把"扩展 Dispatch"和"扩展权威存储"说成两个独立问题，但通篇没有给 Redis 分片、多活、故障切换方面的数据——它是整个方案事实上的单点权威源，论文没有讨论这一层出问题时会怎样。
- **对比基线部分是"模型"而非真实系统在同一生产规模下跑出来的**：Orleans-AC、guard-lease、source-assisted 等对照协议是作者按论文描述抽象出的模型，运行在 DHSched 自己的 workload 生成器上；虽然另外补了一组跑真实 Orleans 10.3.0 的实验，但那组实验是在本地 2–16 个 silo 规模，与生产 5 万并发会话规模不在同一量级，只能算侧面印证。
- Bottom-tier 采样里的层大小 k(P)、分数窗口 τ 等具体取值论文只说"随 Pool 规模扩大、保留最小层大小"，没有给出生产环境实际配置的数字。
- 论文场景是实时数字人渲染（cs.DC 视角的调度问题），不是 agent/RL 训练常见的沙箱执行环境，但 generation fencing 和 stale-view 调度这两个机制本身与具体业务无关，可以直接迁移。

## 对我们的启发

1. **会话/沙箱热迁移的"控制面提交 vs 数据面认领"分离**：如果我们平台要支持有状态沙箱（比如长跑的 REPL/kernel session）的活迁移或快速故障转移，DHSched 的三段式（Commit 生成新 generation → 目标 Claim → 每次交互都重新校验 generation）比"迁移完就切流量"更能避免迁移窗口期的双主/脑裂问题，尤其是在消息可能重复投递、Dispatch 副本可能崩溃重试的场景下。
2. **epoch fencing 可以替代调度器的 leader 选举**：我们目前如果依赖单一调度器或选主来串行化会话归属变更，这篇论文提供了一个不需要选主、只需要一个线性一致存储（Redis 足够）+ CAS 语义的替代方案，值得评估能不能把调度器做成真正无状态、水平扩展的对等副本。详见 [[epoch-fencing]]。
3. **stale-view 下的 bin-packing/放置策略**：我们做沙箱调度时如果多个调度副本各自缓存集群负载视图，"贪心选最闲节点"的策略在高并发下几乎必然出现和本文 Strict-Min 类似的负载倾斜/超卖问题。副本本地增量修正 + 低负载分层随机采样 + 最终原子准入兜底，这套组合值得直接搬到我们自己的调度器设计里。详见 [[stale-view-placement]]。
4. **"能不能不搬状态"是一个值得显式建模的分类问题**：source-independent recovery 只在会话状态已经外部化时成立；对我们平台而言，值得梳理哪些沙箱/会话状态天然可以外部化（元数据、待处理任务队列）、哪些必须真迁移（内存态、GPU 显存里的 KV cache 或模型状态），针对两类分别设计恢复路径，而不是一刀切。

**可执行 follow-up**：
- 调研 Slicer（OSDI'16）的 generation + CAS 强一致性路径与 DHSched 的差异，评估能否直接复用到我们的调度器（可开一个 research-topic issue）。
- 梳理 Kafka consumer group 的 epoch/generation fencing 实现细节，和 DHSched 的 ReleaseInput 校验做对比，抽象出一个可复用的 "epoch fencing" 组件设计模式文档。
- 盘点我们自己平台里哪些会话/沙箱状态"可外部化"（可支持 source-independent recovery），哪些必须做真正状态迁移，整理成决策表，指导后续故障恢复设计。
