# AReaL: A Large-Scale Asynchronous Reinforcement Learning System for Language Reasoning

> 完全异步 RL 系统：rollout worker 持续生成不等待、训练 worker 攒够 batch 就更新，配合 staleness 控制 + 解耦 PPO 目标，实现 2.77× 训练加速且精度不降。

## 元信息

机构：IIIS, Tsinghua University（通讯）、Ant Group、HKUST / 发表时间：2025-05-30（arXiv v1，本笔记基于 2026-03-02 修订的 v5）/ 链接：[arXiv](https://arxiv.org/abs/2505.24298) · [Code](https://github.com/inclusionAI/AReaL/) / 对比基线：VeRL（同步系统的 SOTA）、同步版 AReaL（Sync.AReaL，论文自建的受控对照）

## 要解决的问题

大规模 RL 后训练里，长思维链 LRM（如 R1-Distilled 系列）的单条输出长度差异极大（数千到 32K token）。主流同步 RL 系统（严格交替 generation → training）必须等一个 batch 里最长的输出生成完才能开始训练，导致 GPU 大量空闲；且同步系统按设备均分生成负载，单卡解码 batch 变小，容易掉进 memory-IO-bound 区间，加设备也不再提升吞吐（§3.2 两条实测动机）。此前的"局部重叠"方案（一步/两步 generation-training overlap）仍要求同一训练 batch 内样本来自同一模型版本，没有从根本上解决空闲问题。

## 方法

**架构（§4.1）**：四个组件彻底解耦，通过 replay buffer 和参数服务器串联，不再有 generation/training 的全局 barrier：
- **Interruptible Rollout Worker**：处理 `generate`（正常生成）和 `update_weights`（中断所有在途生成、丢弃旧权重算出的 KV cache、加载新权重后重新计算 KV cache 并继续解码未完成序列）两类请求。一条轨迹因此可能由多个策略版本的片段拼接而成。
- **Reward Service**：独立评估生成结果（如代码任务里跑单测），与生成/训练解耦成单独服务。
- **Trainer Workers**：持续从 replay buffer 采样，攒够 batch size 就做 PPO 更新，参数写入分布式存储；buffer 里的数据只用一次以保证新鲜度。
- **Rollout Controller**：桥接三者——读数据集发起生成请求、把结果送 reward service、把（轨迹, reward）存入 buffer、在训练 worker 更新完参数后触发 `update_weight`。

**两个由异步引入的算法问题（§4.2、§5）**：
1. **Staleness-aware training**（§5.1）：引入超参 $\eta$（一个 batch 内允许的最大策略滞后），$\eta=0$ 退化为同步 RL。控制器按公式 $\lfloor(N_r-1)/B\rfloor \le i+\eta$（$N_r$ 为已生成轨迹数、$B$ 为 batch size、$i$ 为当前策略版本）限流生成请求节奏，并优先用 buffer 里更老的轨迹组 batch，从而把陈旧度关进一个可控上限，而不是靠限制吞吐硬保同步。
2. **Decoupled PPO 目标**（§5.2，来自 Hilton et al. 的解耦 PPO 思路）：把标准 PPO 里"生成轨迹的行为策略"与"约束更新的 proximal 策略"拆成两个不同的量——$\pi_{behav}$ 是真正采样轨迹的策略（可能因中断跨越多个版本），$\pi_{prox}$ 是每次模型更新前的那个策略版本，只用作 clip 的信任域中心。公式 5：
   $$J(\theta)=\mathbb{E}_{q\sim\mathcal{D},a_t\sim\pi_{behav}}\Big[\sum_t \frac{\pi_{prox}}{\pi_{behav}}\min\big(u_t^{prox}(\theta)\hat{A}_t,\ \mathrm{clip}(u_t^{prox}(\theta),1\!-\!\epsilon,1\!+\!\epsilon)\hat{A}_t\big)\Big]$$
   其中 $u_t^{prox}(\theta)=\pi_\theta(a_t|s_t)/\pi_{prox}(a_t|s_t)$。这个改写的关键收益是**不再要求同一 batch 内所有 token 来自单一策略**——Proposition 1（Appendix D 证明）说明"跨版本拼接的中断轨迹"在数学上等价于存在一个统一的行为策略 $\pi_{behav}$ 采样得到，因此可以直接套用重要性采样，interruptible generation 与该目标是自洽的。与 [[rollout-training-mismatch]] 里讨论的"重要性加权修正"是同一种数学工具，但这里修正的是**时间维度的策略滞后**（policy lag），不是数值 kernel 差异。

**系统实现优化（§6）**：GPU 计算与 CPU 侧操作（rule-based reward 计算、TCP 数据搬运）用独立线程 + 流水线重叠；rollout worker 内用 asyncio 协程并发多个请求避免互相阻塞；训练侧用**无 padding 的序列打包 + 动态 micro-batch 分配算法**（Algorithm 1：按长度降序贪心装箱到不超过 token budget 的 micro-batch，同时满足最少 micro-batch 数下限）取代固定 micro-batch 数的传统方式。底层基于 ReaLHF 框架，生成用 SGLang v0.4.6，训练用 Megatron-Core v0.11.0，SLURM 管资源调度。

## 实验与结果

**Setup**：64 节点×8 GPU 的 H800 集群，NVLink 机内 + RoCE 3.2Tbps 机间；R1-Distilled-Qwen 系列 1.5B~32B 为基座；math 用 Qwen 评测协议，code 用 LiveCodeBench 官方协议；inference:training 设备配比固定 3:1（早期实验里优于 1:1，未做动态调整）；math 默认 $\eta=8$，code 默认 $\eta=4$。

- **端到端加速（Table 1）**：1.5B（AIME24 42.2 vs VeRL 43.1\*）训练时长 14.8h vs VeRL 33.6h vs Sync.AReaL 41.0h，即**训练时间缩短 2.77×**；7B（63.1 vs Sync.AReaL 63.0）25.4h vs Sync.AReaL 57.7h；14B（LiveCodeBench 58.1 vs VeRL 57.9\*）21.9h vs VeRL 44.4h；32B（61.0 vs Sync.AReaL 61.2）31.1h vs Sync.AReaL 51.1h。**关键结论：加速伴随的是持平或更好的精度，不是拿精度换速度**。
- **Scalability（§7.3, Figure 4）**：对比 VeRL，AReaL 在 16k/32k 上下文长度下呈近似线性扩展，最高 2.5× 吞吐；VeRL 在 32k+32B 配置下持续 OOM（数据点缺失）；上下文越长 AReaL 优势越大，因为长生成可以被异步流水线完全隐藏在关键路径外。
- **Staleness × 解耦目标消融（§7.4, Table 2，1.5B math）**：naive PPO（无解耦目标）哪怕 $\eta=1$ 都明显掉分（AIME24 从 oracle 42.0 掉到部分配置 23.3）；加上解耦目标后 $\eta\le8$ 基本能维持 oracle 水平（AIME24 41.0~42.2），$\eta\to\infty$（无约束）仍比 oracle 差（36.9 vs 42.0）——说明**解耦目标是必要条件但不是充分条件，staleness 上限仍要显式约束**。
- **系统消融（§7.5）**：动态 micro-batch 分配平均带来 **30%** 吞吐提升（Figure 6a）；interruptible generation 在 1.5B/7B、4 节点配置下分别带来 **12%/17%** 生成吞吐提升（Figure 6b）。
- **附加结果（Appendix C）**：换成 Llama 架构（DeepSeek-Distilled-Llama-8B）、换成 RLOO 算法都验证了同样的 staleness-throughput 权衡趋势；小规模学术设置（8×GPU，1.5B）里 $\eta$ 从 0 升到 16，吞吐从 27.1k 升到 52.0k（token/s 量级），精度基本持平甚至略有波动。

## 局限与疑点

- **训练:推理设备配比（3:1）是启发式选定，非动态**——论文自己在结论里承认最优配比应随 setting 变化，甚至应该在训练过程中动态调整，但本文没有实现这一点。
- **只评测了单轮数学/代码任务**，作者在 Appendix E 明确把"多轮交互与 agentic 场景"列为未来工作——这意味着 AReaL 论文本身**没有验证**其架构在长程 agent/tool-use rollout（更贴近我们关注的方向）下的表现，需要看 AReaL 后续版本或社区分支（如 AReaL-Hex 等，见 [[async-rl-training]] 笔记引用）。
- Table 1 里 VeRL 部分数字带 "\*"，是引用自 DeepScaleR/DeepCoder 论文报告的最佳可复现结果，而非作者用同一套硬件重新跑出来的——吞吐/时长对比虽然是作者自己复现的（用最新 VeRL 代码），但精度数字的可比性打了折扣。
- 没有给出 rollout worker 中断+权重重载的具体延迟开销（只定性描述机制），也没有报告 replay buffer 的内存占用或数据新鲜度以外的存储成本。
- 消融只在 1.5B 规模做，未验证解耦目标 + staleness 控制的结论是否在 32B 规模下依然成立（大规模端到端结果只报了最终精度和训练时长，没有单独做 staleness 消融）。

## 对我们的启发

1. **"用中断 + 重算 KV cache 换取权重实时同步"是一个具体可评估的设计模式**：AReaL 的 interruptible rollout worker 在权重更新到达时丢弃旧 KV cache、重算后继续解码，这本质上是"用一次性计算浪费换取生成不中断服务"——我们做沙箱/推理 serving 时如果要支持类似的"训练权重热更新"能力，这是一个可以直接复用的机制原型，且论文给了效果对照（interruptible generation 带来 12%~17% 吞吐提升）。
2. **训练:推理设备配比是运行时可调的旋钮，而不是架构常数**：论文承认 3:1 只是启发式且应该动态调整，这正好是我们调度系统能补的能力——如果我们的平台能在 RL 训练作业运行时感知 rollout/training 两侧的排队深度并动态重新分配 GPU 配比，就是在补 AReaL 自己承认的缺口（可与 [[rollout-training-disaggregation]] 里"按队列深度独立伸缩"的思路结合）。
3. **Staleness 上限 $\eta$ 是一个需要暴露给用户/平台的一等公民参数**，不是训练框架内部细节：论文的消融清楚显示"多大的陈旧度可以接受"直接决定吞吐-精度权衡（Table 2），如果我们要托管客户的异步 RL 训练作业，应该把 $\eta$（或等价的 staleness 预算）做成可观测、可调的调度参数，而不是让它被训练代码写死。
4. Follow-up（可转 issue）：
   - 精读社区对 AReaL 架构的 agentic/多轮扩展（AReaL-Hex 等，见 [[async-rl-training]] 提到但尚未精读的分支），确认本文"只测单轮任务"的局限是否已被后续工作补上。
   - 核实动态 micro-batch 分配算法（Algorithm 1，贪心装箱）与我们自己序列打包/批处理策略的差异，看 30% 的吞吐提升能否复现到我们的 serving 场景。
   - 对比 AReaL 的 replay buffer + 参数服务器架构与 [[hybridflow]]（veRL）的单控制器 dataflow 编排，具体量化两种架构在"训练/生成权重切换开销"上的差异（veRL 论文给了 Table 2 的公式，AReaL 论文没有对应数字）。
