# AgentBench: Evaluating LLMs as Agents

> 首个系统性评测 LLM-as-Agent 的多环境基准（8 类异构环境、29 个模型），并给出一套 Docker 隔离 + Server-Client 解耦 + max-flow 调度的评测框架。

## 元信息

- 机构：清华大学 THUDM + 智谱 AI（资助 GPU/API 成本）+ Ohio State University + UC Berkeley
- 发表：2023-08-07（arXiv v1），ICLR 2024 收录，v3 修订至 2025-10-04（补充 claude-3、glm-4 等后续模型结果）
- 链接：[arXiv](https://arxiv.org/abs/2308.03688) · [代码 github.com/THUDM/AgentBench](https://github.com/THUDM/AgentBench)
- 对比基线：文本游戏类前置工作 TextWorld/Jericho/LIGHT、代码执行类 APPS/HumanEval/MBPP；并行工作 InterCode（同期发布，覆盖 Bash/SQL 交互，与 AgentBench 的 OS/DB 环境类似但范围更窄）

## 要解决的问题

2023 年中，LLM-as-Agent 的应用（AutoGPT、BabyAGI 等）已经爆发，但缺少系统性、标准化的评测：此前的 agent 评测框架要么局限于单一任务/单一环境，要么要求 Task、Agent、Evaluation 三方组件同机部署（进程内通信或子进程），一次只能评一个 agent 对一个任务，无法规模化、无法跨设备部署。同时，静态文本游戏环境动作空间闭合、多模态具身仿真器又偏离真实使用场景，都不适合纯文本 LLM 的实际部署评估。

## 方法

### 8 类环境，3 种 grounding

- **Code-grounded**：Operating System（Ubuntu Docker 里跑真实 bash 交互，Success Rate 指标）、Database（真实 SQL 接口/数据库，SR）、Knowledge Graph（Freebase 规模的部分可观测 KG 问答，Answer F1）。
- **Game-grounded**：Digital Card Game（简化版 Hearthstone 式对战 Aquawar，胜率）、Lateral Thinking Puzzles（海龟汤猜谜，LLM host 自动判题，Game Progress）、House-Holding（ALFWorld/TextWorld 衍生的具身家居任务，SR）。
- **Web-grounded**：Web Shopping（改编自 WebShop，纯 prompting 而非训练好的策略网络，Reward）、Web Browsing（改编自 Mind2Web，Step SR）。

5/8 环境为首次提出，其余改编自已有数据集但重新设计为可交互多轮格式。

### 评测框架：Decoupled Server-Client 架构

核心贡献不是环境本身，而是一套通用评测工具链（Appendix A）：

- **三方解耦**：Task Server（任务控制器 + 若干 Task Worker）、Agent Server（模型服务，暴露 HTTP API）、Evaluation Client 各自独立部署，通过 HTTP 通信，摆脱"同机部署"限制。
- **Docker 隔离 Task Worker**：每类任务的复杂运行环境封装进 Docker 镜像，挂载代码路径即可复用；每个任务再细分为独立 Worker 进程，保证环境互不冲突。
- **max-flow 调度**：把"n 个 agent × m 个任务 × 待评样本数"建模为带权二部图网络流问题（源点→agent→task→汇点，[[2308.03688]] 用 Edmonds–Karp 实现 Ford–Fulkerson，复杂度 $O(|V||E|^2)$），周期性重跑算法把新增评测三元组分配给空闲 worker，从而支持多 agent、多任务同时协作评测。
- **可恢复评测**：中断后可续跑，不必重跑已完成样本。

### Prompt 与评分设计

- 采用最原始的 Chain-of-Thought（"Thought"+"Action"单轮输出），不引入 ensemble/reflection/search 等改进策略，greedy decoding（temperature=0）保证可复现。
- 对话历史超长时按 token 预算裁剪早期轮次，兼容 chat 模型与纯文本补全模型（text-davinci 系列）两种接口形态。
- **Overall Score 归一化**：每个任务的平均分先归一化到 1，再取该任务在全体模型上的"倒数均值"作为固定权重，跨任务加权平均得到 OA 分数，避免高分任务（如 Web Shopping）掩盖低分任务的区分度。

## 实验与结果

- 29 个模型（10 API-based 商用模型 + 19 个 ≤70B 的 OSS 模型）全量评测；gpt-4 (0613) 在 8 项里的 6 项拿到最高分，House-Holding 达到 78% SR，OA=4.01 排名第一（Table 3）。
- OSS 模型整体远落后于 API 模型（平均 OA 0.51 vs 2.32），≤70B 里最强的 codellama-34b 也只有 0.96，明显不及 gpt-3.5-turbo（2.32）。
- **失败模式分布（Table 4）**：Task Limit Exceeded（未在预算轮数内完成/陷入重复生成）是主导性失败原因，尤其在 Lateral Thinking Puzzles（82.5%）和 Knowledge Graph（67.9%）上占比极高，暴露长程推理与决策能力不足；Database/Digital Card Game 里 Invalid Format 占比高（分别 53.3%/38.5%），反映严格格式约束下的指令遵循问题；House-Holding/Web Browsing 里 Invalid Action 占比高，反映模型倾向生成超出预定义动作空间的动作。
- **代码训练影响是双刃剑**：对比 codellama 与 llama-2 系列发现代码调优在偏程序化任务（Web Shopping）上有优势，但在需要通用思维的任务（Digital Card Game、OS 中"与系统交互"而非"写 bash"的部分）上反而拖累表现。
- **对齐数据质量的证据**：同底座的 vicuna-13b（ShareGPT/GPT-4 数据对齐）显著优于 llama-2-13b（原生对齐），甚至逼近参数量大 3 倍的 codellama-34b。

## 局限与疑点

- **论文完全未披露评测框架本身的工程数字**：Docker 隔离开销、Worker 并发密度、冷启动时间、跨设备部署的网络延迟等——这是一篇"评测方法论 + 排行榜"论文，不是系统性能论文，我们最关心的沙箱工程指标在这里查不到。
- 隔离粒度仍是任务级 Docker 容器，静态配置，不涉及像后来 [[agent-execution-sandbox]] 里讨论的动态权限收敛问题，本质上是 2023 年早期实践，工程复杂度和安全模型都远低于后续系统（Harbor ASP、OpenEnv Cloud Sandbox Providers）。
- 仅用最原始 CoT + greedy decoding 评测，不含 function calling、tool use 框架、reflection 等后续agent scaffold 常用技术，results 与今天的 agent 能力对照参考价值有限（论文本身也在 v3 修订里补测了 claude-3/glm-4 等更新模型，但框架未变）。
- Overall Score 的"倒数均值权重"依赖当前评测的模型池，模型池变化会导致权重、进而导致历史分数不可比，作者自己承认这套打分法是为了解决当前问题而设计，未必是长期稳定的评测标准。

## 对我们的启发

1. **Docker-per-task-worker + Server-Client 解耦，是"沙箱执行环境标准化"这条演进线里很早期的一环**：相比 [[agent-execution-sandbox]] 里盘点的 nono/E2B/Anthropic sandbox-runtime、以及 [[harbor]] 的 ASP 协议、OpenEnv 的 ContainerProvider，AgentBench 2023 年的方案只做到"任务级 Docker 隔离 + HTTP 解耦部署"，没有细粒度权限收敛、没有 suspend/resume 等生命周期管理、没有安全不变量清单。值得作为"这条技术线从哪里起步"的历史锚点，对比后续系统具体补了什么能力。
2. **max-flow 动态配对调度是一个可复用的通用算法模式**：当我们需要在评测/训练场景里把"多种 agent（不同模型/不同 scaffold）"和"多种任务/环境 worker 池"做多对多动态匹配、并希望随着 worker 空闲/完成持续重新分配时，这个网络流建模（agent/task 作为二部图两侧节点、worker 数量作为边容量）是一个成熟且复杂度可控（$O(|V||E|^2)$）的调度算法参照，可以评估是否比我们当前简单轮询/队列式调度更高效。
3. **"评测框架论文不等于系统工程论文"是一个通用的检索陷阱**：AgentBench 作为 LLM-as-Agent 评测的奠基性工作被大量后续论文引用（[[agentic-rl-environments]] Table 10 就把它列为"通用环境"代表），但它本身不含任何我们关心的隔离开销、并发密度、成本数字——查文献时看到"AgentBench"这个高频引用名字，不能默认它包含系统性能数据，需要单独找复现/对比实验的来源。

可执行的 follow-up：
- 对比 AgentBench 的 Docker-per-task 隔离方案与 [[harbor]] ASP / OpenEnv ContainerProvider 在能力边界上的具体差异（是否支持 suspend/resume、动态权限、安全不变量），补进 [[agent-execution-sandbox]] 的时间线视角。
- 核实同期 InterCode（论文中提到的并行工作）是否也值得单独精读，其 Bash/SQL 交互框架与 AgentBench 的 OS/DB 环境设计差异。
- 评估 max-flow agent-task 调度算法能否直接复用到我们平台的批量评测/训练 rollout 调度场景，估算在我们规模下（agent 数、环境 worker 数）的调度开销。
