# R2E-Gym: Procedural Environments and Hybrid Verifiers for Scaling Open-Weights SWE Agents

> 程序化合成（而非人工标注）把 SWE 可执行训练环境从 [[swe-gym]] 的 2,438 个扩到 8,135 个，并用"执行型 + 无执行型"混合验证器把推理时扩展上限从单轴饱和的 ~43% 拉到 51%。

## 元信息

UC Berkeley / Australian National University · arXiv 2025-04-09 · [arXiv](https://arxiv.org/abs/2504.07164) · [项目页](https://r2e-gym.github.io)
对比基线：[[swe-gym]]（同规模对标，同为 Qwen2.5-Coder 系列模型）；同期/后续工作 [[swe-smith]] 给出更大规模的三方对标数字。

## 要解决的问题

[[swe-gym]] 证明了"真实仓库 + 可执行环境 + 拒绝采样"能训出有效的 SWE agent，但其环境构造几乎全靠人工（200 人工小时/2,438 实例），且问题陈述依赖人工编写的 GitHub issue，规模天花板明显。R2E-Gym 要解决两个问题：（1）能否把环境构造和问题陈述生成都自动化，从而把规模再扩大一个数量级；（2）SWE-Gym 的 ORM 验证器 Best@16（32.0%）与 Pass@16 上限（42.8%）之间有 10.8pp 差距，单一验证器是否已经到顶，能否用更好的验证器设计把推理时扩展的天花板进一步推高。

## 方法

**SweGen：程序化环境与任务合成流水线**

- **仓库与提交筛选**：用 SEART GitHub 搜索定位高提交量 Python 仓库，再用规则 + LLM 启发式过滤器筛选提交，限定单提交改动 ≤5 个非测试文件、≤100 行编辑、补丁长度 ≤2000 字符，控制任务复杂度在可控范围。
- **环境构建**（Appendix A）：Docker 化的"搜索型依赖解析"——从 requirements.txt / setup.py 提取依赖，迭代探测版本冲突，用半自动流程反复尝试候选依赖配置直到构建成功。论文明确承认这一步"semi-manual and challenging to scale"，是全文唯一仍主要依赖人工的环节。
- **Fail-to-Pass 测试收集**：优先复用仓库里"修复前失败、修复后通过"的已有测试；对没有配套测试的提交，额外自动生成缺失的 F2P 测试。这一执行式准入门槛与 [[swe-gym]]「gold patch 通过测试数 > 原代码」、[[swe-smith]]「候选 patch 破坏 ≥1 个原通过测试」是同一族确定性检查的第三个变体，用在"任务本身是否有效"这一步。
- **反向翻译（backtranslation）生成问题陈述**（核心创新）：观察到人写的 GitHub issue 通常本身就包含失败测试和报错堆栈，于是反过来把 F2P 测试的执行输出／报错信息当作 prompt 的一部分，让 LLM 反推生成问题陈述，从而彻底摆脱"必须有人工编写的 issue/PR 描述"这一数据源限制。消融显示合成问题陈述与真实 PR 描述训练效果几乎等价（27.8% vs 28.0%，400 条轨迹控制变量），且这一步让可用数据源扩大约 2.5 倍（不再局限于恰好配有高质量 issue 的提交）。

**混合验证器（Hybrid Verifier）**

- **执行型验证器（Execution-Based, EB）**：训练一个 32B"测试代理"，为每个问题生成 10 个额外的多样化边界测试，与官方 F2P/P2P 测试一起跑；候选 patch 里在这些回归测试上得分最高的记为通过，其余记 0 分（Eq. 1）。局限（Figure 5）：多数问题里 <20% 的生成测试真正具有区分度，即"测试虽然能跑但分不出候选好坏"。
- **无执行型验证器（Execution-Free, EF）**：微调 14B 模型直接读 (问题, agent 轨迹, 补丁)，输出单 token YES/NO，用其归一化 log 概率当分数——与 [[swe-gym]] 的 ORM 思路一致。关键发现：这个验证器严重依赖 agent 的"思维轨迹"而非补丁本身——若只喂最终 patch（去掉轨迹），Best@26 从 42.8% 掉到 37.6%；注意力可视化（Figure 7b）证实模型把最高权重放在思维部分而非代码 diff 上，提示 EF 验证器可能在用"agent 听起来自信"这种代理信号，而非真正核验补丁正确性。
- **混合公式（Eq. 2）**：$s_k^H = \mathrm{Top}_n(s_k^{EF}) + s_k^{EB}$，其中 $\mathrm{Top}_n$ 只保留 EF 分数排名前 n 的候选（其余记 $-\infty$），目的是抑制"毒性测试"（toxic tests：通过错误补丁但让正确补丁失败的测试）对 EB 分数的污染——先用 EF 做一轮粗筛去掉明显不像样的候选，再用 EB 在小范围候选里精排。

**Agent 训练**：ReAct 框架 + 4 个工具（文件编辑、搜索、bash 执行、提交），用 Claude-3.5-Sonnet-v2 在 R2E-Gym-Subset（4,578 任务，2,048 个去重环境，与 SWE-Bench 仓库不重叠）上做拒绝采样，收集 3,321 条成功轨迹（每条 ≤40 步、≤32K token），SFT Qwen2.5-Coder 7B/14B/32B，LLaMA-Factory 全参数微调，2 epoch，batch=8，LR=1e-5，训练上下文截断到 20K token（论文明确写"due to computational constraints"，是复杂长任务的已知瓶颈）。测试代理同样用 Sonnet 监督采集 2,203 条轨迹，32B 模型 LoRA rank=64 微调（仅用于 EF 验证器路径）。

## 实验与结果

- **数据集规模对比**（Table 1）：SWE-Bench(train) 19,008 条（不可执行）；SWE-Gym Raw 66,894 条（不可执行）；SWE-Gym 2,438 条可执行；**R2E-Gym 全集 8,135 条可执行**；R2E-Gym-Subset（与 SWE-Bench 仓库无重叠）4,578 条。引言原文称"increasing the number of executable environments by over 33 times"——这一倍数是相对更早期工作（论文引用的 246 个可执行环境基线，而非 SWE-Gym 的 2,438）而言，相对 SWE-Gym 本身则是约 3.3 倍。
- **同规模/同基座直接对标 SWE-Gym**（Table 3，SWE-Bench Verified Pass@1，同为 Qwen2.5-Coder 系列）：7B 19.0%（SWE-Gym 10.6%，+8.4pp）、14B 26.8%（SWE-Gym 16.4%，+10.4pp）、**32B 34.4%（SWE-Gym 20.6%，+13.8pp）**。这组数字正是 wiki 里 [[agentic-rl-environments]]、[[gef-loop]] 已经引用的"环境规模化"量化链条的中间点（SWE-Gym 20.6% → R2E-Gym 34.4% → SWE-Smith 40.2%）。
- **混合验证器推理时扩展**（Table 4）：纯 EB 验证器饱和于约 43.7%，纯 EF 验证器饱和于约 42.8%，两者单独都遇到天花板；**混合验证器 Best@26 达到 51.0%**，是全文最高分，也是当时开源权重模型首次在 SWE-Bench Verified 上逼近/部分超过部分闭源系统（Claude-3.5-Sonnet 49.0%、o1+Agentless 49.2%；但仍显著落后 Claude-3.7-Sonnet Best@Any 70.3%）。
- **消融**（Figure 3、Figure 8）：去掉 agent 思维轨迹训练，32B 模型从 34.4% 降到 30.4%，说明轨迹（而非仅最终 patch）对 SFT 效果贡献显著；仅用 Agentless 式静态测试代理（不训练）得 48.8%，用训练出的 agentic 测试代理生成测试则达 51.0%，说明"用 agent 主动探索生成测试"优于固定流水线；加入 Top_n 过滤后 51.0%，不加则 49.8%，验证了"先用 EF 粗筛再用 EB 精排"确实比直接线性相加更好。
- **轨迹规模曲线**（Figure 3 左）：14B 模型在约 800 条轨迹处饱和，32B 模型到该规模仍在提升，与 [[swe-gym]]、[[swe-smith]] 观察到的"模型越大、越晚饱和"趋势一致。

## 局限与疑点

- **环境构建仍是半人工瓶颈**：论文自己承认 Docker 依赖解析"semi-manual and challenging to scale"，但未披露具体人工工时/CPU 小时数字（对比 [[swe-gym]] 给出的 200 人工小时+10,000 CPU 核心小时、[[swe-smith]] 给出的 128 仓库 $1,360+38 人工小时），这是三篇环境合成论文里成本透明度最低的一篇——我们无法据此估算"自建同类程序化合成流水线"的实际投入。
- **EF 验证器可能在学一个错误的代理信号**：严重依赖思维轨迹而非补丁本身（去掉轨迹掉 5.2pp），这提示单纯"无执行型 LLM 判分"类验证器有被"听起来自信的错误答案"欺骗的系统性风险，呼应 [[generator-verifier-asymmetry]] 里"验证器质量≠验证域是否易验证"的观察。
- **执行型验证器的区分度普遍偏低**：Figure 5 显示多数问题里 <20% 的生成测试有区分力，说明"让模型自己生成回归测试"这条路径本身产出效率不高，10 个测试里大部分是噪声。
- **毒性测试规模不明**：论文提到在约 10% 的问题子集上毒性测试出现率达 10%，但未做更细粒度的失败模式分析（比如毒性测试是否集中在特定仓库/任务类型）。
- **训练上下文截断到 20K token 是算力妥协**，论文明确写出这一限制，对需要长上下文推理的复杂任务是已知短板。

## 对我们的启发

1. **反向翻译（backtranslation）是"去人工标注瓶颈"的一个可迁移思路**：SweGen 用"F2P 测试的失败输出反推问题陈述"取代人工写 issue，这个模式不限于 SWE——只要某类任务的"验证失败信号"本身信息量足够大（报错堆栈、断言失败详情），就可能反过来合成任务描述。对我们平台而言，如果要批量合成 agent 训练任务（而不仅仅是跑现成 benchmark），这是一个值得复用的低成本数据增广手段。
2. **混合验证器的"EF 粗筛 + EB 精排"两阶段设计，是应对"执行验证准确但慢/贵、LLM 判分快但不准"这一矛盾的具体工程模式**：如果我们平台未来要给客户提供"验证器即服务"，两阶段过滤（先用便宜的启发式/模型判分砍掉明显候选，再用真实沙箱执行做终审）是一个成本与准确率之间可复用的折中方案，而不必在"全部执行"与"全部 LLM 判分"之间二选一。
3. **警惕 follow-up**：EF 验证器过度依赖 agent"思维轨迹"而非最终结果这一现象值得我们在设计任何"轨迹+结果"联合判分的验证器时提前防范——建议对验证器做输入消融测试（去掉思维只留最终产物），作为验证器上线前的标准检查项，避免部署一个实际上只在"读语气"而非"读正确性"的判分模型。
