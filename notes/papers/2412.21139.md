# Training Software Engineering Agents and Verifiers with SWE-Gym

> 首个可执行的 SWE agent 训练环境：2,438 个真实 GitHub issue + Docker 执行环境 + 单测，用 491 条轨迹微调就让 32B 模型解决率翻 3 倍多。

## 元信息

UC Berkeley / UIUC / CMU / Apple；arXiv 2412.21139，v1 2024-12-30，v2 2025-06-06（ICML 关键词）；[项目代码](https://github.com/SWE-Gym/SWE-Gym)。对比基线：[[swe-bench-pro]]、[[swe-bench-multilingual]] 之前的评测集 SWE-Bench（Jimenez et al. 2024）及其 train split、R2E（合成任务）。

## 要解决的问题

SWE agent 领域此前严重依赖 GPT-4/Claude 等闭源模型的 prompting 与人工设计的 specialized workflow，缺少可训练的环境：SWE-Bench 的 train split 只有 19,008 条"结果补丁"（git diff），没有可执行环境、没有单测反馈、没有中间动作序列，只能做模仿学习；R2E 任务是合成的，脱离真实场景；APPS/HumanEval 只是孤立函数级任务，不是仓库级。构造"可执行 + 可验证 + 真实"的 SWE 训练环境本身就很难：需要为历史某个 commit 时间点的仓库配好可运行的依赖环境，还要保证单测能真正区分对错。

## 方法

**环境构造流水线（[[swe-gym]]）**：
1. 用 SEART GitHub 搜索筛选仓库：2022-07 前创建、500+ star、300+ 行代码、500+ PR、100+ 贡献者 → 358 个 Python 仓库（比 SWE-Bench 覆盖的 "PyPI 下载量前 5k" 策略更宽，仓库集合特意与 SWE-Bench 的仓库不重叠以避免污染）。
2. 复用 SWE-Bench 的 instance 抽取脚本，从这 358 个仓库抽出 64,689 条任务（issue 描述 + 仓库快照 + 单测），称为 **SWE-Gym Raw**（无可执行环境）。
3. 从中选 11 个仓库半人工搭建可执行环境：先做版本号关联（按 pyproject.toml / git tag 等半自动化提取版本号，避免逐 issue 重复配环境），再手工配依赖（requirements.txt / CI 脚本 / 仓库文档），最后用 SWE-Bench 的执行式验证脚本确认「gold patch 通过的单测数 > 原始代码通过的单测数」，淘汰不满足的实例。
4. 得到 2,438 个验证通过的任务实例（**SWE-Gym**），并按 SWE-Bench Lite 的过滤流程（排除多文件编辑、描述不清、diff 过于复杂、只验证报错信息的任务）划出 230 个的 **SWE-Gym Lite**。

**Agent 训练（两种 scaffold 对照实验）**：
- **General-purpose prompting**（OpenHands CodeAct，ReAct 式长程规划）：用 gpt-4o / claude-3.5-sonnet 在 SWE-Gym 上采样，拒绝采样（rejection sampling fine-tuning，即 filtered behavior cloning）筛出 491 条成功轨迹（平均 19 轮 / ~19k tokens），微调 Qwen2.5-Coder-Instruct 7B/14B/32B。
- **Specialized workflow**（MoatlessTools，人工分阶段：定位→编辑→重排）：用当前策略自身在线采样做迭代拒绝采样式自我提升，两轮迭代。关键工程技巧是 **per-instance capping**（每个任务最多保留 cap 条成功轨迹，实验取 cap=2）：因为重复采样下任务成功率长尾分布，直接用全部成功轨迹训练会让数据集偏向"容易的任务"。

**验证器（Outcome-Supervised Reward Model, ORM）**：把 (问题描述, agent 轨迹, 当前 git diff) 拼成 prompt，微调模型输出 `<YES>`/`<NO>` 单 token，用 `<YES>`/`<NO>` 的归一化 log 概率作为标量奖励 $r=\exp(l_y)/(\exp(l_y)+\exp(l_n))$。训练数据混合 on-policy（微调后模型自采样成功轨迹）与 off-policy（gpt-4o/claude 采样成功轨迹），并对成功/失败样本配平。推理时对同一任务采样 k 条轨迹，用 ORM 打分选最优（Best@k），构成 [[generator-verifier-asymmetry]] 中"易验证域"下的一个完整训练时+推理时两用验证器实现。

## 实验与结果

- **环境构造成本（Table 1 & 正文）**：从 64,689 条 raw 任务里精选 11 个仓库人工配置，耗费约 **200 人工标注小时 + 10,000 CPU 核心小时**，最终产出 2,438 个验证通过实例；公开发布的预构建 Docker 镜像共 **6 TB**（约 2.5GB/实例）。
- **SWE-Gym vs SWE-Bench 任务难度（Table 2）**：SWE-Gym 平均 gold patch 编辑 69.8 行 / 2.5 个文件 / 4.1 个函数，明显高于 SWE-Bench test split 的 32.8 行 / 1.7 文件 / 3.0 函数；模型在 SWE-Gym 上的解决率也持续低于 SWE-Bench，作者认为部分原因是模型/scaffold 对 SWE-Bench 过拟合，部分是 SWE-Gym 收录了 pandas、MONAI 这类更复杂的仓库。仓库分布长尾：pandas 占近 1/3 任务，bokeh 仅占约 1%。
- **Agent 微调效果（Table 3，OpenHands scaffold）**：仅用 491 条轨迹微调 Qwen2.5-Coder-32B，SWE-Bench Lite 解决率 3.0%→15.3%（+12.3pp），Verified 7.0%→20.6%（+13.6pp）；同时"卡死循环"（连续 3 次重复同一动作）比例下降 4.6–18.6pp，"空补丁"比例也下降，说明微调后模型更敢于真正编辑代码而不是原地打转。
- **Specialized workflow 自我提升（Table 4，MoatlessTools）**：per-instance capping=2 时，7B 模型两轮迭代后 7.0%→9.0%→10.0%；32B 模型 19.0%→19.7%，第二轮几乎无增益（作者归因于该 scaffold 动作空间受限 + 拒绝采样方法本身的上限）。
- **推理时扩展（Fig. 3/4，§5.1）**：OpenHands + 32B 微调 agent + 32B ORM 在 SWE-Bench Verified 上，Pass@k 从 20.6%（k=1）升到 37.8%（k=8）、42.8%（k=16）；Best@k（ORM 选优）从 20.6% 到 29.8%（k=8）、**32.0%（k=16，全文最高分）**；Best@k 与 Pass@k 之间的差距说明 ORM 还有明显提升空间。MoatlessTools 上 32B 验证器把 7B/32B agent 的 SWE-Bench Lite 解决率分别从 10%/19.7% 提到 13.3%/26.0%，7B 验证器在 k=4 后就饱和，32B 验证器到 k=8 仍在提升——**验证器规模本身影响其 scaling 行为**。一个反直觉结果：ORM 用 LoRA 微调（29.8@8）比全参数微调（27.2@8）效果更好，作者猜测是正则化效应。
- **训练数据消融**：ORM 训练数据里 on-policy + off-policy 混合效果最好（27@8）；仅 on-policy 提升有限；仅 off-policy（Claude/GPT 轨迹）在约 22% 附近早早见顶——验证器训练同样受益于数据多样性。
- **训练时数据规模化（§5.2，Fig. 5）**：三种子采样方式（随机丢弃轨迹 / 按任务去重只留一条 / 按仓库顺序累加）在 SWE-Bench Verified 上都随数据量单调提升，491 条轨迹时仍未看到饱和迹象——作者判断当前瓶颈是"用于采样轨迹的算力预算"，而不是 SWE-Gym 本身的任务/仓库多样性。
- **自我提升失败案例**：用微调后的 32B 模型在线采样 6 条/任务（t=0.5）得到 868 条 on-policy 轨迹，与原 491 条 off-policy 轨迹混合再训练，SWE-Bench Lite 解决率反而从 15.3% 掉到 8.7%——简单拒绝采样式自我提升在这个 scaffold 上不 work，作者认为需要更强的策略优化算法（如 PPO）或更强的基座模型。

## 局限与疑点

- 作者自陈三点未来方向：① 环境多样性有限（仅 11 个仓库、Python 单语言、任务类型单一），需要自动化环境合成；② 自我提升的 RL 方法仍不成熟（拒绝采样在 OpenHands scaffold 上直接失败）；③ 完全没有 human-in-the-loop 协作场景，只测"独立完成任务"。
- 200 人工小时 + 10,000 CPU 核心小时只覆盖了 11/358 个候选仓库（2,438/64,689 个候选任务），人工配置环境的边际成本没有随规模下降的证据——这是"环境规模化"论点里最大的手工瓶颈，论文没有给出自动化这一步的方案（后续 R2E-Gym、SWE-Smith 等工作正是在补这一课，见 [[agentic-rl-environments]]）。
- 论文没有披露单实例的 Docker 镜像分发/加载耗时、并发跑多少个实例评测的具体资源开销，只提到用 OpenHands remote runtime 并行化评测——对我们判断"这套环境能不能直接搬进自己的调度系统"缺关键工程数字。
- Best@k 与 Pass@k 之间的差距（10.8pp @ k=16：42.8% vs 32.0%）说明当前 ORM 远未达到"完美验证器"，用它做 RL 训练的奖励信号可能引入系统性偏差，论文未评估这一点对策略优化的影响。
- 仓库分布长尾（pandas 近 1/3）可能让训练出的 agent 对特定代码风格/库过拟合，论文的"仓库规模化"实验（按仓库顺序累加）显示前 25% 数据（含完整仓库覆盖）表现相对更好，但未系统排除"任务量更大 vs 仓库更全"两个因素的混淆。

## 对我们的启发

- **环境构建成本可以直接拿来做预算参照**：2,438 个可执行 SWE 环境 = 200 人工小时 + 10,000 CPU 核心小时 + 6TB 镜像，折算约 4.1 CPU 核心小时/实例 + 2.5GB 镜像/实例。这给我们评估"要不要自建一套 SWE 训练沙箱环境库"提供了一个真实的成本量级锚点，可以据此估算把类似规模的内部代码库/任务库跑通所需的算力和存储预算。
- **6TB Docker 镜像的分发与存储是现实的工程问题**：论文完全没有讨论镜像去重、分层复用、按需拉取，这正是我们平台的强项（[[sandbox-image-distribution]]、[[on-demand-image-loading]]）——如果要支撑类似规模的 SWE 训练环境，镜像分层/按需加载几乎是刚需，而不是这篇论文视角下的"锦上添花"。
- **质量防作弊的核心手段很朴素但有效**：用"gold patch 通过的单测数必须严格多于原始代码通过的单测数"作为唯一准入门槛，配合仓库集合与评测基准（SWE-Bench）不重叠来防污染。这是一个成本很低、但对训练数据质量有硬保证的过滤规则，值得在我们自己构造可验证奖励环境时优先复用，而不是一开始就上更复杂的 LLM-as-judge。
- **per-instance capping 是防止"训练数据被简单任务淹没"的低成本手段**：在我们自己做数据规模化构造时，遇到长尾成功率分布（多数任务要么很容易破解要么几乎不可能）是大概率会碰到的问题，capping 是一个几乎零额外成本、直接在采样后处理阶段就能上的对策。
- **验证器（ORM）训练本身也需要 on-policy + off-policy 混合数据**，纯粹用强模型（GPT/Claude）蒸馏的轨迹训出来的验证器会早早见顶——如果我们要给内部代码 agent 配一个奖励模型/验证器，不能只用外部强模型的轨迹当训练集，还需要让当前策略自己产出失败样本。
- Follow-up 建议（可转 issue）：
  1. 深挖 SWE-Gym 之后的 R2E-Gym / SWE-Smith 具体自动化环境合成流水线，评估能否把"半人工配依赖 + 执行式验证"这一步自动化，对比 200 人工小时/2,438 实例这个基线能压缩多少。
  2. 评估我们现有的 [[repolaunch]] 沙箱镜像构建能力是否能覆盖 SWE-Gym 这类"历史 commit 时间点 + 精确依赖版本"的仓库快照场景，量化冷启动和镜像体积。
  3. 复现 ORM 训练数据消融（on-policy vs off-policy 混合比例）在我们自己的代码 agent 上是否成立，作为内部验证器训练的最小可行方案参考。
