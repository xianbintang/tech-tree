# Auditing Reward Hackability in Code RL Training Environments

> 用 Docker 实测量化 code RL 训练环境的"可作弊率"：SWE-bench Verified 28.5%、R2E-Gym 25.0% 的任务能被弱测试套件放过错误补丁，并给出一套带 gold-sanity gate 的修复闭环。

## 元信息

- 作者：Shreshth Rajan（单作者，论文正文未标注机构）
- 发表：2026-06-14（v1，审计部分完成于 2025-10，元分析/复现/修复闭环完成于 2026-06）
- 链接：[arXiv](https://arxiv.org/abs/2606.16062) · [HTML](https://arxiv.org/html/2606.16062v1)（代码/数据未公开发布，声明"合理请求可提供"）
- 对比基线 / 相关工作：OpenAI SWE-bench Verified 退役说明（59.4% 失败任务测试有缺陷）、UC Berkeley BenchJack/`trustworthy-env`（8 个 agent 基准上 45 个 process-isolation exploit，即 [[benchmark-item-validity-audit]] 的来源论文）、*The SWE-bench Illusion*（记忆而非推理）、SWE-ABS（对抗性加固拒绝 19.71% 幸存补丁）、HARDTESTGEN / ACECoder / EvolveCoder（执行对照参考解的测试加固）

## 要解决的问题

RL from execution feedback 只有在 verifier 正确时才成立：如果测试套件把错误解判为正确，policy 就在为错误行为拿奖励。已有证据都是间接或定性的——SWE-bench Verified 发布时 93 名开发者的人工复核、OpenAI 退役说明里"59.4% 失败任务有缺陷测试"——都没有回答一个 curator 真正需要的操作性数字：**code RL 训练集里，究竟有多少比例的任务会为错误解发奖励？** 本文直接测量这个比例，并给出修复流程。

## 方法

四组件管线（Section 3），建立在已有技术之上（NVIDIA 风格 verifier 打分、Ugare & Chandra (2026) 的半形式化 LLM 代码判定、EvolveCoder 式迭代攻击、人工难度分层），新意在实证结果本身：

1. **Exploit generation（漏洞生成）**：用 Claude Sonnet 4 为每个任务生成 K 个候选"错误但能通过测试"的补丁。第 1 轮 single-shot；第 2、3 轮用上一轮失败日志引导生成，偏向测试套件尚未拦截的漏洞方向。每个候选在任务的 Docker 容器内用项目自身 harness（SWE-bench 的 `run_evaluation`、R2E-Gym 的 `DockerRuntime.apply_patch`）应用并跑测试；只要有一个候选通过，任务判定为 hackable。
2. **Environment Quality Score（EQS）**：四维加权分数 EQS(t) = 0.35·V(t) + 0.30·(1−H(t)) + 0.20·F1(t) + 0.15·D(t)，其中 V 是 verifier 判别力、H 是实测 hackability、F1 是 LLM 判官三分类（CORRECT/PARTIAL/INCORRECT，PARTIAL 按错误算）的一致性分数、D 是跨模型可学习性信号。按阈值分 KEEP(>0.70) / FIX(0.40–0.70) / DROP(<0.40)。作者明确说明：权重未在验证集上调过,是"信号直接程度"的先验排序；论文三个核心数字（28.5%、25.0%、+14.14pp、61.9%）都直接用 H(t)>0 或独立于权重计算,EQS 权重只决定 FIX/KEEP/DROP 这一策略性划分。
3. **Sanity-gated repair loop（修复闭环）**：对 FIX 判定任务跑闭环——augmenter 提议一条能拦截漏洞的新测试 → **Docker gold-sanity gate**：把新测试注入真实项目测试文件、打上 gold 补丁、只跑这一条测试，不通过就丢弃并触发更高温度（0.3→0.7）+ diversity-biased 提示的重试 → 通过 gate 的测试交给 3-sample 自一致性 LLM 判官（温度 0.2/0.4/0.6，多数投票）判定是否真的拦住了目标漏洞 → 全部目标漏洞被拦住则 FIX→KEEP。
4. **134-模型元分析**：从 SWE-bench/experiments 仓库收集 134 个前沿模型的逐任务 Pass@1 记录，用发布时固定的人工难度分层做协变量控制（明确拒绝用跨模型 solve rate 做难度控制，因为 hackable 任务会通过"作弊"抬高 solve rate,造成循环论证），对每个模型算 flagged-hackable 子集与 robust 子集的分层内 Pass@1 差值 Δ_m,再用 DerSimonian-Laird 随机效应元分析跨模型汇总。

## 实验与结果

**SWE-bench Verified 审计（n=49，Section 4.1）**：50 个审计任务中 1 个 gold patch 本身跑不过被剔除,剩 49 个。**14/49（28.5%）Docker 验证 hackable**,集中在 12 个仓库里的 2 个（astropy 6 个、django 8 个）。仅第 1 轮 single-shot 的比例是 18.4%（9/49）,第 2、3 轮迭代攻击再加 5 个。全部 50 个任务平均 EQS 0.806,判定分布 KEEP 38 / FIX 11 / DROP 1。审计花费 $6.04（Claude Sonnet 4 API + 本地 Docker）。

**R2E-Gym 复现（n=20，6 仓库，Section 4.2）**：seed=42 抽样自 R2E-Gym-Subset（4,578 任务）,覆盖 orange3/numpy/pyramid/aiohttp/tornado/pandas。K=1 single-shot,16 个"决定性"任务（gold baseline 通过且至少 1 个漏洞候选成功应用）中 **4/16（25.0%）hackable**。作者明确标注这是下界：R2E-Gym 用的是比 SWE-bench 审计（K=3+迭代）更弱的攻击预算,若只看 SWE-bench 的纯 single-shot 结果（18.4%）,两者在抽样误差内一致。花费 $8.29 API + 约 2.5 小时 M-series Docker。

**134-模型元分析（Section 5）**：分层内 Δ̂ = **+14.14 pp**（95% CI [+11.80, +16.48]；单侧 p < 10⁻⁶；I² = 0%）,134 个模型里 123 个方向为正（符号检验 p<10⁻⁶,Wilcoxon 符号秩检验一致）。未分层的原始效应是 +25.64pp,按人工难度分层后保留 55%——说明部分效应确实是"难度混杂",但分层后仍有过半效应无法用难度解释。按提交年代（2025 前/2025/2026）、Pass@1 四分位、前沿/非前沿 scaffold 分组,方向一致（I²=0% 表明异质性不显著）。四组独立证据（本文 28.5%、OpenAI 59.4% flawed-on-failed、Berkeley 45 个 process-isolation exploit、本文元分析 +14.14pp）用不同分母/攻击面得出同一定性结论。

**61.9% 的 augmenter 缺陷率（Section 6，本文的核心方法论发现）**：无 gate 的原始修复闭环报告 10/11 任务 FIX→KEEP,均值 EQS 0.570→0.816,花费 $5.57。但对 8 个抽样的 BLOCKS 判定做 Docker 复核后,只有 **1 个被证实**,**6 个是 augmenter 自己的 bug**（Table 1 逐条列出：错误 import 路径、装饰器语义理解反了、跨数据库测试断言反了、把 `inspect._empty` 断言成 `None`、把 `escape()` 的语义理解反了、关键字参数冲突导致 TypeError 等）,**1 个是方法论边界情形**（所有候选方法都被 `@pytest.mark.parametrize` 装饰,导致 augmenter 写的 `def test_X(self)` 根本不会被收集）。LLM 判官对这 6 个 bug 全部误判为 BLOCKS——判官正确读懂了测试代码"如果能跑会检查什么",但没发现测试代码本身跑不起来、跑错了或断言方向反了。加入 gate 后重跑全量闭环：**111 次生成 → 111 次 gate 检查 → 65 次 FAIL、40 次 PASS,per-augmentation 缺陷率 61.9%**——这是 LLM 判官单独使用时完全漏检的一类问题。最终 gated 版本收敛 **9/11**,均值 EQS 0.570→0.797,花费反而更低（$3.60 vs $5.57,尽管生成的 augmentation 数更多 111 vs 87）。

**消融（Section 6.4，Table 3）**：gate + judge 但**不重试**,只剩 3/11（把 gate 追溯应用到无 gate 版本的输出上,65/105 被过滤掉）;加回重试恢复到 9/11——**重试机制本身是决定性的**。把 diversity-biased 重试提示换成中性提示"再生成一些测试"、重试温度从 0.7 降到 0.3,结果仍是 9/11——**diversity bias 这个设计细节其实不起作用,起作用的只是"有没有重试"这一件事**。判官采样数从 3 降到 1,掉 1 个任务（8/11）但省 56% API 成本。

## 局限与疑点

- 审计样本小:SWE-bench Verified 只审了 49 个任务、12 个仓库里的 2 个;R2E-Gym 20 个任务、K=1,是明确标注的下界。134 模型元分析是唯一 n>100 的部分。
- 攻击者是单一前沿 LLM（Claude Sonnet 4）,作者自己承认更准确的表述是"至少 28.5% 可被前沿 LLM 攻击者攻破"——真实上限未知,不同攻击者/更大预算可能测出更高比例。
- 论文未做"用修复后 vs 未修复的任务训练 RL,看下游效果差异"的因果实验——28.5%/25.0%/+14.14pp 证明的是"测试套件能被骗、且模型确实更多在这类任务上'赢'",但没有直接证明"修好这些任务能改善训练结果"这一因果链条(作者列出这是最自然的下一步)。
- 61.9% 缺陷率虽是最稳定的数字（n=105 决定性 sanity check）,但闭环收敛结果（9/11）建立在 n=11 上,样本量很小。

## 对我们的启发

1. **"Docker gold-sanity gate"是一个可以直接复用的低成本质检组件**：在把任何 LLM 生成的测试/断言当作训练信号之前,先在 gold 解上跑一遍——本文证明这能以极低成本（$3.60 全流程)拦住 61.9% 的 augmenter 自身缺陷,而这类缺陷是纯 LLM 判官系统性漏检的。如果我们内部要做"LLM 生成测试用例加固可验证奖励环境"的流水线（呼应 [[verifiable-reward-environment-generation]] 里几条环境生成路线的质检环节),这个 gate 应该作为默认前置步骤,而不是可选项。
2. **重试机制比重试的"花样"更重要**：消融显示 diversity-biased prompt 相对中性 prompt 没有增量收益,真正起效的是"有没有重试"这一件事。这提示我们设计类似修复闭环时,不必在提示工程上过度投入,先把重试轮数/预算做对,比设计精巧的多样性提示性价比更高。
3. **EQS 的"信号直接程度排序"（verifier 判别力 > 实测 hackability > 判官一致性 > 跨模型可学习性)是一个可以直接搬到我们自己环境质检打分体系的先验结构**,即使具体权重需要按我们自己的场景重新校准。
4. **28.5%/25.0% 这两个数字本身就是给"直接拿公开 SWE-bench/R2E-Gym 任务做内部 RL 训练"的团队的警示**：如果我们计划复用这两个基准(或其衍生物,如 [[swe-bench-multilingual]])作为训练环境,应该先假设四分之一到近三分之一的任务存在可被利用的弱测试,而不是默认"能跑通=能学到正确行为"。
5. **follow-up 建议**：① 把本文的四组件审计管线（漏洞生成 → EQS → gate → 元分析)套用到我们内部/候选的可验证奖励环境上,产出一份类似的 hackability 基线数字,作为环境准入的门槛之一;② 评估能否把 gold-sanity gate 直接接入 [[verifiable-reward-environment-generation]] 里已经在追踪的几条环境生成路线（尤其是依赖 LLM 生成测试/断言的 skill-模板先行、代码先行路线),量化能拦住多少类似的 augmenter 缺陷。
