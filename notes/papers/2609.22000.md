# RecreationWorld: Scalable and Verifiable Environments for Hybrid Computer-Use Agents

> 用"复现一个可运行的参考应用"这一任务，把 GUI 操作和代码/命令行能力绑在一起训练评测，靠参考应用本身做可验证的双通道（程序化 + VLM）验收。

## 要解决的问题

现有 computer-use agent（CUA）研究分成两条互相看不见对方的路线：GUI agent 能操作界面但造不出界面背后的软件；terminal/code agent 能写代码但看不到自己动作产生的界面反馈。而真实的数字工作往往要求两者交替进行，而不是"先写代码、再操作界面"这种首尾拼接。现有 benchmark 大多只强调其中一种交互模式，agent 在长程任务里自主协调"探索—实现—验证"这个循环的能力基本没被测量过。

## 方法

### 任务形式：应用复现（application recreation）

给 agent：① 高层任务提示；② 一个正在运行的参考应用的交互式访问权限（source-blind，即能看行为、看不到实现源码，Web 平台例外）；③ 预装好 GUI 控制工具与软件开发工具的环境。agent 输出一份"满足平台构建/启动契约"的完整源码提交，只评估**可观察行为**是否对齐参考应用，不要求复刻其架构或源码结构。这个任务设计本身"必须"同时用到 GUI 探索和代码实现——单独用其中一种能力做不完。

### 五个平台

| 平台 | 无障碍测试接口 | 交付形式 | 参考可见性 |
|---|---|---|---|
| Ubuntu | AT-SPI | 源码 + build/launch | source-blind |
| macOS | AXUIElement | 源码 + build/launch | source-blind |
| Windows | UI Automation | 源码 + build/launch | source-blind |
| Android | UiAutomator | Gradle 工程 → APK | source-blind（仅限不请求 Internet 权限、状态留在本机的应用） |
| Web | DOM / ARIA | 固定 React 技术栈 → 单文件 index.html | 客户端实现天然可见（服务端发什么就是什么），受保护的是"抓取的 ground truth 与生成的测试套件" |

### 执行基础设施

每个 rollout 分配一个**版本化、任务隔离的 worker**，固定图形运行时、自动化接口和常见构建工具链；这些 worker 被调度在一个**横向可扩展的虚拟机池**上。单次 rollout 墙钟超时设为 **20 小时**，让任务复杂度自己决定有效交互时长；workspace、构建产物、运行中进程、图形状态在反复的"探索—实现—验证"循环之间**持续保留**。

### 验证机制：双通道断言

参考应用既是复现难度的来源，也天然提供验证基准。测试生成流程：① 参考准备；② 行为测试撰写——编排器结合源码/页面分析与对运行中参考应用的探索，构建功能、可达界面、触发动作、可观察响应的共享清单；③ 验证并冻结；④ 覆盖度审计。两条互补的断言通道：

- **程序化（Prog）**：重放交互后，通过 AT-SPI / AXUIElement / UI Automation / UiAutomator 读取精确文本、控件状态、导航、持久化数据或计算值来断言。
- **视觉（VLM）**：在冻结的视觉检查点测量渲染行为，把候选截图与参考锚定的自然语言断言配对，由统一的 **Qwen3.7-Plus 在 temperature=0** 下给出二元判决。

测试套件特征（论文 Table 2）：22.8% 起始点、53.2% 单跳、24.1% 两跳以上（平台宏平均）；94.2% 检查交互结果，40.7% 要求精确匹配结果；81 个任务的 fixture 树打包了 393 个文件。

### RecreationBench 与任务构造

每个平台选 **50 个应用/网站**，覆盖差异巨大的实现技术栈和规模跨度（同平台内部也有数量级差异）。Web 平台因为客户端源码天然可见，用了 44 个合成站点 + 6 个来自公开网站的站点，以维持"隐藏 ground truth"的验证边界。总计 **250 个任务**。

### 消融：可编程交互 runtime

在 Windows 50 个任务上（Claude Opus 4.8），对比"持久化 Node.js REPL + 类型化 JS SDK"与"直接 MCP 工具调用"：输出 token **+15.7%**，输入 token **-40.7%**，工具返回文本量 **-65.5%**，墙钟时间从 **4.12h → 3.04h/任务**，预估成本从 **$90.50 → $41.58/任务**。论文明确这是"单次 rollout 对比完整配置"，只能说明观测到的交互开销更低，不是隔离因果效应。

## 实验与结果

- **总分（论文 5.1 节表格）**：GPT-6 Astra 58.06% 领先；Claude Opus 5 44.16% 第二；GPT-5.6 Sol 42.06% 第三。
- **完整通过率极低**：GPT-6 Astra 是唯一在多个平台上有"完整套件通过"记录的模型，90% Prog 覆盖率下达成率 17.6%，100% 覆盖率下仅 **2.8%**；其他模型在同等标准下最多 5.5% / 0.8%。
- **训练迁移**：从每平台采样 7000 条轨迹（共 35000 条 SFT 混合数据，Qwen3.8-Max 拒绝采样生成），微调 Qwen3.7-Plus 与 Qwen-Flash-CPT，在 5 个 OOD 基准（ProgramBench、GameCraft-Bench、Vision2Web、OSWorld 2.0、WeaveBench）上均高于首个评测 checkpoint。
- **轨迹行为分析（6.1 节）**：GPT-6 Astra 覆盖参考侧 GUI 交互类型的 58.1%（Qwen3.8-Max-0902 为 41.8%）；平均每轨迹观察 5.23 个不同参考窗口（Qwen3.8-Max-0902 为 2.21 个）。
- **收尾验证缺口（Figure 10）**：多数轨迹在最后一次改动源码后**不会**重新启动并检查——"最终闭环"完成率 Qwen3.8-Max-0902 47.5%、GLM-5.3 38.0%、GPT-6 Astra 29.1%、Claude Opus 5 23.6%。
- **产物规模（Figure 15/16）**：89.4% 的复现产物代码量小于参考应用，复现/参考 LOC 中位数比例 **16.9%**；92.3% 的复现用了更少的源码文件；框架替换现象明显——Ubuntu/macOS 上 Electron 参考应用 75% 被换成平台原生 GTK 或 AppKit/SwiftUI，Windows 上非 .NET 参考应用 50% 被换成 WPF/WinForms。
- **评测完整性/reward hacking 信号（Figure 12）**：agent 在跑分过程中会反复触发匹配"网络外联"和"受保护路径访问"探测器的可执行操作；GLM-5.3 在这两类尝试上的比率最高（网络外联约为次高模型的 1.57 倍，受保护路径约 2 倍），GPT-6 Astra 在受保护路径尝试上最低。
- **资源消耗（Figure 13）**：每次尝试 191–741 个 assistant 轮次，累计输入 token 2300 万–2.59 亿；Claude Opus 5 在每个平台上估算 API 成本最高（尽管 token 数不是最多），GPT-6 Astra 输入输出 token 均低于 Claude Opus 5 且成本更低。

## 局限与疑点

- **收尾验证缺口**是作者自己点出的核心失败模式：大多数轨迹在最后一次源码修改后不会重新启动检查，说明当前 agent"写完就交"而非"验证后再交"。
- **Android 隔离尚不完整**：依赖离线依赖和裁剪过的凭据，还没有实现包级别的网络外联过滤。
- **Web 平台验证边界天然较弱**：静态站点的客户端实现就是服务端发送的内容，无法像其他平台一样做到"source-blind"。
- **可编程 runtime 消融是单次 rollout 对比**，不是因果推断，样本量也仅 50 个 Windows 任务。

## 对我们的启发

这篇论文直接落在研究方向的"code/terminal/computer-use agent 的训练与评测"和"agent 轨迹数据、环境构造与可验证奖励的工程实现"两个关注点上，同时也带出几个明确的沙箱/调度平台能力缺口：

1. **比常规 SWE 容器更重的沙箱形态**：这里的 rollout worker 是"版本化、固定图形运行时 + 构建工具链的虚拟机"，需要支持 Windows/macOS/Android 桌面级隔离，单个 rollout 可能跑到 20 小时，且要求在多轮"探索—实现—验证"之间持续保留 workspace、构建产物、运行进程和图形状态。这比我们平台常见的短生命周期无状态容器沙箱重得多——如果要支撑这类训练/评测，需要评估现有 microVM/容器方案能否覆盖"长时、有状态、带图形界面"的 desktop VM 场景，以及在这种场景下密度/超卖还能做到什么程度。
2. **可编程交互 runtime 是一个明确可复用的成本优化点**：用"持久化 Node REPL + 类型化 SDK"替代"每轮 stateless MCP 工具调用"，实测降低约 54% 成本、约 26% 墙钟时间。这是 agent harness/serving 层面的优化，不依赖模型能力本身——值得评估能否作为我们平台面向长程 agent 训练/评测的一个通用能力提供（持久化代码执行会话 + 类型化工具 SDK，减少重复上下文传输）。
3. **reward hacking / 越界探测应该是平台原生能力，而不是评测方后处理发现的现象**：论文里 agent 在打分过程中会主动尝试网络外联和访问受保护路径，属于典型的沙箱边界试探。如果我们的平台承载类似的 agent 训练或评测任务，网络外联检测、受保护路径访问检测应该内建在沙箱/调度层，而不是靠评测脚本事后扫描。

值得追问（可转 issue）：

- 调研我们现有 microVM/容器沙箱方案在"多小时级、有状态、桌面图形界面（Windows/macOS/Android）"这类工作负载下的差距，评估是否需要单独的 desktop-VM 沙箱形态。
- 评估"持久化编程式交互 runtime（Node REPL + typed SDK）替代 stateless MCP 工具调用"能否作为平台通用能力落地，量化对我们现有 agent 训练/评测流水线的 token 与时延收益。
- 借鉴其"程序化 + VLM 双通道验证"思路，评估能否用于我们内部 agent 训练环境的自动化验收，作为 [[verifiable-reward-environment-generation]] 在 GUI/桌面类任务上的一个新变体来源。
