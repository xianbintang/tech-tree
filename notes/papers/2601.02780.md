# MiMo-V2-Flash Technical Report

> Xiaomi 的 309B/15B-active MoE，用混合滑窗注意力 + 轻量 MTP 做快推理，用三阶段 Multi-Teacher On-Policy Distillation（MOPD）把多个领域专精教师蒸馏进一个学生，并公开了一整套 agentic RL 基础设施（环境搭建流水线、Toolbox/Tool Manager、R3、Data Scheduler）。

## 元信息

机构：LLM-Core Xiaomi ｜ 发表：2026-01-08（v2）｜ arXiv：https://arxiv.org/abs/2601.02780 ｜ Code：https://github.com/XiaomiMiMo/MiMo-V2-Flash ｜ 对比基线：DeepSeek-V3.1/V3.2(-Exp)、Kimi-K2(-Thinking)、Gemini-3.0 Pro、Claude Sonnet 4.5、GPT-5-High。团队与 [[2505.07608]]（MiMo-7B，同一批作者 LLM-Core Xiaomi）一脉相承：预训练数据管线沿用 MiMo-7B 的路线，RL 基础设施里的 Data Scheduler 明确说是"扩展 Seamless Rollout Engine"（MiMo-7B 提出的那一套）。

## 要解决的问题

两个独立问题打包在一篇报告里：① 长上下文场景下全局注意力的二次复杂度既拖慢训练也拖慢推理，需要在不牺牲精度的前提下做稀疏化；② 后训练阶段的"多能力域联合优化"存在跷跷板效应（practicing 一项能力常常损害另一项）和学习效率问题（离线蒸馏数据集利用率低），团队认为传统的参数合并或串行训练都无法两全。

## 方法

### 架构：混合滑窗注意力 + 轻量 MTP

- 48 层 Transformer，39 层 Sliding Window Attention（SWA，窗口 128 token）+ 9 层 Global Attention（GA），5:1 交替，仅第一层用 GA+dense FFN 稳定早期表示学习；MoE 每层 256 专家、激活 8 个，无共享专家；总参数 309B，激活 15B。
- **可学习 attention sink bias**（沿用 gpt-oss 设计）是让激进滑窗架构不掉点的关键：给 softmax 分母加一个可学习标量 $sink$，让每个 head 可以选择"不怎么关注任何 token"。32B dense 模型上的消融显示：无 sink 的 128-窗口 SWA 比全局注意力基线在通用榜单上明显掉点，加上 sink 后不仅追平、在复杂推理榜单（AIME24/25、LiveCodeBench、GPQA-Diamond）上反而以 46.3 对 42.4 平均分超过全 GA 基线（Table 2/4）。作者给出的解释是更小窗口起到正则化作用、把长程依赖清晰地"甩给"GA 层处理，窗口开到 512 反而模糊了这层分工，长上下文场景下明显掉点（Table 3）。
- **MTP 的双重定位**：不只是训练期的辅助目标（提升质量），更被当作生产环境的原生投机解码草稿模型——MTP block 用 dense FFN（非 MoE）+ SWA（非 GA），单层仅 0.33B 参数，足够轻量不会自己成为新瓶颈。3 层 MTP 在低熵任务（WebDev）上平均接受长度达 3.6，高熵任务（MMLU-Pro）更短，两者由 next-token cross-entropy 精确拟合（$R^2=0.995$）；16K 输入/1K 输出下 3 层 MTP 带来 1.82×–2.70× 解码加速，加速比随 batch size 和接受长度非线性变化，需要按硬件 roofline 调参（Table 10）。

### 后训练：MOPD 三阶段范式

1. **SFT**：建立指令遵循基础；作者发现 MoE SFT 的关键稳定性指标是 **num-zeros**（零梯度参数数量）——它上升说明专家负载失衡恶化，下降说明过拟合，需要靠 expert bias 更新率和 AdamW $\epsilon$ 联合调参来维稳，直接影响后续 RL 阶段能否收敛。
2. **领域专精教师训练**：对 agentic（搜索、代码、通用工具使用）和非 agentic（数学、通用推理、安全对齐）任务分别独立跑 RL/SFT，训出多个各自领域最强的教师。
3. **MOPD（多教师 on-policy 蒸馏）**：不做参数合并也不生成离线蒸馏数据集，而是把多教师知识整合建模成一个 on-policy RL 过程——学生按自己当前策略采样，教师对同一轨迹逐 token 打 reverse-KL 形式的奖励（公式 5–6），再套用 training-inference importance sampling 做截断修正（丢弃比值超出 $[\epsilon_{low},\epsilon_{high}]$ 的 token，公式 7–8），并可以把这个 MOPD advantage 直接和 [[grpo]] 风格的 ORM outcome advantage 相加（公式 9，$\hat{A}=\text{MOPD advantage}+\alpha\hat{A}_{ORM}$）。教师可以是 RL 模型、SFT 模型，甚至学生自己，解耦设计让新教师接入不需要重构整个流水线。详见 [[on-policy-distillation]]——那一页已经收录了另一篇论文（[[2609.23377]]）用"标签路由 + ReLU 门控奖励外推"实现的同名 MOPD，与本文的"reverse-KL + importance-sampling 截断"是两套不同的技术方案，见该页「争议与矛盾」。
   - 效果（Table 7）：12 个基准里 9 个蒸馏后超过各自最强教师（如 AIME 2025 从教师 93.9 提到 94.1、Arena-Hard Hard Prompt 从 50.0 提到 54.1），3 个基准（GPQA-Diamond、Arena-Hard Creative Writing、SWE-Bench Verified、BrowseComp）出现小幅下降，其中 BrowseComp 掉了 6.3 分最明显——作者没有解释这几项下降的原因。

### Agentic RL 训练：环境规模化 + 三个基础设施组件

- **Code Agent**（[[agentic-rl-environments]]）：超过 100,000 个源自真实 GitHub issue 的代码任务，agent 在真实仓库里读写文件、执行命令，靠可验证单测给奖励。关键基础设施：① 自动化环境搭建流水线，从仓库快照拉起开发环境并打包成容器镜像，覆盖 8 种编程语言，成功率 70%，跑在 10,000+ 并发 pod 的 Kubernetes 集群上；② 轻量 agent scaffold，只暴露 `bash`、`str_replace`、`finish` 三个原子工具，通过 shell 命令与 Kubernetes/Docker/本地后端交互，不用服务端工具实现，系统提示词极简、不预设工作流，让模型自己摸索最佳实践。RL 训练曲线（Figure 4）显示在约 120K 个环境上做 on-policy rollout 后 SWE-Bench-Verified/Multilingual 相对 SFT 基线显著提升，且这种大规模代码 agentic RL 能泛化到数学、通用推理等非 agentic 任务（Figure 5）。
- **Terminal Agent**：从 Stack Overflow/Stack Exchange 提炼高技术门槛问题，转成带 Dockerfile 和测试用例的计算任务，验证环境可安装、按难度和可靠性过滤后剩约 30,000 条有效查询。
- **Web Development Agent**：收集真实网页做种子 prompt，用 Playwright 执行生成代码得到渲染视频，多模态视觉判别器筛选高质量样本；用视频而非静态截图能显著降低视觉幻觉误判，覆盖 8 个网页品类。
- **General Agent**：搜索 agent 只给 `search`/`open`/`find` 三个工具，用递归事实图谱扩展生成难度可控、答案可验证的查询；工具调用 agent 用显式数据依赖 + 隐式逻辑依赖构造 tool-call graph，同时要求数据传播和隐藏状态推理能力。
- **RL 训练系统**（SGLang 推理引擎 + Megatron-LM 训练引擎，FP8）：
  - **Rollout Routing Replay（R3）**：MoE 模型在 rollout 和训练之间存在路由不一致问题（数值精度导致同一 token 在两个引擎里选到不同专家），是 [[rollout-training-mismatch]] 的一个 MoE 专属子问题；R3 强制训练时复用 rollout 阶段实际路由到的专家，通过优化数据类型和通信重叠让额外开销可忽略。多轮 agent 训练额外用请求级前缀缓存同时保存 KVCache 和 MoE 路由结果供后续轮次复用，且不同于常见的 radix cache（会跨请求共享输出缓存、破坏路由一致性），这个缓存专门避免重新 prefill 或跨请求共享。
  - **Data Scheduler**：在扩展版 Seamless Rollout Engine（[[2505.07608]] 提出的原始版本只做 rollout–reward 解耦）基础上，改成按细粒度序列而非 micro-batch 调度，动态采样时参考历史通过率做负载均衡分配新 prompt；集成 partial rollout 把超长轨迹跨训练步切分，配合 staleness-aware truncated importance sampling 限制陈旧度和局部样本占比——这是 [[async-rl-training]] 里"样本/轨迹粒度"解耦思路的一个生产实例，也是 [[rollout-efficiency]] "Partial & Early-Stop Rollout" 类别的具体落地。
  - **Toolbox 与 Tool Manager**：用 Ray 做调度，Toolbox 是集中式资源分配器，对并发任务间的工具调用强制资源配额和 QPS 限制，用容错 Ray actor pool 消除冷启动延迟；Tool Manager 与 rollout 引擎集成，靠环境预热（environment pre-warming）和序列级异步 reward 计算加速训练，并通过超时恢复和实时监控维持稳定性。两者职责分离——工具管理逻辑与系统级调度策略解耦——使得新增工具类型不需要改动 rollout 主流程，是 [[agentic-rl-frameworks]] 里"集中式环境编排"这一共识架构方向的一个具体生产实现。

## 实验与结果

- **预训练（Table 5/6）**：MiMo-V2-Flash-Base（15B 激活/309B 总参）在 MMLU-Pro（73.2）、GPQA-Diamond（55.1）、AIME 24&25（35.3）上超过 Kimi-K2-Base（32B 激活/1043B 总参）和 DeepSeek-V3.1/V3.2-Base（37B 激活/671B 总参），但 SimpleQA（20.6 对 Kimi-K2 的 35.3）明显偏低，作者归因于参数规模受限导致知识容量不足。长上下文：32K–256K 检索成功率接近 100%，GSM-Infinite Hard 从 16K 到 128K 性能衰减远小于 Kimi-K2-Base（128K 时 29.0 对 8.8）。
- **后训练（Table 9）**：73.4% SWE-Bench Verified、71.7% SWE-Bench Multilingual，均为开源模型最优（接近 GPT-5-High 的 74.9%/55.3%）；AIME 2025 94.1 分与 Kimi-K2-Thinking（94.5）、DeepSeek-V3.2-Thinking（93.1）基本持平；BrowseComp 45.4 分（搭配 Appendix C 的上下文管理方法可提到 58.3）。
- **RL 基础设施加速**：Table 10 给出的 3-MTP 解码加速（16K 输入/1K 输出，1.82×–2.70×）是本文唯一有完整数字支撑的效率指标；R3、Data Scheduler、Toolbox/Tool Manager 三个组件均**只有架构描述，没有给出吞吐提升、冷启动延迟、GPU 利用率等量化数字**——这与 [[2505.07608]] 的 Seamless Rollout Engine 给出明确的 2.29×/2.61× 加速和空闲率数字形成对比，是本文在工程量化上的明显退步。

## 局限与疑点

- RL 基础设施章节（4.6 节）三个组件全部缺少量化效果数字，"негligible overhead"（R3）、"显著加速"（Data Scheduler 未给具体倍数）、"消除冷启动延迟"（Toolbox）都是定性表述，无法评估相对 MiMo-7B 的 Seamless Rollout Engine 究竟提升了多少。
- Code Agent 环境搭建流水线的 70% 成功率意味着近三分之一任务构建失败，论文未说明失败任务的处理方式（丢弃、重试次数、还是计入训练信号），也未披露 10,000+ 并发 pod 集群的具体规模和成本。
- MOPD 蒸馏后 4 个基准下降（尤其 BrowseComp 掉 6.3 分），论文没有分析原因，也没有讨论是否存在更优的教师选择或权重调整能避免这类回退。
- 作者自己在结论里承认"架构探索仍然初步，缺乏对设计权衡的充分分析"，混合 SWA 的窗口大小/比例选择目前更多是经验结果而非理论指导。

## 对我们的启发

1. **Code Agent 的环境搭建流水线是可直接对标的沙箱能力清单**：从仓库快照自动生成容器镜像、覆盖多语言、跑在万级并发 pod 的 Kubernetes 集群上——这几乎是我们沙箱平台如果要承接"大规模代码 agentic RL 训练"客户时需要的完整能力项。70% 成功率这个数字值得作为我们自己流水线的对照基线去调研：我们的仓库快照→可执行沙箱镜像转化率能做到多少，卡点在哪个语言/生态。
2. **Toolbox/Tool Manager 的"资源配额 + 容错 actor pool + 环境预热"三件套，直接对应我们冷启动优化的核心手段**：用长驻、可复用的 actor pool 避免每次工具调用都冷启动，是我们做沙箱密度/成本优化时应该验证是否已经具备的能力；"工具管理与调度策略解耦"这个架构选择也值得参考——如果我们要支持客户自定义工具/环境，接口设计上应该避免让新工具类型侵入核心调度逻辑。
3. **MTP 不只是训练技巧，是可以直接部署给 RL rollout 阶段提速的推理特性**：论文明确指出 MTP 能缓解小 batch on-policy RL 训练中的长尾 straggler GPU 空闲问题（把并行度从 batch 维度转移到 token 维度）。如果我们平台要给训练客户提供"rollout 推理加速"选项，MTP/投机解码应该是标配能力，而不只是模型自带的推理优化。
4. **R3 提示了一个容易被忽视的 MoE 特有正确性问题**：rollout 和训练引擎路由到不同专家会造成隐藏的训练信号偏差，这是我们如果要承载 MoE 模型的 RL 训练（而不只是稠密模型）必须补的一致性保证，且不能靠"数值对齐"完全消除、需要显式的路由复用机制。
5. **Follow-up**：① 调研 R3 的原始论文（Ma et al., 2025，[[rollout-training-mismatch]] 页面提到的技术家族之一）拿到量化的开销/收益数字；② 评估我们自己的沙箱镜像构建流水线相对 MiMo 的"仓库快照→容器镜像"自动化程度和成功率差距，能否建一个内部基准；③ 跟踪 MOPD 在 SWE-Bench Verified / BrowseComp 上出现的回退是否在后续论文（如 MiMo 下一代模型）有解释或修复。
