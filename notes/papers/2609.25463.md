# Rollout Efficiency in RL for Reasoning LLMs: A Taxonomy and Future Directions

> 80 篇 rollout 效率方法的系统综述：按"系统杠杆 vs 算法杠杆"×"四类瓶颈"建双重分类，发现 67/80 只测了单一维度的收益，报告口径互不可比。

- 发表：2026-09-21（arXiv v1），目标发表在 ACM Computing Surveys
- 链接：[arXiv](https://arxiv.org/abs/2609.25463)
- 类型：综述（非提出新方法），检索 ACM DL / IEEE Xplore / arXiv / OpenReview（2024-01–2026-09），150 篇候选筛选后 86 篇入选，80 篇进入方法对比表（正文 Table 9）
- 对比基线：与本文并列的其他综述（Table 1）——多数覆盖"训练效率"或"推理效率"，唯独 Surana et al. 的 Generate-Filter-Control-Replay 综述范围最接近，但是工作流视角而非效率视角

## 要解决的问题

Reasoning RL（如 DeepSeek-R1、Kimi k1.5、OpenAI o1 的做法）把大量训练算力花在 rollout（策略生成轨迹）上——同步训练下 rollout 占单步墙钟时间的比例，多项测量给出 70%、85%，长输出场景超过 90%（作者自己在生产推理轨迹上的同步测量：基础工作负载 49%，长 CoT 变体 58%，Figure 1）。核心挑战：
1. **策略滞后与陈旧数据**：rollout 与训练重叠会引入 stale trajectory；
2. **长度离散与同步气泡**：长尾轨迹拖慢整批同步执行；
3. **长度分布随训练演化**：固定的调度/批处理假设会过时；
4. **rollout–训练不一致**：rollout 引擎和训练引擎对同一 token 算出不同 log-prob，静默扭曲优化器输入；
5. **样本效率与轨迹选择**：并非每条生成的轨迹都有学习价值，均匀分配 rollout 预算浪费算力。

已有综述分别覆盖训练效率、推理效率或 RL 方法论，没有一篇把"生成训练轨迹的成本"当作独立的分析单元——这是本综述要填的空白。

## 方法（这是一篇综述：两层分类法本身就是核心贡献）

### 问题形式化

一次同步迭代有 4 个计入成本的阶段：rollout（$T_{roll}$）、reward 评估（$T_{rew}$）、选择与更新（$T_{upd}$）、权重同步（$T_{sync}$）。Rollout efficiency 定义为达到目标策略质量 $Q^*$ 所需的成本：$\min_S C_S(Q^*)$，$C$ 可以是墙钟时间、加速器小时、生成 token 数或金钱成本——这些量**不可互换**，一个方法可能减少 token 数但增加墙钟时间。论文特别区分"rollout-path cost"（单次迭代的生成成本）与"端到端 cost-to-quality"（达到目标质量的总成本）——很多文献混淆这两者，是不可比性的主要来源之一（Section 8）。

### 双重分类法

**机制分类**（7 大技术家族，系统杠杆 5 个 + 算法杠杆 2 个）：

- **系统杠杆**（把已请求的 rollout 工作执行得更快，不改变请求了什么）：
  - **A.1 Pipeline Decoupling**（流水线解耦）：让 rollout 和训练 worker 并发运行，代价是引入策略滞后（policy lag），需要 staleness bound 或 off-policy 修正。代表：[[async-rl-training|AReaL]]（1.5B–32B，吞吐 2.77×）、LlamaRL（405B，单步 10.7×，用 AIPO 修正 1-step lag）、Laminar（轨迹粒度，lag ≤ 4）、ProRL Agent/FlexMARL/RollArt/AstraFlow（把 barrier 移出训练器，走 HTTP 接口）。新趋势是放宽"能容忍多少 lag"而非"多细粒度跨越 barrier"：VCPO 报告 lag 到 128 步仍稳定（配合按有效样本量缩放学习率）。
  - **A.2 Resource-Aware Execution**（资源感知执行）：把 rollout/训练当作异构或间歇可用硬件上的放置问题。三个方向：收割 preemptible/spare 容量（RLBoost）、借用 serving 的空闲 GPU（ROSE）、在线重规划 rollout/训练 GPU 配比（Libra、DynaResize）；另一翼是降低单条 rollout 的footprint：4-bit/FP8 量化 rollout（QaRL、FP8-RL、Jet-RL）、KV cache 压缩（Sparrow、Sparse-RL）、只传输变化的权重分片（AReaL-DTE，权重同步加速 6.8–7.6×）。
  - **B.1 Scheduling & Load Balancing**（调度与负载均衡）：不改变生成算法或资源池，只改变请求的排序/分组/分配。核心是长度预测信号：训练 ranker（StreamRL）、历史长度分布（RhymeRL 的 HistoPipe，不需要额外模型）、短探针（TailSieve）、GRPO 组内 sibling 相关性（Seer，用一个 sibling 先跑做探针）。RollPacker 端到端 2.03–2.56×。
  - **B.2 Partial & Early-Stop Rollout**（部分/提前停止 rollout）：不生成完整轨迹。固定预算截断（DeepScaleR，逐步提高 context 从 8K→16K→24K，约 3800 A100-小时对比全量单阶段估算的 70000 小时）；暂停恢复（Kimi k1.5，128K context 下可行的关键）；学习信号触发的提前停止（ESPO，减少 rollout token >20% 且提升准确率，随机停止对照组只能到 42.4% vs ESPO 的 46.28%，证明收益来自"停哪些"而非"停多少"）。
  - **B.3 Speculative Decoding**（投机解码）：RL 场景的特殊之处是连续 batch 不独立——旧策略的输出可以做新策略的草稿。草稿来源分四类：复用上一步轨迹（SPEC-RL）、跨步 suffix tree（RhymeRL 的 HistoSpec、DAS）、训练小型草稿模型（ReSpec、TLT）、策略自带的 multi-token-prediction 头（MTP-RL，复用 DeepSeek-V3/R1、Qwen3.5 原生自带的 MTP 模块）。

- **算法杠杆**（减少学习所需的 rollout 工作量，改变请求什么/用什么）：
  - **C. Rollout Selection**（rollout 后选择）：生成后再决定用哪些。PODS 生成大批次、只在最大奖励方差子集上做更新，peak accuracy 提速 ≥1.7×（但只省了 update 阶段，生成成本已经付出）；POPO 用 decoupled importance sampling 从 replay buffer 替换退化组，达到与过采样基线相当的效果只用约 30% 的 rollout 预算。
  - **D. Prompt Filtering & Selection**（prompt 过滤与预算分配）：在生成前/生成中预测哪些 prompt 值得生成。GRESO（reward 历史信号，rollout 提速 2.4×，最多减少 3.35× rollout，质量持平 61.5 vs 61.3）；KGPS（线性高斯状态空间模型显式建模非平稳性，比动态采样减少 83% rollout）；VIGOR（少量探针 rollout + 方差重分配，数学任务 2.3× 更少 rollout 达到目标质量）。

**瓶颈分类**（4 类问题，与机制分类是正交的两个视角）：
- **Problem A**（rollout–训练同步 barrier 与空闲容量）与 **Problem B**（长尾生成）是"执行浪费"——请求的工作没变，但执行它浪费了时间/容量；
- **Problem C**（生成后发现不够有信息量的 rollout）与 **Problem D**（生成前就该跳过的 prompt）是"学习价值浪费"——预算花在了边际学习价值低的轨迹/prompt 上。

### GRPO 退化组：算法杠杆的根本动机

标准 GRPO（[[grpo]]）里，一个 prompt 的 $G$ 个采样在组内做标准化得到 advantage；如果全组奖励相同（都对或都错），标准差为零，整组 advantage 全部归零——但生成和评估的成本已经付出。退化概率 $P_{deg}(p,G) = p^G + (1-p)^G$，在 $G=8$、$p=0.9$ 时约 43%，$p=0.95$ 时约 66%（即三分之二的组毫无信号）。DAPO 的动态采样（过采样直到凑够非退化组）是标准做法，但随着策略变强、prompt 变"容易"，其 rollout 成本会持续增长——这正是 rollout selection 与 prompt filtering 两个算法家族存在的理由。

## 实验与结果（综述自身的实证发现，而非某个方法的实验）

- **两个杠杆几乎不同时报告**（Finding 1）：80 个方法中 50 个只报系统收益、17 个只报算法收益、12 个两者都报、1 个（I-PPO）只做了未量化的效率声明。系统杠杆里的两个 Problem A 家族（pipeline decoupling、resource-aware execution）合计 32 个方法中 30 个完全没有算法效率的量化证据。
- **同一个系统内部的配置差异，比不同方法之间的差异还大**（Finding 2）：HybridFlow 在自己的不同配置下报告 1.53–20.57× 的跨度；StreamRL 相对 veRL 报 1.12–2.12×，相对自建的 colocated baseline 只报 1.06–1.41×——baseline 选择、阶段边界（rollout-only vs 端到端）、吞吐单位（samples/s vs tokens/s）、聚合统计量（max vs mean）、硬件规格（H100/H800/H20/A800 等出口管制变体的互联带宽不同）共同决定了报出来的数字，五个来源叠加使跨论文的加速比基本不可比。
- **算法杠杆几乎只在单轮可验证任务上测过**（Finding 3）：29 个报算法收益的方法里只有 6 个测了交互式 rollout（如 ALFWorld、BFCL-V2、SWE 任务），11/80 的方法甚至没披露评测任务本身。
- 论文给出的补救措施：(1) 最小报告清单（baseline 版本、测的是哪个阶段、吞吐单位、聚合统计量、硬件规格、workload 特征包括响应长度的变异系数、测的是哪个杠杆、质量证据）；(2) 把两个杠杆统一到同一个"加速器小时 → 目标质量 $C(q)$ 曲线"上比较；(3) 五个诊断协议——同等丢弃比例下随机对照（ESPO 已示范）、增量 ladder（TailSieve 已示范：路由 1.67×→路由+尾部投机 2.59×）、投机接受率随策略漂移的变化曲线、staleness 扫描而非单点、匹配 cost 而非匹配 step 数比较质量。
- **可组合性分析**（Table 3，21 对组合中只有 2 对有隔离测量的增量）：AReaL-Hex 在已经异步的 AReaL 基础上再叠加异构硬件放置，测到 1.31–1.50× 的独立增量，是论文认定"最干净的跨家族组合证据"。多数组合停留在"共同实现但未隔离测量增量"或纯粹是机制推导的假设。

## 局限与疑点

- 论文自己承认：taxonomy 按"每个方法的主导机制/主导瓶颈"归类是一种简化，跨杠杆的混合方法（如 partial rollout 同时改变执行方式和采样分布）依赖人工判断放在哪一族。
- **可组合性的大部分结论是机制推导的假设，不是实测**（21 对里只有 2 对有隔离增量证据）——论文自己列出的"复合收益"很多其实未经验证，读者需要区分"实测"vs"假设"标记（Table 3 有明确区分）。
- 综述统计口径本身受限于"论文声明的效率增益"，无法验证每个被综述方法自己的复现性；本文没有做任何独立复现实验。
- Finding 3 指出算法杠杆几乎没在 agentic/多轮/部分信用奖励任务上测过——这恰好是本方向（沙箱/SWE/terminal agent）最关心的场景，意味着这条文献路线对我们的直接可迁移性目前证据不足，需要自己验证。

## 对我们的启发

- **Rollout ≠ 普通 serving，是一个独立的调度优化问题**（Section 3.2 五条性质：受控批到达、批 makespan 而非请求延迟、重复且部分可预测的工作负载、演化中的模型状态、训练专属正确性要求）。如果我们平台要同时承载 RL 训练的 rollout 生成和常规推理 serving，**不能直接搬普通 serving 的调度策略**——rollout 阶段可以利用"任务重复出现、历史长度/难度可预测"这些普通 serving 没有的信息做调度，这是我们做调度系统时值得专门设计的差异化能力点。
- **Resource-Aware Execution 家族直接对应我们"沙箱/超卖"关心的问题**：借用空闲 serving GPU 做 rollout（ROSE）、异构硬件按阶段特性分配（AReaL-Hex：rollout 对内存带宽敏感、训练对算力/内存容量敏感）、在线重规划 rollout/训练配比（Libra、DynaResize）——这些都是"把 RL 训练当成可以超卖/借用容量的弹性工作负载"的具体做法，值得作为我们平台调研候选深挖（尤其是 ROSE 借用 serving GPU 这条路线，如果我们本身也提供推理 serving，存在直接复用的可能）。
- **Pipeline Decoupling 的核心权衡（重叠 vs 策略滞后）与我们做调度/抢占系统时的经验一致**：粒度越细（batch→sample→trajectory→service interface），吞吐收益越大但 staleness 管理越复杂；论文指出"文献里没人系统扫过 lag-quality 曲线"，如果我们要设计自己的异步训练调度器，这是一个可以自己补的实验空当，而不是照抄某个固定 lag 值。
- **Rollout–训练数值不一致（[[rollout-training-mismatch]]）是一个容易被忽略但会静默腐蚀训练信号的正确性问题**：即使完全同步、on-policy，rollout 引擎（vLLM/SGLang）和训练引擎（FSDP/Megatron）因为 kernel/精度/batching 不同也会对同一 token 算出不同概率，长轨迹上会累积。如果我们平台要为客户提供"rollout 生成"能力（而不仅是通用推理 serving），需要把这个一致性问题作为产品/API 设计的显式约束，而不是假设"用同样的模型权重就等价"。
- **评估口径的五个不可比来源（baseline/阶段边界/吞吐单位/聚合统计量/硬件规格）值得直接搬进我们自己的 benchmark 规范**：无论我们是评估内部训练系统还是对外做能力宣传，都应该采用论文提出的最小报告清单，避免自己也掉进"同一系统内部配置差异比方法差异还大"的陷阱。
- Follow-up 建议（可转 issue）：
  1. 精读 AReaL / veRL(HybridFlow) / StreamRL 这几个开源异步 RL 训练框架的具体实现，评估其 pipeline decoupling 设计能否复用到我们自己的调度系统；
  2. 精读 ROSE（借用 serving 空闲 GPU 做 rollout）与 Libra（在线重规划 rollout/训练 GPU 配比），这两个最贴近"沙箱超卖/弹性容量"的方向；
  3. 跟踪本文列出的"评估检查清单"和 $C(q)$ 曲线方法论，看是否可以直接作为我们内部训练系统 benchmark 的报告规范；
  4. 关注 Section 9 提出的"多模态/异构推理 rollout 重构"方向——如果我们平台未来要支持多模态 agent 训练，当前 token-based 成本模型不适用，需要提前调研。
