# Restoring Uniqueness in MicroVM Snapshots

> Firecracker microVM 快照克隆/恢复能把 serverless 冷启动砍到毫秒级，但克隆出的多个实例内存状态完全相同，会导致 UUID/nonce/密钥重复这种“意外 Sybil 攻击”；本文提出两个新内核接口——MADV_WIPEONSUSPEND 与 SysGenId——分别在挂起时清空敏感内存、在恢复时递增一个可被监听的世代号,以最小的性能开销恢复实例唯一性。

## 元信息

- 机构：Amazon Web Services（AWS Lambda 团队，含 Firecracker 作者 Marc Brooker）
- 发表：arXiv 2021-02-04（cs.CR / cs.DC / cs.OS，未见正式会议/期刊版本）
- 链接：[arXiv abs](https://arxiv.org/abs/2102.12892) · [HTML](https://arxiv.org/html/2102.12892v1)
- 对比基线：Microsoft Hyper-V 的 VmGenId（Windows Server 2012 起）、fork 场景下已有的 MADV_WIPEONFORK（Linux 4.14, 2017）、密码学层面的替代方案（AES-GCM-SIV 等 nonce-misuse-resistant 加密模式、HSM/KMS/TEE）

## 要解决的问题

Lambda 用 post-initialization 内存快照 + 克隆恢复来隐藏代码初始化（下载代码、执行静态初始化、填充缓存、建立连接）耗时——这一步在 Du et al.（Catalyzer）的测量中占启动总时间的 25%–95%。Firecracker 快照恢复可以做到 4ms 级别，但这种"存一次、恢复很多份"的模式带来三个系统级挑战：① 快照把内存（可能含密钥等高价值内容）落到存储介质上；② 克隆复制了完整内存状态，破坏了应用生成唯一值（UUID、请求 ID、加密 nonce）的假设；③ 克隆与 TCP/TLS 等假设客户端唯一身份的会话层协议不兼容。本文只聚焦第②个问题——唯一性恢复，尤其是密码学意义上的唯一性（IV/nonce 重用会直接破坏 AES-CTR、AES-GCM 等模式的安全性，NIST SP800-38D 要求同 key 同 IV 重复使用的概率 ≤ 2⁻³²）。

## 方法

核心思路：不改变用户态 CSPRNG（Java SecureRandom、OpenSSL 等）的接口和性能特征，而是在系统层提供一个"克隆/恢复发生了"的确定性信号，让 PRNG/密码库能据此重新播种（reseed）。

- **MADV_WIPEONSUSPEND**（本文贡献，已提交进 Linux 内核主线）：类比已有的 `MADV_WIPEONFORK`（fork 时子进程该页清零），新增一个 madvise 标志，标记的内存页在 microVM 被挂起（快照前的必经步骤）时清零。PRNG 把内部状态或一个 guard 变量标记为该 flag，就能在下次访问时检测到"我被克隆过"并触发 reseed。优点：① 在挂起（而非恢复）时清空，把开销放在非关键路径上，优化恢复延迟；② 可以直接标记高价值密钥，让它们根本不出现在快照里（作者称为"从快照里排除敏感数据"）；③ 不需要 `open`/`read` 系统调用，适合 seccomp-bpf 之类禁止文件访问的沙箱环境。性能：每次随机数生成约增加 600ns 开销；对"生成顺序 nonce"这种极简操作，开启检查会让吞吐降 13 倍，但只要检查内做了有意义的工作（如跑完整个 CTR_DRBG),相对开销就趋近于零。
- **SysGenId**（本文贡献，已提交进 Linux 内核）：类比 Hyper-V 的 VmGenId（一个 128-bit UUID，出现在 ACPI 暴露的内存位置,Windows Cryptography API 直接使用),在 Linux 里实现为字符设备 `/dev/SysGenId`，暴露一个单调递增的世代计数器。应用/库 `open` 该设备后 `read` 会阻塞直到世代号变化;还提供两个 ioctl（`SYSGENID_GET_OUTDATED_WATCHERS` / `SYSGENID_WAIT_WATCHERS`)供 serverless/容器控制面用来确认"所有打开了该设备的进程都已经确认了新世代号",再放行新请求进入刚恢复的沙箱。SysGenId 是一个前端驱动，依赖一个后端（VmGenId 是其中一种后端）来判定"身份何时变化";这个设计也能支持用户态 checkpoint/restore（CRIU）和 Linux 容器，因此作者称 SysGenId 是 VmGenId 的推广。
- **对比与取舍**（Table 1）：MADV 方案的优势是同时覆盖 fork 与 suspend、可隐藏密钥、无需文件系统权限、最小权限；SysGenId 的优势是自带通知机制（能确认所有 watcher 都已感知新世代号，代价是可能在恢复路径上引入阻塞式工作,重新带回一部分冷启动延迟）；VmGenId 的优势是直接给出一个高质量 128-bit UUID,可以直接当 PRNG 的高熵种子或分布式系统节点 ID 用,但不支持 fork、无法隐藏密钥、非 root 进程访问不便。三者都不依赖磁盘 I/O,都是通过内存页/mmap 暴露信息。
- **原子性与 TOCTOU 边界**（§3.7）：这两个机制只保证"检测到克隆并 reseed"这一步是可行的,但不能杜绝"生成值和使用值之间发生克隆"这类 time-of-creation/time-of-use 竞态——需要更上层的机制（如健康检查、负载均衡器探活）在放行请求前确认 reseed 已完成。Serverless 系统本身天然具有优势：可以完全静默一个 VM,确保它在完成通知流程前不处理任何请求，这足以保证"跨请求"不会重复使用随机数（前提是应用不跨请求缓存这些值）。
- **替代路线**（§3.6，被作者认为都不充分或不现实）：nonce-misuse-resistant 加密模式（AES-GCM-SIV 等）只能缓解密码学层面的后果，且现网大量协议仍用传统模式；完全弃用用户态 CSPRNG、只用内核/硬件随机数会牺牲性能；依赖 HSM/KMS/TEE（如 Nitro Enclaves）在很多场景下不适用（性能、已有代码库约束）。

## 实验与结果

在 x86 机器（EC2 m5.12xlarge）上测量：

- Reseed 开销：从 `/dev/urandom` 取 32 字节（含 open/read/close）均值 11µs；从 RDRAND/RDSEED 取 32 字节仅 0.6µs（与 Intel 官方性能数字一致）。
- Guard page 检查开销：检查一个用 MADV_WIPEONSUSPEND 或 mmap 的 VmGenId 页很快;对"生成一个顺序 nonce"（仅一次 128-bit 自增）这种极简操作，开启检查使吞吐降低 13 倍；但对 OpenSSL 默认 `md_rand` 这类有实质计算量的生成器，开启检查前后吞吐无统计显著差异——即检查开销会被真实工作量摊薄到可忽略。
- 论文本身未给出的数字：MADV_WIPEONFORK/WIPEONSUSPEND 对 NIST CTR_DRBG 具体吞吐下降百分比处标注了「TODO%」——**发表版本里这个关键数字缺失**，读者需要自行留意这是未完成的占位符,不能当作已验证结论引用。

## 局限与疑点

- 论文明确留白：CTR_DRBG 的具体吞吐损失数字用「TODO%」占位，未补全，是本文最大的可复现性缺口。
- 只在单一 x86 机型（m5.12xlarge）上测量,未讨论跨代 CPU、ARM（Graviton）等平台上 guard page 检查与硬件 RNG 指令的开销是否一致。
- §3.7 承认 TOCTOU 问题无法在系统层被完全杜绝,只能"缓解"，具体缓解手段（健康检查、探活）语焉不详,留给使用方自行设计,可操作性不足。
- SysGenId 的通知机制（`SYSGENID_WAIT_WATCHERS`）本身可能在恢复路径上引入阻塞式等待，作者只说"应用/库应仅用于轻量目的"，但没有给出这种阻塞对冷启动延迟实测影响的数字。
- 论文只讨论了 Linux guest；虽然作者说方法可推广到其他 guest OS/unikernel/libOS，但没有给出移植成本或验证。
- "VM 的身份何时改变"这一语义问题（§3.5，如"不克隆的普通快照恢复"是否该算新身份）作者承认 Microsoft 现有规则未必适合 serverless 场景，但本文没有给出 SysGenId 在 Lambda 里具体采用的规则,只指出这是一个需要单独设计的系统级问题。

## 对我们的启发

- **我们的沙箱平台如果用"快照恢复"做冷启动优化（无论是 microVM 快照，还是容器 checkpoint/restore 类似 CRIU），克隆出的实例默认会共享内存里的全部随机状态**——这不是一个边缘案例,而是所有走这条路径的系统都会踩的坑:PRNG 种子、TLS session、request-id 生成器、幂等 token 生成器都可能在恢复后产生重复值,进而造成日志串号、trace 错乱、幂等语义失效,乃至密码学意义上的密钥/nonce 重用漏洞。做快照/暂停恢复类冷启动优化之前，必须先盘点"哪些内存内容依赖唯一性假设"。
- **两种解法代表两种不同的工程哲学，值得对照评估而非无脑抄一个**：MADV_WIPEONSUSPEND 是"清空 + 应用自行 reseed"，改造成本在应用/库这一侧（需要库主动标记 guard page），优点是可以顺带隐藏密钥、无需设备访问权限，适合我们这种默认限制文件/设备访问的沙箱环境；SysGenId 是"系统提供一个可监听的世代号 + 控制面等待所有客户端确认"，改造成本在运维/控制面这一侧（需要在恢复后主动等待确认才放行请求），优点是有确定性的完成信号,适合我们已经有 edge/控制面统一管理沙箱生命周期的架构（类似 DSec 的 edge 组件）。
- **如果我们平台的沙箱快照被设计成"存一次、恢复出多个并发实例"（而不是单实例暂停/恢复同一份状态），这个唯一性问题会比 DSec 目前描述的场景更严重**——需要在设计快照复用策略时明确判断是哪种模式（见下「与母论文的关系」）。
- **性能启示可直接复用**：guard page 检查本身开销极小（对有实质计算量的 PRNG 几乎可忽略），意味着"给所有克隆敏感状态加唯一性检查"不是一个需要在性能和安全之间做艰难取舍的决定,可以默认开启。
- Follow-up 建议（可转 issue）：
  1. 盘点我们现有沙箱冷启动/暂停恢复路径（如果用了类似 Firecracker 快照或容器 checkpoint）是否存在"多实例共享同一份克隆前内存状态"的场景，具体检查 PRNG 种子、TLS 连接、幂等 token 生成逻辑；
  2. 评估在我们的沙箱 guest 镜像里引入类似 MADV_WIPEONFORK/WIPEONSUSPEND 语义（如果 guest 内核版本支持）或等价的"恢复时强制 reseed"约定的可行性与改造成本；
  3. 如果我们的控制面（对应 DSec 的 edge）未来需要支持"暂停后被多次/并发恢复"这种快照复用模式,需要设计类似 SysGenId 的世代号 + 就绪确认机制,而不是假设恢复出的实例天然与原实例等价。
