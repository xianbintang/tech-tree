# MiMo-VL Technical Report

> Xiaomi 用四阶段预训练（2.4T token，含大量长 CoT 推理数据）+ 混合 on-policy RL（RLVR+RLHF）把一个 7B VLM 练到多模态推理、GUI grounding 均达到开源 SOTA，同时首次报告"多域联合 RL 存在任务干扰、难以同时提升所有能力"。

## 元信息

机构：LLM-Core Xiaomi ｜ 发表：2025-06-04（v1）｜ arXiv：https://arxiv.org/abs/2506.03569 ｜ Code：https://github.com/XiaomiMiMo/MiMo-VL ｜ 评测框架：https://github.com/XiaomiMiMo/lmms-eval ｜ 对比基线：Qwen2.5-VL-7B/72B、InternVL3-8B、Gemma-3-27B-IT、GPT-4o、Claude-3.7-Sonnet、QVQ-72B-Preview、Gemini-2.5-Pro；GUI 专精模型 UI-TARS、Aguvis、OS-Atlas

## 要解决的问题

多模态预训练长期依赖直接问答式（QA）数据，短答案训练容易导致模型停留在表层模式匹配、在新场景过拟合。同时后训练阶段通常只单独做 RLVR（可验证奖励）或单独做 RLHF（人类偏好对齐），本文尝试在同一个后训练框架内同时做两者，覆盖推理、感知、grounding、人类偏好四类差异很大的能力。

## 方法

### 预训练：四阶段 + 后期大幅注入长 CoT 推理数据

架构为 Qwen2.5-ViT 编码器 + 随机初始化 MLP projector + [[grpo|MiMo-7B-Base]] 语言模型骨干。四阶段（Table 1）：Stage 1 projector warmup（300B token，图文对）→ Stage 2 视觉-语言对齐（167B token，解冻 ViT，引入交错图文数据）→ Stage 3 通用多模态预训练（1.4T token，OCR/grounding/视频/GUI/QA/推理数据全量引入）→ Stage 4 长上下文 SFT（550B token，序列长度 8K→32K，大幅提高长推理数据占比）。

关键发现：把合成的长 CoT 推理数据直接大量注入**预训练**后期阶段（而不是仅作为后训练补充微调数据），效果持续提升不饱和——Stage 4 单阶段带来 MMMU +9、OSWorld-G +14、OlympiadBench +16 的跃升；MMMU 上模型平均回复 token 数从 680 涨到 2.5K，说明推理深度本身在增加。

### 后训练：Mixed On-policy Reinforcement Learning（MORL）

MORL = [[grpo|RLVR]]（Reinforcement Learning with Verifiable Rewards）+ RLHF 同时优化：

- **RLVR 五类任务**：视觉推理（8 万道 STEM 题，Math-Verify 规则判分，剔除可解性>90%的简单题和不依赖图片就能解的题）；文本推理（复用 [[grpo|MiMo-7B]] 的数学数据）；图像 grounding（框输出用 GIoU 奖励，点输出用"落入 ground-truth 框内"判定）；视觉计数（计数准确率）；时序视频 grounding（预测 `[mm:ss,mm:ss]` 时间段，IoU 计分）。
- **RLHF**：双奖励模型（文本奖励模型从 MiMo-7B 初始化，多模态奖励模型从 MiMo-VL 初始化），Bradley-Terry 目标；查询经过去重、聚类多样性筛选、中英文与"有用性/无害性"配比平衡；用先进 VLM 对多模型响应做成对排序构造训练数据；同一批查询同时用于奖励模型训练和 RLHF，以降低 reward hacking 风险。
- **On-policy [[grpo]] 变体**：单步策略更新、无需 clipped surrogate；沿用 [[grpo|MiMo-7B]] 的三项改动组合（去 KL loss、Dynamic Sampling、easy data filter/resampling），把同一套文本 reasoning RL 配方原样搬到多模态场景。
- **Reward-as-a-Service（RaaS）**：MORL 需要同时服务推理、感知、grounding、文本/多模态 RLHF 等多种差异很大的奖励函数或奖励模型。RaaS 提供统一接口——一个 reward router 根据任务类型动态路由到对应奖励函数；奖励模型被部署为独立的 HTTP 服务以保证近零延迟；所有奖励归一化到 [0,1]；训练中**不使用额外的格式奖励**。整套 MORL 流程构建在 verl 框架 + Seamless Rollout Engine（即 [[grpo|MiMo-7B]] 论文里那一套同步 rollout 加速基础设施，见 [[async-rl-training]]、[[agentic-rl-frameworks]]）之上。

## 实验与结果

- MiMo-VL-7B-RL 在 40 个评测任务里有 35 个超过 Qwen2.5-VL-7B（Table 2）；OlympiadBench 59.4 分，超过参数量达 78B 的模型（Table 3）。
- GUI：OSWorld-G 56.1 分，超过 GUI 专精模型 UI-TARS；作为通用 VLM 在 ScreenSpot-Pro、OSWorld-G 这类更难的基准上与专精模型（UI-TARS、Aguvis、OS-Atlas）表现相当甚至更优（Figure 4）。
- Elo 评测（style-controlled、GPT-4o 判分）：MiMo-VL-7B-RL 在所有开源 VLM 中 Elo 最高，逼近 Claude 3.7 Sonnet；MORL 相对纯 SFT 模型带来 22+ 分的 Elo 提升（Figure 5）。
- **On-policy RL vs vanilla GRPO 的规模化行为对比（Figure 7，纯文本推理任务）**：on-policy 算法性能随训练数据量持续正相关增长，在观测窗口内未见饱和迹象；vanilla GRPO 初期样本效率更高，但训练样本达到约 2 万条后性能基本饱和，之后继续训练收益可忽略。

## 局限与疑点

- **任务干扰（interference）未解决**：MORL 几乎在所有任务上都有提升，但难以让所有能力域同时稳定提升——推理类任务训练中倾向拉长回复长度，grounding/计数类任务则倾向缩短，两种相反的长度增长趋势互相干扰；任务难度差异和 reward hacking 风险可能也是原因之一。作者明确表示"仍在积极调查根因"，本文未给出解决方案。
- On-policy vs vanilla GRPO 的对比只在纯文本推理任务上做了一次定性曲线观察（Figure 7），没有在多模态任务上重复验证，也没有给出具体样本量-性能的数值表格。
- RaaS 只有架构描述（路由器 + 独立 HTTP 服务），没有披露延迟、吞吐或奖励计算引入的额外开销等工程数字。
- 视觉推理 RLVR 数据的"剔除可解性>90%简单题"依赖 MiMo-VL 自身的 rollout 通过率来定义难度，如果基座模型能力本身有偏差，这个过滤标准的有效性存疑（论文未讨论）。

## 对我们的启发

1. **Reward-as-a-Service 是一个值得对照的奖励服务解耦模式**：把"奖励路由 + 奖励模型作为独立 HTTP 服务"与 rollout 引擎解耦，是我们平台如果要同时支持规则奖励（数学/代码判分）和模型奖励（RM 打分、LLM-as-judge）混合的多任务 RL 训练时的一个具体架构参考。可以对比同团队更晚期的 Toolbox/Tool Manager（[[agentic-rl-frameworks|见 2601.02780 笔记]]）——后者面向工具调用而非奖励计算，值得调研 RaaS 这条子系统是否在后续模型里被合并或替换（follow-up）。
2. **任务干扰的发现为"专家化训练 + 蒸馏合并"提供了动机线索**：本文（2025-06）报告"联合多域 RL 难以同时提升所有任务"且未给出解法；同团队更晚的 MiMo-V2-Flash（[[on-policy-distillation|2601.02780]]，2026-01）改为"分域训练专家 + MOPD 蒸馏合并"的路线。两篇论文互不引用对方的这个具体论点，但时间线和技术选择的呼应值得关注——如果我们要给客户建议"单个大 MORL 联合训练 vs 拆分多个专项 RL 再合并"，这组前后对照是一个有价值的案例，值得读 2601.02780 原文确认是否显式提到规避本文这个干扰问题（follow-up，可建 issue）。
3. **On-policy RL 不饱和 vs vanilla GRPO 提前饱和的规模化差异，是容量规划信号**：如果 on-policy 训练能持续从更多 rollout 数据中获益而不饱和，这意味着为 on-policy RL 训练场景持续投入 rollout 吞吐容量是值得的；而 vanilla GRPO 场景下，超过某个样本量继续加大 rollout 预算收益递减，容量规划应该设置更保守的上限。这条经验目前只在文本任务上验证过一次，规划前应先确认是否适用于我们实际训练的任务类型。
