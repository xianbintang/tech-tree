# OpenHands: An Open Platform for AI Software Developers as Generalist Agents

> 开源 agent 平台（原 OpenDevin）：用统一的"代码即动作"接口 + Docker 沙箱 REST 运行时，把 agent 框架、执行环境、多 agent 协作和评测打包成一体，ICLR 2025 收录。

## 元信息

机构：UIUC / CMU / Yale / UC Berkeley / Contextual AI / KAUST / ANU / All Hands AI / Alibaba

链接：[arXiv](https://arxiv.org/abs/2407.16741) · [Code](https://github.com/All-Hands-AI/OpenHands)（MIT 协议，32K+ star，2.1K+ PR，188+ 贡献者）
对比基线：AutoGPT、LangChain、MetaGPT、AutoGen、SWE-Agent、AutoCodeRover 等（Table 1 定性对比）

## 要解决的问题

2024 年前后涌现的开源 agent 框架（LangChain、MetaGPT、AutoGen 等）普遍只覆盖"agent 框架三件套"的一部分：要么没有内置沙箱执行、要么没有浏览器、要么没有可复现的评测框架、要么各功能之间彼此割裂（Table 1）。作者认为一个可用于生产/研究的 agent 平台必须同时具备：(1) 统一的动作接口，(2) 安全隔离的代码执行环境，(3) 可扩展的工具/技能库，(4) 多 agent 协作能力，(5) 内置、可复现的评测框架——OpenHands 试图把这五者做成一个开箱即用的整体，而不是让每个研究组各自拼凑。

## 方法

系统由三个核心组件构成（Fig. 2）：**Agent 抽象**（可插拔实现）、**Event Stream**（action/observation 的时间序历史）、**Runtime**（把 action 转成 observation 的执行层）。

- **动作空间（CodeAct 范式）**：不用 JSON function-calling 描述工具，而是直接让 agent 产出可执行代码/命令。核心动作只有三类：`IPythonRunCellAction`（Python 代码）、`CmdRunAction`（bash 命令）、`BrowserInteractiveAction`（浏览器操作，DSL 来自 BrowserGym）。这个范式继承自 [[codeact-action-space]] 论文（Wang et al. 2024a），论点是"代码"本身就是最通用、最省心维护的工具描述语言——不需要为每个 API 单独定义 JSON schema，agent 甚至能现场用代码自造工具。
- **Agent Runtime（沙箱执行层）**：每个任务 session 启动一个独立的 Docker 容器沙箱，容器内跑一个 REST API server（"OpenHands Action Execution API"），维护 bash shell、Jupyter IPython server、基于 Playwright 的 Chromium 浏览器三类子环境。OpenHands 后端（`runtime.py`）通过 RESTful API 把 event stream 里的 action 发给容器内 client 执行，client 把执行结果（stdout/stderr、DOM、截图等）作为 observation 传回。支持任意用户提供的 base Docker 镜像：构建流程会把 OpenHands 的 runtime client 代码注入用户镜像，生成新的"OH runtime image"。
- **运行时镜像构建与缓存（dual-tagging）**：为兼顾可复现性与构建效率，每个 runtime 镜像同时打两个 tag——**hash tag**（基于 Dockerfile + runtime client 源码的 MD5，相同 hash 保证内容完全一致，可放心复用）和**generic tag**（`oh_v{version}_{base_image}_tag_{tag}`，代表"某个 base image + OpenHands 版本组合"下的最新构建，即使源码变化也会被覆盖更新）。构建时先查 hash 精确命中 → 未命中则退化为用 generic tag 镜像做增量构建（复用依赖安装结果）→ 都没有才从 base image 完全重建（Appendix F.2，Fig. 5）。这是一个比 [[sandbox-image-distribution]] 里 DSec 的分层 + 按需拉取方案简单得多的缓存策略，本质是"镜像内容寻址 + 增量重建"，没有把 base/workspace/toolkit 拆成独立生命周期的层，也没有按需 I/O。
- **AgentSkills（Agent-Computer Interface）**：一个作为 Python 包自动导入进 IPython 环境的工具库（文件编辑 `edit_file`/`scroll_up`/`scroll_down` 改编自 SWE-Agent 和 Aider，多模态解析 `parse_image`/`parse_pdf`）。收录标准很克制：只有当 (1) LLM 靠写代码本身做不到（如精确按行编辑），或 (2) 需要调用外部模型（如语音转文字）时才新增工具，避免重新教 agent 它已经会用的 Python 库（如 pandas）。
- **多 agent 委托**：`AgentDelegateAction` 允许一个 agent 把子任务转交给另一个专精 agent（如通才 CodeActAgent 把复杂浏览任务委托给专门的 BrowsingAgent），复用而非重写能力。
- **AgentHub**：内置 10+ 社区贡献的 agent 实现，默认通才 agent 是基于 CodeAct 的 CodeActAgent；此外有 BrowsingAgent（WebArena 风格零样本浏览 baseline）、GPTSwarm Agent（可优化图结构多 agent 系统）、Micro Agent（复用通才 agent 逻辑、专注单一场景的轻量特化）。
- **集成测试框架（Appendix E）**：为避免每次代码改动都要跑一次完整评测（如一次 SWE-Bench Lite 用 gpt-4o 约 600 美元），OpenHands 搭了一套端到端集成测试：预定义任务 + "金标准"输出文件做断言，同时**mock LLM 调用**（按 exact prompt match 返回预存响应）保证测试确定性、降低成本；prompt 有实质性变化时才用真实 LLM 重新生成响应对。

## 实验与结果

覆盖软件工程、Web 浏览、杂项辅助三大类共 15 个基准（Table 2）。关键数字（均使用 CodeActAgent，不针对具体基准做手工 prompt 工程）：

- **SWE-Bench Lite**（300 实例，无 hint）：CodeActAgent v1.8 + claude-3.5-sonnet 解决率 **26.0%**，单实例均成本 $1.10；同期 SWE-Agent（18.0%）、AutoCodeRover（19.0%）、Aider（26.3%）（Table 4）。全量 2294 实例跑一遍成本估算 $6.9k（按 $3/实例保守估算），这是它们默认用 Lite 子集评测的原因。
- **HumanEvalFix**（164 实例，Python 子集）：CodeActAgent v1.5 + gpt-4o **79.3%**，接近双倍于非 agent 方法 StarCoder2-15B 的 48.6%；SWE-Agent 1-shot 达 87.7%，但给了完整成功轨迹示范，OpenHands 是 0-shot。
- **WebArena**（812 实例）：BrowsingAgent v1.0 + claude-3.5-sonnet **15.5%**，同量级最优；MiniWoB++（125 环境）：gpt-4o **40.8%**，远低于专门训练的 CC-NET（91.1%，用 RL+人类标注 BC 训练的专精模型）。
- **GAIA**（L1 验证集）：借助 GPTSwarm agent 集成 OpenHands 的 runtime/tools 基础设施，**30.2%–32.1%**（对比 AutoGPT 的 13.2%）——作者强调 GAIA 的集成难度主要来自工具整合，OpenHands 的基础设施显著简化了这一步。
- **GPQA**（diamond，198 实例）：CodeActAgent + claude-3.5-sonnet **52.0%**，接近非专家人类水平（21.9%）但仍远低于专家人类（81.3%）。
- **成本–规模消融**：同一 agent 换不同底座模型时，成本和分数都随模型档位显著变化（如 SWE-Bench Lite 上 gpt-4o-mini 仅 $0.01/实例、6.3% 解决率 vs. claude-3.5-sonnet $1.10/实例、26.0%），论文没有做严格的 cost-accuracy Pareto 分析，但数字本身可以拿来估算不同模型档位下大规模跑评测/训练环境的预算。

## 局限与疑点

- **作者自己承认的方向**（Appendix A）：长文件编辑能力弱、workflow 目前仍需大量手工搭建（未来考虑图结构自动生成）、多模态支持有限（还在用 IPython/浏览器变通而非原生支持）。
- **评测设置口径不完全对齐**：多处对比基线用的是不同 shot 数（如 HumanEvalFix 上 SWE-Agent 是 1-shot、OpenHands 是 0-shot），直接比数字容易高估/低估相对差距，论文本身也标注了这一点。
- **成本数字是"当时快照"**：所有 $ Avg. Cost 都是 2024 年中的 API 定价，模型和定价都已过时数版本，不能直接套用到今天的成本估算，只能作为"不同任务复杂度下 token/步数消耗量级"的参考。
- **沙箱安全边界描述较浅**：论文只说"securely isolated docker container"，没有展开容器逃逸防护、资源限额、网络出站控制等具体安全工程细节（对比我们更关心的 microVM/gVisor 级隔离方案，这篇论文的沙箱部分更偏"功能齐全"而非"安全加固"）。
- **镜像缓存方案规模未验证**：hash-based + generic dual-tag 的缓存策略是个人/小团队 CI 场景下的合理设计，论文没有给出大规模并发构建/多 base image 组合爆炸下的性能数据——这正是 [[sandbox-image-distribution]] 里 DSec 论文要解决的规模化问题，两者可以对照读。

## 对我们的启发

1. **"代码即动作"这套统一接口值得作为我们评测/训练沙箱的默认动作协议**：bash + IPython + 浏览器三件套覆盖了软件工程、数据分析、Web 任务的绝大部分场景，比为每个工具单独维护 JSON schema 的 function-calling 方案更省维护成本、扩展性更好——如果我们要给沙箱平台设计一个通用的 agent-runtime 交互协议，CodeAct 式的"REST API 里跑 bash/IPython/browser 三个持久化会话"是一个经过验证的最小可行设计。
2. **runtime image 的 hash-based 内容寻址 tag + generic 最新 tag 双标签方案，是构建/CI 缓存的最小可行模式**：如果我们平台目前是"每次都重建整个镜像"或"tag 只有 latest 语义不明确"，可以直接照搬这个思路作为过渡方案（低工程成本），但规模上不如 DSec 的可组合层方案，两者不是互斥，可以先上双标签缓存,再逐步往可组合层演进。
3. **集成测试里"mock LLM 调用做确定性回归测试"的做法可以搬进我们自己的 agent/沙箱平台 CI**：用 exact prompt match 缓存 LLM 响应，既能测 action 解析、sandbox 执行链路是否被意外改坏，又不用每次 PR 都烧真实 API 预算——这个模式比"跑真实模型比对最终分数"更适合做高频、低成本的回归门禁，值得写成一个具体 follow-up：调研我们现有的 agent CI 有没有类似机制，没有的话可以立项引入。
