# SWE-smith: Scaling Data for Software Engineering Agents

> 用"环境优先、任务后生"的架构 + 四种自动化 bug 合成策略，从 128 个仓库产出 50,137 个可执行 SWE 任务（比 SWE-Gym 大一个数量级），存储只要 295GB（vs 估算 50-150TB），32B 模型微调后 SWE-bench Verified 40.2%，是当时开源 SOTA。

## 元信息

Stanford University / Stanford SALT Lab / Princeton Language & Intelligence / Alibaba Qwen；arXiv 2504.21798，v1 2025-04-30，v2 2025-05-21（NeurIPS 2025 poster）；[项目主页](https://swesmith.com)、[代码](https://github.com/swe-bench/swe-smith)。对比基线：[[swe-gym]]（2,438 任务，11 仓库，真实 PR）、R2E-Gym（4,600 任务，10 仓库，合成）、SWE-bench 原始 train split（19,008 条无执行环境的结果补丁）。

## 要解决的问题

SWE agent 训练数据构造此前有两个硬约束互相拖累：① 数据规模小——现有数据集最多几千条实例、来自 11 个或更少仓库（如 [[swe-gym]] 仅 11 个仓库 2,438 条）；② 构造流程贵——人工标注动辄上百小时，且每个任务独立建执行环境导致存储爆炸（论文估算若按 SWE-bench 的"任务独立建环境"方式构造 5 万任务，需要 50-150TB 存储）。这两点共同限制了"给 SWE agent 训练造数据"这件事的可扩展性，SWE-smith 的目标就是同时解决规模和成本两个瓶颈。

## 方法

**架构反转（§2.2）**：SWE-Bench/SWE-Gym 是"任务优先"——每个任务独立配一份执行环境；SWE-smith 反过来做"环境优先、任务后生"——先给一个 Python 仓库在最新 commit 上建好唯一一份可执行环境，再在这份环境里批量合成成百上千个任务，同库任务共享环境镶像。这个反转是存储从 50-150TB 压到 295GB 的根本原因。

**环境构造（§2.1，[[repolaunch]] 可比对象）**：从 PyPI 下载量前 5,000 的包里按 GitHub star 排序筛选（剔除 <1,000 star 及全部 12 个 SWE-bench 测试仓库），用 SWE-agent + claude-3.5-sonnet 在最新 commit 上自动跑安装（限 150 步、$2 成本），要求 80% 以上测试通过，平均 $0.72/仓库、17 步、2 分钟；再人工审查安装规范（3-20 分钟/仓库，128 个仓库共 18 人工小时），最终固化为 Docker 镜像。

**任务候选生成（四种自动化策略，产出率见 Table 1）**：
1. **LM Modify**：给定一个函数，提示 LM 直接引入 bug（产出率 56.0%，17,887 条，成本 $0.38/条）。
2. **LM Rewrite**：只给函数签名 + docstring，要求 LM 重新实现（产出率 35.0%，4,173 条，成本 $3.93/条——更贵因为要生成完整实现）。
3. **Procedural Modification**：解析 AST，随机施加 13 种预定义代码变换（去掉条件分支、改操作符等，Table 8 附录），零 LM 成本（产出率 40.2%，15,641 条）。
4. **PR Mirror**：收集仓库历史 PR，用 LM 尝试在当前版本上撤销该 PR 的修改，还原出"引入 bug 前"的 PR 逆向版本（产出率 33.8%，2,344 条，成本 $5.53/条，最贵但最接近真实 SWE-bench 分布）。
5. **Combine Bugs**：把同文件/模块内的多个候选按算法聚合成更复杂的复合任务，几乎零成本（产出率 96.9%，10,092 条）。

**执行验证（零人工介入的质量门槛，[[generator-verifier-asymmetry]]）**：把候选 patch 应用到仓库，跑测试套件（单条测试限时 2 分钟），只保留"至少破坏 1 个原本通过的测试"（Fail-to-Pass，与 [[swe-gym]] 的"gold patch 通过测试数 > 原始代码"门槛同源但方向相反——SWE-smith 是反向构造 bug，SWE-Gym 是正向验证修复）。

**问题陈述生成**：把 patch diff、随机抽取的 F2P 测试源码、测试执行输出一起喂给 LM，生成 GitHub issue 风格的自然语言问题描述（Table 5 消融显示 LM 生成的效果与真实 PR 原文相当，优于固定模板）。

## 实验与结果

- **总产出与成本（Table 1）**：128 个仓库 → 50,137 个任务实例，整体产出率 50.1%，总成本 $1,360（$1,000 生成 bug、$160 自动装环境、$200 生成 1 万条 issue），折算约 $2.32-2.54/条。人工投入约 20 小时（主要是从 agent 轨迹里解析安装指令 ~7 分钟/仓库 + 写测试输出解析器 ~1 分钟/仓库）+ 18 小时环境安装审查。
- **存储对比（Table 2）**：SWE-gym 2.4k 任务/11 仓库/6TB，R2E-gym 4.6k 任务/10 仓库/4TB，**SWE-smith 50k 任务/128 仓库/295GB**——"环境优先"架构让镜像总量不随任务数线性增长。
- **模型效果（Table 3，pass@1，无推理时扩展）**：SWE-agent-LM-32B 在约 5,016 条轨迹（限每任务最多 3 条）上微调，SWE-bench Verified **40.2%**、Lite 30.7%，是当时开源模型 SOTA（对比 Claude 3.7 Sonnet 58.2%、GPT-4o+Agentless 38.8%）。轨迹采集：对 8,686 个唯一任务尝试求解，36% 解决率（6,457/17,906）。
- **同规模直接对标（§4 末）**：限定在 500 条成功轨迹（三方工作都报告过的规模）比较，SWE-smith-32B 达 28.2% Verified，比 [[swe-gym]] 高 +8.2pp、比 R2E-Gym 高 +0.7pp——控制轨迹数后，SWE-smith 的任务质量/多样性仍有边际优势，不只是规模堆量。
- **Bug 策略消融（Table 4，1,000 任务抽样，控制成功轨迹数 507 条）**：PR Mirror 训练效果最好（9.2% Verified），Procedural（8.6%）与 LM Rewrite（8.8%）具竞争力，LM Modify 最弱（5.7%）——"越接近真实 PR 分布的合成策略，训练信号质量越高"，但纯程序化、零 LM 成本的 Procedural 也能打平昂贵的 LM 策略。
- **仓库多样性 vs 单仓库特化（图5）**：固定 700 样本，训练集覆盖的仓库数从 4 增到 100，性能对数增长；反过来只用 SymPy 单仓库 700 样本微调，在 SymPy 子集上 42.4%（远高于全仓库训练的 33.3%），但泛化到其他仓库的整体性能仅微降——说明"广度覆盖"和"单域深挖"可以按需求取舍，不是非此即彼。
- **难度与解决率的关系"出人意料"（§4.1）**：专家标注的难度分档（易/中/难解决率 58.6%/41.0%/17.0%）合理，但学生模型在难度 2/4/6/8 档上的解决率（12.4%/10.8%/13.6%/12.2%）几乎不随难度单调变化，作者未给出解释。

## 局限与疑点

- 作者自陈：① 流水线以 Python 为中心，AST 解析等机制依赖 `ast` 库，迁移到其他语言需要重新实现（但架构本身语言无关）；② 出于预算和"数据集贡献"的定位，只验证了微调（rejection sampling fine-tuning），完全没有探索 RL 等训练方式对这批数据的效果。
- 18 人工小时的环境安装审查仍是硬人力成本，且只覆盖 128 个仓库（相对全网 Python 生态是很小的样本），"人工审查成本是否随仓库数线性增长"论文未讨论。
- 合成 bug 与真实 GitHub issue 的自然性差异未被系统评估——LM Modify/Procedural/PR Mirror 四种策略的效果差异（Table 4）某种程度上印证了"越像真实分布越好"，但论文没有做人工评审/图灵测试类的质量校验，只用下游训练效果反推质量。
- 难度分档与学生模型解决率无强相关这一发现没有被深入解释，如果难度打分本身不可靠，前面"专家 58.6%/41.0%/17.0%"这条难度校验结论的可信度也需要打折。
- 仅测 Python 生态里下载量靠前的成熟开源库，任务分布可能偏向工程规范、测试覆盖率高的项目，这类仓库的 bug 模式未必代表内部/私有代码库的真实故障分布。

## 对我们的启发

- **"环境优先、任务后生"是压缩存储成本的关键架构决策**：把 50-150TB 压到 295GB，靠的不是压缩算法而是"同库多任务共享一份环境镜像"这个数据模型层面的选择。我们评估自建 SWE/代码类训练环境库时，应该优先设计成"仓库级镜像 + 任务级 patch/配置叠加层"，而不是照抄 SWE-bench 式"任务独立打包"的路数，这直接决定我们 [[sandbox-image-distribution]] 需要支撑的规模级别。
- **零 LM 成本的 Procedural Modification 值得优先复用**：AST 级别的规则化代码变异（13 种预定义转换）产出率 40.2%、训练效果（8.6% Verified）逼近成本高一个量级的 LM Rewrite，是"用最低成本刷任务规模"的现成方案，我们如果要为内部代码库批量合成 bug/任务，可以先照搬这套 AST 变换规则库再逐步扩展。
- **防作弊/质量门槛可以完全不依赖 LLM-as-judge**：唯一硬门槛是"patch 必须破坏至少 1 个原本通过的测试"，用确定性的测试执行结果判定，这和 [[swe-gym]] 的"gold patch 通过数 > 原始代码"是同一思路的镜像版本（构造 bug vs 验证修复）。这类"执行式而非语义式"的过滤规则应作为我们自己做任务规模化构造时的第一道防线，成本几乎为零且难以被数据本身的噪声绕过。
- **500 条轨迹同规模对标（28.2% vs SWE-Gym 20.6% vs R2E-Gym 27.5%）说明"任务合成质量"和"任务规模"是两个独立可加的收益来源**——这提示我们评估/复现类似工作时，不能只看最终 SOTA 数字（40.2% 用了 5,016 条轨迹），控制规模后的对比才能分离出"流水线设计本身有多好"这一变量,这对我们判断要不要投入自建流水线（而非直接买数据/用现成环境）是更有参考价值的证据。
- Follow-up 建议（可转 issue）：
  1. 把 Procedural Modification 的 13 种 AST 变换规则（Table 8）整理成一份可复用的清单，评估能否直接套用到我们内部代码库做零成本任务/bug 合成的第一版原型。
  2. 深挖"环境优先"的镜像分层设计（是否用 OverlayFS/镜像 diff 层等技术进一步复用基础层），对比我们现有 [[repolaunch]] 沙箱镜像构建能力，量化能否把类似规模（128 仓库、50k 任务）的环境库压到比 295GB 更小或分发更快。
  3. 复现"同规模对标"实验方法论（固定轨迹数比较不同数据源的下游效果），作为我们评估自建数据合成流水线 vs 直接复用开源数据集时的标准评估协议。
