# HybridFlow: A Flexible and Efficient RLHF Framework

> veRL 的原始论文：单控制器（跨节点编排）+ 多控制器（节点内分布式计算）的混合编程模型，让 RLHF 数据流灵活表达、高效执行，吞吐提升 1.53×~20.57×。

## 元信息

机构：The University of Hong Kong（一作）、ByteDance / 发表时间：2024-09-28（arXiv v1），EuroSys '25 录用 / 链接：[arXiv](https://arxiv.org/abs/2409.19256) · [Code (veRL)](https://github.com/volcengine/verl) / 对比基线：DeepSpeed-Chat、OpenRLHF、NeMo-Aligner

## 要解决的问题

RLHF 的数据流比传统 RL 复杂得多：传统 RL 每个节点是一个小型神经网络（可单机跑），RLHF 里每个节点（actor/critic/reference/reward）都是一个**分布式 LLM 训练或生成程序**，节点间的边是**多对多的 resharding**。已有两类范式各有短板：
- **单控制器**（RLLib 等）：全局视角，调度灵活，但给每个分布式 accelerator 下发指令的 dispatch 开销大，无法承受 LLM 规模的分布式计算（Table 1 对比）。
- **多控制器**（DeepSpeed-Chat、OpenRLHF、NeMo-Aligner）：每个 worker 只有本地视角，通信开销低，但要在每个 worker 程序里手写点对点通信来协调不同模型的执行顺序，代码耦合、难扩展新算法、只支持固定的模型 placement。

## 方法

**核心思路**：节点间（inter-node）用单控制器，节点内（intra-node）用多控制器——两个范式按层次组合，而不是二选一。

- **Hybrid 编程模型**（§4）：`3DParallelWorker`/`FSDPWorker`/`ZeROWorker` 基类封装每个模型的分布式前后向、生成、优化器更新为原语 API（`generate_sequences`、`compute_values`、`update_actor` 等）；用 `@register` 把每个 API 绑定一个**传输协议**（transfer protocol，含 collect + distribute 函数），由单控制器协调不同并行策略模型间的多对多 resharding，但实际数据搬运只发生在 GPU 之间，不经过中心节点。8 种内置协议覆盖大多数场景（Table 3）。`ResourcePool` 类虚拟化一组 GPU，决定模型是 colocate 还是分开部署。效果：PPO 用这套 API 只需 8 行代码，改成 Safe-RLHF 加 5 行，改成 ReMax 去掉 critic 相关代码即可（Figure 6）。
- **3D-HybridEngine**（§5）：actor 模型训练和生成用不同的 3D 并行配置（生成阶段通常用更小的 TP/PP、更大的 DP，因为生成是 memory-bound 而训练是 compute-bound），但两阶段共享同一份权重副本，避免 OpenRLHF 那种"训练+生成各存一份权重"的冗余。关键创新是**新的并行分组方式**：让生成阶段的 TP/PP group 按间隔取 rank（而不是连续取），使生成权重和训练权重在每张卡上天然重叠，resharding 时只需在 micro DP group 内 all-gather，做到**零冗余显存**、通信量降到 $\frac{tp-t_gp_g}{t_gp_g \cdot tp}M$（Table 2 对比 DeepSpeed-Chat 和 vanilla 版 HybridFlow-V）。
- **Auto Device Mapping**（§6）：给定 dataflow 图、模型 workload、GPU 总数，用一个模拟器（`simu`/`auto_parallel`）枚举可行的 model placement（4 个模型时有 15 种，对应 Bell 数）与并行策略组合，选出预测端到端延迟最小的方案。复杂度是最坏情况的整数划分问题规模，但缓存同一 (模型, GPU数) 下的最优并行策略后，搜索时间控制在半小时内（Figure 16）。

系统架构：single controller 基于 Ray + RPC；训练/推理引擎支持 Megatron-LM、PyTorch FSDP、DeepSpeed；生成引擎用 vLLM（把其集中式 KVCache manager 换成分布式版本以适配多控制器范式）。全系统约 12k 行 Python（API 1.8k + 3D-HybridEngine 2.4k + Auto-Mapping 1.9k + 其余）。

## 实验与结果

**Testbed**：16 台机器 / 128×A100-80GB，NVLink 600GB/s 机内、200Gbps 机间。模型：Llama 7B/13B/34B/70B，跑 PPO/ReMax/Safe-RLHF。指标：RLHF 吞吐（tokens/sec，一次迭代的 prompt+response 总 token 数 / 迭代耗时）。

- **端到端吞吐**（§8.2，Figure 9-11）：PPO 上比 DeepSpeed-Chat/OpenRLHF/NeMo-Aligner 平均快 3.67×/3.25×/12.52×（最高 7.84×/5.93×/20.57×）；70B 模型上平均加速 9.64×，因为把 transition（训练↔生成权重切换）开销相比 DeepSpeed-Chat 和 OpenRLHF 分别降低最多 71.2%/89.1%。NeMo-Aligner 因生成引擎没有 KVCache，生成阶段能占到单次迭代时间的 81.2%。
- **可扩展性**：128 GPU 跑 7B 模型时仍比最优 baseline（OpenRLHF）快 1.68×(PPO)/1.53×(ReMax)/1.71×(Safe-RLHF)；跨模型规模的平均强扩展效率 66.8%。
- **Transition 开销**（§8.4，Figure 14）：平均降低 55.2%（11.7s），70B 模型上最高降低 89.1%（78.2s），且开销随集群规模基本恒定（对比 baseline 随规模退化）。
- **Model Placement**（§8.3）：没有一种 placement 是全局最优——16~64 GPU 时 colocate 全部模型最好；34B 模型 96~128 GPU（13B 在 96 GPU）时 split（actor+ref 一组，critic+reward 一组）最优；13B 在 128 GPU 时 standalone（每个模型各自一组设备）最优。Auto-Mapping 算法在所有测试点都能找到最优或近最优 placement。**当 critic/reward 用更大模型（13B actor + 70B critic）时**，colocate 在 64 GPU 内平均领先 44.8%，但 128 GPU 时最优方案变成把 actor/ref/reward colocate 在 64 GPU、critic 单独用另外 64 GPU。
- 论文给出三条 placement 经验（§9）：① 给 actor 分配更多 GPU 能缩短不可并行的生成延迟；② 小集群下各模型都能占满算力时 colocate 最优；③ 大集群（strong scaling）下把 actor/critic 分开部署做并行执行更好。

## 局限与疑点

- 所有吞吐对比都强制统一了 prompt/response 长度（都是 1024），是为了给不支持 continuous batching 的 baseline 一个"公平"的比较基准——这意味着论文数字**没有反映真实变长 rollout 下的吞吐**，我们不能直接拿这些倍数套用到生产工作负载。
- 消融/scaling 实验全部基于同构 A100 集群；论文承认 Auto-Mapping 假设同构 GPU，异构设备的扩展只是"可以做"，没有实验验证。
- 容错（§9）只是设计讨论（checkpoint via RPC + NCCL 错误检测），没有故障注入实验验证恢复时间或正确性。
- Resource multiplexing（GPU 时分复用/并发跑 colocate 模型）明确说"目前仍是顺序执行以避免 OOM"，细粒度共享是留给未来工作的开放问题——这正是我们平台关心的密度问题，论文本身没给答案。
- §9「From alignment to reasoning」提到可以把 reward model 换成 sandbox/reward function 做代码生成、数学推理的 RL（即今天的 agentic RL / verifiable reward），但这篇论文本身没做这个实验，只是前瞻性提了一句，后续 veRL 生态（AgentFly、AgentRL、VerlTool 等，见 [[agentic-rl-frameworks]]）才把这条线做实。

## 对我们的启发

1. **单控制器编排 + 多控制器执行的分层，直接对应我们"沙箱执行服务 + 训练循环"的架构选择**：veRL 把"谁负责协调模型间数据依赖"和"谁负责节点内分布式计算"彻底分开，我们如果要做训练/rollout 编排层，可以照抄这个分层原则——编排层（决定哪个 rollout 结果送给哪个训练 worker）不需要感知每个 worker 内部的并行细节。
2. **Auto Device Mapping 的核心洞察可以移植到我们自己的调度决策**：placement 最优解随集群规模变化（小集群 colocate、大集群拆分），且这是通过给定 workload 做延迟模拟搜索出来的，不是拍脑袋定的规则。我们的沙箱调度系统在决定"同机混部多少 rollout 沙箱 vs 独立机器"时，值得引入类似的 simulate-then-search 方法而不是写死阈值。
3. **3D-HybridEngine 的"训练/生成权重零冗余共享"是我们评估任何 rollout-training 框架时该问的具体问题**：如果我们要给客户的 RL 训练托管环境评估某个框架（veRL/AReaL/ROLL 等），"训练与生成之间切换要花多久、要不要额外显存"是一个可以直接量化对比的指标（本文给了公式和 Table 2 的对比方法），不是含糊的"支持异步"就够。
4. Follow-up（可转 issue）：
   - 精读 veRL 现在（2026）的 GitHub 实现，确认论文里 2024 年的设计（Ray+RPC 单控制器、vLLM 分布式 KVCache）是否还是当前主分支的架构，还是已经被后续 PR 大改（HybridFlow 论文距今已近 2 年，veRL 是活跃度极高的项目）。
   - 对照 [[2609.22978]]（DSec）把 veRL/Slime/OpenRLHF/Seer 归为"把执行环境当黑盒"的训练系统这一判断，具体核实 veRL 的 `ResourcePool`/传输协议抽象是否真的假设了执行环境无状态、可复用——这决定了我们的沙箱平台要不要为接入 veRL 单独设计生命周期钩子。
   - Auto Device Mapping 的模拟器（`simu`）预测延迟 vs 实测延迟的误差没有在本文报告，值得找后续论文或 issue 追问其准确性，再决定是否值得移植这套方法。
