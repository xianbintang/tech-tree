# The Llama 3 Herd of Models

> 405B 稠密 Transformer 在 16K H100 上完成预训练的完整生产记录：4D 并行 + 54 天 466 次中断仍做到 90% 有效训练时长；后训练弃用 PPO 改用 SFT→DPO 六轮迭代，并用"生成-执行-纠错"的代码执行反馈闭环造出约 100 万条自我验证过的合成 SFT 数据。

## 元信息

- 机构：Meta AI
- 发表：2024-07-23（arXiv v3 2024-11-23）
- 链接：[arXiv](https://arxiv.org/abs/2407.21783) · [Code/权重](https://github.com/meta-llama/llama3) · [项目页](https://llama.meta.com/)
- 对比基线：GPT-4、GPT-4o、Claude 3.5 Sonnet、Gemini 系列（技术报告性质，无单一主对比基线）
- 产出模型：Llama 3.1 8B / 70B / 405B（Base + Instruct），Llama Guard 3；图像/视频/语音为复合式扩展实验，未广泛发布

## 要解决的问题

这是一篇技术报告而非单点创新论文：目标是记录如何把"数据、规模、管理复杂度"三个杠杆系统性落地成一个 405B 稠密模型的完整生产流水线——包括 16K GPU 规模下如何保证训练基础设施的可靠性，以及后训练阶段如何用更简单、更稳定的流水线（SFT + 拒绝采样 + DPO）替代复杂的 PPO/RLHF 以提升可扩展性。本篇精读按阅读清单要求聚焦 §3 预训练基础设施与 §4 后训练两节。

## 方法

### §3.3 预训练基础设施：16K GPU 规模的生产级训练

**硬件与网络**：405B 模型训练用到最多 16K 张 H100（每卡 700W TDP、80GB HBM3），Meta Grand Teton 服务器（每台 8 GPU + 2 CPU，NVLink 互联），用 MAST 做全局调度。网络采用 RoCE（Arista 7800 / Minipack2 OCP 交换机）三层 Clos 拓扑：机柜内 16 GPU 全互联，192 机柜聚成 3,072 GPU 的 pod（满二分带宽、无超卖），8 个 pod 聚成 24K GPU 集群（但顶层聚合交换机有 **1:7 超卖比**）。并行方法与调度器都对网络拓扑感知，尽量减少跨 pod 通信。负载均衡上，collective 库把 2 个 GPU 间的通信拆成 16 条网络流（而非 1 条）配合 Enhanced-ECMP 按 RoCE 包头字段哈希分流；拥塞控制靠 spine 深缓冲交换机吸收瞬时拥塞，**最终在 24K GPU 集群上不依赖传统 DCQCN 也能稳定运行**。存储用 Meta 自研分布式文件系统 Tectonic（7,500 台 SSD 服务器，240PB，持续 2TB/s / 峰值 7TB/s），核心难题是 checkpoint 写入的突发尖峰会短时打满存储带宽，因此优化方向是缩短 GPU 暂停时间、提高 checkpoint 频率以减少故障后重算的损失。

**4D 并行**：组合 TP（张量并行）+ CP（上下文并行，按序列切分支持 128K 长序列）+ PP（流水线并行）+ DP（即 FSDP）。关键设计是并行维度顺序 `[TP, CP, PP, DP]`——按所需网络带宽/延迟从高到低排列，TP 限制在单机内，DP 作为最外层因为 FSDP 可以用异步预取权重/异步 reduce 梯度来容忍更高的网络延迟。16K GPU 配置下（TP=8, PP=16, DP=128, 序列长度 8,192）达到 **BF16 MFU 41%**（Table 4：8K GPU 时 43%，128K 超长序列配置时 38%）。

流水线并行做了三处针对性改造：① 用可调的连续 micro-batch 数 N（而非固定等于 PP 或总 micro-batch 数 M）解决 batch size 灵活性与通信/内存效率的权衡；② 把第一个/最后一个 stage 各减少一层 Transformer 层以平衡显存和计算（embedding 单独放第一阶段、loss 计算单独放最后阶段）；③ 用交织调度（interleaved schedule）+ 异步点对点通信降低流水线气泡比 `(PP-1)/(V*M)`。上下文并行用 all-gather 式实现（而非 ring 式）——因为 GQA 下 K/V 张量远小于 Q，all-gather 的暴露延迟相比 `O(S²)` 的 attention 计算本身可忽略，换来更灵活地支持 document mask 等不同 attention 掩码类型。数值稳定性上，FSDP 的梯度累加与 reduce-scatter 全部用 FP32。

**容错与可靠性（核心数字）**：54 天快照期内共 466 次任务中断——47 次计划内（固件升级、配置更新），419 次意外中断。意外中断中约 78% 可归因于确认或疑似的硬件问题，GPU 相关故障占全部意外中断的 58.7%（Table 5：Faulty GPU 30.1%、GPU HBM3 Memory 17.2%、Software Bug 12.9%、Network Switch/Cable 8.4%……）。尽管故障频发，**仅 3 次需要人工介入，其余全部由自动化处理**，最终实现 **>90% 的有效训练时间**（有效训练时间 = 有效训练耗时 / 总耗时）。配套工具包括 PyTorch 的 NCCL flight recorder（环形缓冲区记录 collective 元数据和调用栈，支持无需重启服务即可在线开关更细粒度的 trace）、针对 straggler（功能正常但变慢的 GPU，一个就能拖慢上千张卡）的通信优先级排查工具。另有两个有趣的环境因素观察：GPU 动态电压频率调节导致的**昼夜 1-2% 吞吐波动**（中午温度更高），以及数万张 GPU 同步启停/checkpoint 导致的数十兆瓦级电网功率瞬变，是扩展到更大集群时的持续挑战。

### §4 后训练：六轮 SFT→DPO 迭代 + 代码执行反馈合成数据

**整体流程**：每轮后训练 = 在预训练 checkpoint 上先训奖励模型（RM，基于人类偏好数据，比 Llama 2 去掉了 margin 项，偏好对里引入"编辑后回复"形成 edited > chosen > rejected 的三元排序）→ 用 RM 做拒绝采样（每个 prompt 采样 10–30 个输出选最优）生成 SFT 数据 → 标准交叉熵 SFT（lr 1e-5，8.5K–9K 步）→ DPO 对齐（lr 1e-5，β=0.1）→ 多版本模型权重平均。**共迭代六轮**，每轮用最新模型重新收集偏好标注和 SFT 数据。

**DPO 替代 PPO 的工程选择**：作者明确提到"探索过 PPO 等 on-policy 算法，但发现 DPO 对大规模模型需要更少算力、且在 IFEval 等指令遵循基准上表现更好"。DPO 的两处算法修改：① **屏蔽格式化 token 的 loss**——header/termination 等特殊 token 若参与 DPO loss，chosen/rejected 中若含相同 token 会导致目标冲突（既要提高又要降低其似然），引发尾部重复或过早终止；② **加入 0.2 系数的 NLL 正则项**（对 chosen 序列），防止 chosen 回复的 log 概率在训练中被压低，同时维持期望的生成格式。

**拒绝采样工程优化**：用 PagedAttention（动态 KV cache 分配）加速拒绝采样，但发现原生实现有 swap-out 风险，因此改为预先限定最大输出长度、仅在显存够用时才接受请求，配合跨同一 prompt 的多个输出共享 KV cache 页，整体**拒绝采样吞吐提升 2 倍以上**。

**代码执行反馈合成数据（§4.3.1，占 SFT 合成代码数据 2.7M 条中的约 100 万条）**：这是本篇精读重点关注的"代码执行反馈"机制。流程为：① 先从随机代码片段出发让模型生成多样化的编程问题描述（覆盖长尾主题）；② 让 Llama 3 生成解答，prompt 中加入"良好编程规范"要求并要求模型在注释里解释思路；③ **正确性校验分两层**：静态分析（parser + linter 捕获语法错误、未初始化变量、类型错误等）+ **单元测试生成与执行**（模型自己生成单元测试，在容器化环境中与解答一起运行，捕获运行时错误和部分语义错误）；④ 失败时把"原始问题 + 错误解答 + parser/linter/测试器的 stdout/stderr/返回码"喂回模型做迭代自我修正，模型可以选择修正代码或修改测试用例来适配代码；只有**全部检查通过的对话**才进入最终 SFT 数据集。作者观察到**约 20% 的解答最初是错的，但通过执行反馈自我纠正成功**，证明模型确实从执行反馈中学到了东西。此外还有两条补充路径：跨语言翻译合成数据（Python→PHP 等，缓解小众语言数据稀缺，用语法解析+编译+执行三重校验）、回译合成数据（代码→文档/解释→回译代码→用原始代码做参照打相似度分过滤，适用于执行反馈信息量不足的文档类任务）。

另外一个关键发现：**405B 模型用自己生成的数据自我训练没有提升甚至会掉点**（8B/70B 用更强模型蒸馏的数据则有明显提升），这正是引入外部"真值来源"（执行反馈）的直接动机——当没有更强的教师模型可用时，执行结果本身充当了验证真值。

**工具使用数据构造（§4.3.5）**：Llama 3 训练支持搜索引擎（Brave Search）、Python 解释器、Wolfram Alpha 三类核心工具，以及 zero-shot 未见工具调用（function calling）。与 RLHF/RLVR 不同，工具使用**完全靠人工标注+偏好构造，不做拒绝采样**（作者说在工具基准上拒绝采样没有带来提升）。数据构造按"先用合成数据 bootstrap 基础能力降低标注员工作量，再逐步复杂化标注协议（单轮→多轮对话→多步工具调用+数据分析）"的路径推进；多步工具使用合成数据采用类 ReAct 的"推理步骤与工具调用交替"轨迹生成方式；标注在消息级别而非对话级别进行（可以对单条工具调用/推理消息做偏好或编辑）。

## 实验与结果

- **GPU 利用率（Table 4）**：8K/16K/16K(长序列) 三档配置分别达到 BF16 MFU 43% / 41% / 38%，16K 相比 8K 的下降是因为要维持全局 batch size 恒定，每个 DP 组的 batch size 变小所致。
- **训练中断根因分布（Table 5）**：54 天 466 次中断中 GPU 相关占比最高（Faulty GPU 30.1% + HBM3 Memory 17.2% + SRAM 4.5% + System Processor 4.1% + Silent Data Corruption 1.4% + Thermal 1.4%，合计约 58.9%），软件 Bug 占 12.9%，网络交换机/线缆占 8.4%。
- **拒绝采样吞吐**：引入 PagedAttention + 限定最大输出长度 + KV cache 跨输出共享后，吞吐提升 **2 倍以上**（未给具体绝对数值）。
- **代码合成数据自我纠错率**：约 **20%** 的生成解答最初错误但在执行反馈迭代后被模型自我修正成功并纳入最终数据集。
- 文中未给出后训练六轮迭代的总 GPU 小时或美元成本（与 DeepSeek-R1 论文 Appendix B.4.4 给出完整后训练成本数字形成对照，是 Llama 3 报告在"后训练成本"维度上的披露空白）。

## 局限与疑点

- **MFU 与故障统计的适用范围**：Table 4/5 的 MFU 和中断统计都来自 405B 主模型预训练，8B/70B 模型的基础设施表现未单独披露。
- **后训练成本不透明**：六轮 SFT+RM+DPO 迭代的总算力/时间成本全文未给出任何数字，无法evaluate 后训练相对预训练的边际成本占比（对照 InstructGPT 给出的"RLHF 仅占预训练算力 1.6%"或 DeepSeek-R1 给出的具体 GPU 小时数，Llama 3 这块披露明显更弱）。
- **工具使用的规则奖励/RL 环境缺失**：全篇工具使用训练完全基于人工标注 SFT/DPO，未涉及任何基于执行结果的 RL 奖励信号或多步交互式 RL 环境，这和 DeepSeek-R1 的 Limitation（"工具调用 RL 环境留给下一版"）性质相同——2024 年 7 月的 Llama 3 与 2025 年 1 月的 DeepSeek-R1 在这一点上处于同一技术代际的空白期。
- **执行反馈的"容器化环境"细节空白**：论文只说单元测试"在容器化环境中执行"，但没有给出隔离级别、并发规模、单次执行延迟等任何工程数字——这恰好是沙箱平台视角下最想知道、但报告完全没披露的部分。
- **1:7 超卖的聚合层如何影响大规模 all-reduce 延迟**：论文提到拓扑感知调度尽量减少跨 pod 通信，但未给出超卖比对实际训练吞吐的量化影响。

## 对我们的启发

1. **"容器化环境执行单元测试 + 自我纠错"是 2024 年中期就存在的生产级执行反馈模式**，比 DeepSeek-R1 的 RLVR（2025 年初，执行反馈直接作为 RL 奖励）早半年，但停留在"SFT 数据生成阶段的静态过滤"而非"训练时的在线奖励信号"。这提示我们：如果要对接训练团队的代码执行需求，至少有两类完全不同的工作负载要支持——**离线批量数据生成**（高吞吐、可容忍分钟级延迟、海量 unit test 并发执行）和 **在线 RL rollout 内联执行**（低延迟尾部敏感、需要和 rollout/inference 阶段异步重叠）——Llama 3 只需要前者，DeepSeek-R1 两者都需要，这是沙箱产品形态上的一个关键分野点。
2. **16K/24K GPU 规模下故障是常态而非例外**（54 天 466 次中断，日均一次以上），但自动化恢复 + checkpoint 频率优化 + 拓扑感知调度能把有效训练时间做到 90%+。这组数字可以直接作为我们评估自己调度系统"容错目标"时的行业基准线——如果我们的沙箱/训练平台支持的集群规模达到类似量级，466/54≈8.6 次/天的故障率、58.7% GPU 故障占比，是值得对照的参考基线。
3. **DPO 替代 PPO 不是算法偏好问题，是工程可扩展性问题**：论文明确说 DPO "需要更少算力"且效果更好——这意味着后训练系统设计上，**是否需要在线 rollout-training 耦合的 PPO 式架构**，取决于任务是否真的需要 on-policy 更新；对可以用离线偏好数据对齐的任务（人类偏好类），DPO 这种纯离线算法大幅简化了系统架构（不需要 rollout 推理服务与训练耦合）。这对我们判断"什么场景必须上 rollout-training disaggregation（见 [[rollout-training-disaggregation]]），什么场景用更简单的离线流水线就够"是一个有价值的参照。

可以转成 issue 的 follow-up：
- 调研 Llama 3 代码执行反馈所用的"容器化环境"候选方案（Meta 内部沙箱实现细节未披露），对比我们自己沙箱的单次 unit-test 执行延迟能否满足类似规模（约 100 万条合成对话、每条若干次迭代纠错）的离线批量生成吞吐需求。
- 把"54 天 466 次中断、90% 有效训练时间"作为基准指标，补一份我们自己调度系统在类似故障率假设下的容错能力推演（checkpoint 频率、GPU 故障检测延迟、自动恢复覆盖率）。
- 调研 DPO 相比 PPO 在系统架构上具体省掉了哪些组件（是否还需要独立的 reward model 推理服务、是否需要 rollout 与 training 的资源解耦），作为我们判断"客户的后训练流水线该用哪种调度模式"的决策依据。
