# OSWorld: Benchmarking Multimodal Agents for Open-Ended Tasks in Real Computer Environments

> 第一个可控、可执行、跨 Ubuntu/Windows/macOS 的真实计算机环境，配 369 个任务和 134 个 execution-based 评测脚本，人类 72.36% 通过率对比当时最强 VLM 只有 12.24%。

## 元信息

- 机构：香港大学、CMU、Salesforce Research、University of Waterloo
- 发表：2024-04-11（arXiv v1），2024-05-30 修订 v2
- 链接：[arXiv](https://arxiv.org/abs/2404.07972) · [项目页/代码](https://os-world.github.io)
- 对比基线 / 相关基准：GAIA、Mind2Web、WebLINX、PixelHelp、MetaGUI、AitW、OmniAct、AgentBench、InterCode、MiniWoB++、WebShop、WebArena、VWebArena、WorkArena、WikiHow、AssistGUI（Table 4 逐一对比）；后续工作见 [[osworld-pro]]

## 要解决的问题

在 OSWorld 之前，多模态 agent 的评测要么是**非交互式的演示数据集**（Mind2Web、AitW 等，只给静态轨迹，非执行式评测会误判"另一条正确路径"为失败，也无法支持交互学习），要么是**限定单一应用/领域的可执行环境**（MiniWoB++、WebArena 只做网页浏览，InterCode 只做代码），无法覆盖真实计算机使用中"任意应用 + 跨应用工作流 + GUI/CLI 混合"的复杂度。作者指出这限制了任务的广度，也限制了 agent 的可扩展性——没有一个统一环境能让研究者自由定义"打开 Chrome 下载文件再用 VS Code 处理"这类跨应用任务。

## 方法

### 环境架构

OSWorld 把 agent 任务建模为 POMDP $(\mathcal{S}, \mathcal{O}, \mathcal{A}, \mathcal{T}, \mathcal{R})$：观测 $\mathcal{O}$ 是自然语言指令 + 截图/accessibility(a11y) 树（或两者组合）；动作 $\mathcal{A}$ 是 pyautogui 风格的原始鼠标键盘代码（`.click(300, 540)`、`.hotkey('ctrl','c')`），外加三个特殊动作 `WAIT`/`FAIL`/`DONE`；执行到终止动作或达到步数上限（实验中设为 15 步）为止；奖励函数 $\mathcal{R}: \mathcal{S}\times\mathcal{A}\to[0,1]$ 是 execution-based 的，在最终状态给出 0/1 或部分完成的小数分数。

系统架构（Figure 2）分三层：
- **Coordinator**：接收任务配置文件，自动拉起虚拟机实例（基于快照恢复，可高效重置环境），通过 Task Manager 初始化任务所需状态。
- **Task Manager**：负责三阶段——启动 VM、准备文件（可选，从云端下载）、执行预处理命令（可选，打开文件/调整窗口大小）；任务结束后做后处理（保存文件、重新激活窗口）并从 VM/云端取回评测所需数据。
- **Simulator**：把 agent 生成的动作代码字符串在 VM 内实际执行。

多个 VM 可以在单台宿主机上并行跑，支持无头（headless）运行，用于训练和评测的并行化。

```mermaid
flowchart LR
    Config[任务配置文件] --> Coord[Coordinator]
    Coord --> VM[VM 快照恢复 + 初始化]
    VM --> TM[Task Manager: 下载文件/打开软件/调整窗口]
    TM --> Loop[Agent 交互循环: 截图+a11y树 -> pyautogui 动作]
    Loop --> Post[后处理: 保存文件/激活窗口]
    Post --> Fetch[取回评测数据: 文件/cookie/a11y树]
    Fetch --> Eval[执行 example-wise 评测脚本]
```

### 任务与评测构造

369 个 Ubuntu 任务（另加 43 个因版权需用户自行激活的 Windows 任务）覆盖 OS、Office（LibreOffice Calc/Impress/Writer）、Daily（Chrome/VLC/Thunderbird）、Professional（VS Code/GIMP）、Workflow（跨应用）五类，其中 268 个（72.6%）单应用、101 个（27.4%）跨应用工作流、30 个（8.1%）故意设为不可行任务（依据真实用户在论坛/教程里提出的过时或臆想功能）、84 个（22.8%）整合自 NL2Bash、Mind2Web、SheetCopilot、PPTC、GAIA 等既有数据集。9 名有计算机背景的作者花约 1800 人时标注（单应用 650h、工作流 750h、复核 400h），每个任务配一份**初始状态配置**（下载文件、打开软件、调整窗口——用混合方案而非纯快照，避免每个样例占用数 GB 存储）和一份**手写的 execution-based 评测脚本**。

评测脚本由 getter（提取最终状态的关键信息，如修改后的文件、cookie 数据、a11y 树里某个元素的文本）+ evaluator（基于提取结果判定成功与否）组成，必要时接入实时爬虫（如论文引用数、博客内容这类会随时间变化的量）。全库共 134 个不重复评测函数，远超此前工作（Table 4 里 WebArena 只有 5 个、MiniWoB++ 125 个但局限在网页里）。质量控制：标注完成后由另外两名未参与该任务标注的作者作为 agent 复测，人类实验和 baseline 跑分阶段又投入 400+ 人时做四轮复查。

## 实验与结果

**人类表现（§3.4，Figure 4）**：中位完成时间 111.94 秒（WebArena 对照样本仅 35.38 秒），整体正确率 72.36%（WebArena 对照为 88%）——说明 OSWorld 的任务比纯网页任务更耗时、更难。

**模型表现（Table 5，四种输入设置 × 多个模型）**：
- A11y tree 输入：GPT-4 12.24%（当时最优）、GPT-4o 11.36%、Qwen-Max 6.87%，开源模型（Mixtral-8x7B、Llama-3-70B）仅 1.6%–3.0%。
- 纯截图输入：GPT-4V 5.26%、Gemini-Pro-Vision 5.80%，CogAgent 仅 1.11%。
- 截图 + a11y tree：GPT-4V 12.17%、GPT-4o 11.21%。
- Set-of-Mark（截图打编号框）：GPT-4V 11.77%，但相比"截图+a11y"反而略降，作者认为高分辨率+海量元素（如表格单元格）让边界框标注引入的噪声抵消了 SoM 原本的辅助效果。
- Workflow（跨应用）任务上，所有配置最高只有 6.57%（GPT-4V SoM），远低于单应用任务的 13.74%（Table 6）。
- 人类基线：72.36% overall，五个类别间方差 <5%；模型方差极大（同一设置下不同类别差距可超 20 个百分点）。

**任务难度/可行性切片（Table 6）**：按人类完成时长分 Easy（≤60s）/Medium（60–180s）/Hard（>180s），GPT-4V(SoM) 成功率从 16.78%→13.12%→4.59%，超过 180 秒的任务几乎不可能完成；人类同样下降但仍有 49.57%。不可行任务上模型反而拿到 16.67%（高于可行任务的 13.34%），但作者指出这里混有"模型轻易放弃报 FAIL"的假阳性。

**跨操作系统相关性（Table 7，§5.3）**：GPT-4V 纯截图设置在 Ubuntu 上 4.88%、迁移到 Windows 后 2.55%，两者相关系数 0.7——说明在 OSWorld/Ubuntu 上积累的方法论可以在较高置信度下迁移到 Windows。

**错误模式（§5.4）**：550 个失败样本中 >75% 存在鼠标点击不准的问题（"规划正确但执行不准"），并衍生出重复误点、环境噪声（误触发弹窗/无关软件）两类连锁错误；模型普遍缺乏专业软件的先验知识（如不知道 GIMP 里调亮度的菜单在哪）。Claude-3 Opus 虽然在 GSM8K/HumanEval 等通用基准上与 GPT-4V 相当，但在 OSWorld 上落后 2.84–7.76 个百分点，具体表现为"高层规划正确但底层 grounding 出现幻觉"（如把双击文件理解成选中而非打开）。

## 局限与疑点

- 作者自陈：评测只跑一次（无方差报告）；Windows 任务因版权需用户自行激活，规模也小得多（43 个）；纯截图历史（多张历史截图）反而不提升甚至拖累表现，说明当时 VLM 还不擅长从图像序列里提取时序信息。
- 评测脚本虽然数量多（134 个），但仍是人工逐任务定制，可复现性依赖于软件版本稳定（如 Thunderbird 账户信息解密要用到逆向工程工具），软件升级可能使评测脚本失效——这是 execution-based 评测普遍要面对的长期维护成本，论文没有讨论。
- "不可行任务"判定用的是模型主动输出 FAIL，容易被"模型习惯性早退"污染，作者自己也承认这一点会产生假阳性，与后来 [[benchmark-item-validity-audit]] 讨论的 all-fail 任务判定问题是同一类陷阱的早期版本。
- 论文完全未披露 VM 密度、冷启动时间、镜像分发方案等我们最关心的基础设施细节——只说"多个 VM 可在单机并行跑、支持 headless"，没有给出具体数字。

## 对我们的启发

- **VM 快照 + 混合式初始状态配置是"从中间状态启动任务"这一需求的一个可参考的最简方案**：论文没有用逐任务全量快照（会占用数 GB/任务），而是"启动 VM → 按需下载文件 → 执行预处理命令"三段式，这对我们做 agent 沙箱的镜像/快照策略有直接参考价值——如果多数任务只需要"打开几个文件+调整窗口"这种轻量初始化，比起为每个任务存一份完整快照，"基础镜像 + 增量脚本"的密度会高得多。
- **execution-based 评测天然要求沙箱支持"取回任意格式的产物"**（文件、浏览器 cookie、a11y 树、终端输出），这意味着执行环境需要提供比"跑完看 stdout"更丰富的取数接口；如果我们的平台要支撑 GUI/computer-use 类评测或训练，需要在沙箱侧预留文件系统快照、浏览器状态导出、UI 树抓取等标准化的"getter"通道，而不是只做进程级 IO 捕获。
- **跨操作系统相关系数 0.7**这个数字提示：如果我们需要支持多 OS（Ubuntu/Windows/macOS）的沙箱池，在方法论验证阶段可以先在成本最低的 Ubuntu 镜像上迭代，再用较小规模的 Windows/macOS 验证集做一次性验证，不需要从一开始就对每种 OS 投入等量资源。
- Follow-up 建议（可转 issue）：
  1. 调研 OSWorld 官方开源实现（`os-world.github.io` / GitHub `xlang-ai/OSWorld`）里 VM 编排具体用了什么虚拟化方案（QEMU/VMware/云虚拟机）、镜像多大、单机可并行几个实例，这是论文完全没披露、但我们最想知道的工程细节；
  2. 对照 [[osworld-pro]]（NVIDIA 的过程式评测后继工作）梳理"OSWorld → OSWorld-Pro"在任务规模、评测粒度、沙箱工程披露程度上的演进脉络，判断这条基准演化路线对我们内部 GUI agent 评测流水线有哪些可直接复用的设计。
  3. 结合 [[benchmark-item-validity-audit]] 的五分类审计方法，重新审视 OSWorld 论文里"30 个不可行任务"和"模型习惯性输出 FAIL 产生假阳性"的问题，看这类早期基准是否也存在 broken-oracle / infrastructure-limited 之类未被识别的脏数据。
