# SkillGym: Internalizing Large-Scale Human Skills into LLMs for Real-World Problem Solving

> 把人写的 agent skill 库批量转成可执行、可验证的训练环境，用 SFT 把"照着 skill 抄"内化成模型自带的过程性能力。

## 元信息

- 机构：East China Normal University（School of Computer Science and Technology）、Shanghai AI Laboratory
- 发表：2026-09-23（v1），2026-09-24（v2，当前版本）
- 链接：[arXiv](https://arxiv.org/abs/2609.27717) · [Code](https://github.com/ECNU-ICALK/SkillGym) · [Envs/Datasets](https://huggingface.co/datasets/ecnu-icalk/SkillGym) · [Model](https://huggingface.co/datasets/ecnu-icalk/SkillGym-Agent)
- 对比基线：Base Qwen3.5-35B-A3B、同规模 Agents-A1（35B，SFT + multi-teacher on-policy distillation，[[on-policy-distillation]]）、公开参考模型（Claude Sonnet 4.6 / Opus 4.8、GPT-5.4 / 5.4 Mini、GLM-5.1、Gemini 3.1 Pro、DeepSeek V4 Pro 等）

## 要解决的问题

人写的 agent skill（结构化的工作流说明：流程描述、用例、伪代码/脚本、执行约束）目前主要作为**推理时的外部指令**使用——喂给模型当 context，模型照着执行。但这些 skill 里的过程性知识（procedural competence：遵循领域工作流、长程工具协调、故障恢复、结果自检）并未被**内化**成模型自身的能力。本文的核心问题：能否把 skill 库转成可执行的训练环境，让 LLM 通过"练习 + 反馈"把这些工作流内化，而不是每次都依赖外部 skill 文本兜底？

对应到我们熟悉的 agent-skill 生态（Claude Skills、[OpenClaw/Clawhub](https://github.com/openclaw/clawhub) 这类 skill 目录），这是"skill 库 → 训练信号"这条路径上少见的系统化尝试。

## 方法

核心是一条 **skill-to-task pipeline**（详细机制见 [[skill-to-task-pipeline]]），三阶段：

1. **Skill-Aware Template Construction**：把 OpenClaw/Clawhub 上的 2,756 个 skill 组织成 12 大类、63 子类；每个子类手工设计可复用的任务模板 $\mathcal{T}_c$（任务蓝图、输入资产、文件结构、验证规范）。
2. **Environment Construction & Validation**：用模板把 skill card $K_i$ 实例化为环境 $E_i=\text{Instantiate}(K_i,\mathcal{T}_{c(i)})=(x_i,A_i,\rho_i,V_i)$（$x_i$ 任务指令、$A_i$ 输入资产、$\rho_i$ 运行时/依赖/执行约束、$V_i$ 代码化 outcome verifier，含反捷径检查）。**两级准入**：① 可行性检查（结构+端到端可执行）；② 对比 skill 依赖性测试——同一参考 agent 在"有 target skill"和"无 target skill"两种条件下各跑一次，$(r_i^+,r_i^-)=(1,0)$（有 skill 通过、无 skill 失败）才标 **Skill-Dep.**，否则若仍通过 verifier 就退而求其次标 **Verifier-Passed** 备选，两者都不满足则丢弃。
3. **Multi-Harness Trajectory Sampling**：用多组 harness-model 配置（Codex + GPT-5.4 / Nex-N2-Pro，Claude Code + DeepSeek V4 Pro / GLM-5.2）在通过准入的环境上采样轨迹，代码化 verifier 再筛一遍，只保留成功轨迹。

**训练**：只做了 **SFT**——用筛出的 8,364 条成功轨迹对 Qwen3.5-35B-A3B 做全参数监督微调（Megatron 后端 via ms-swift，16×H200）。论文明确说 verifier 给出的 outcome reward 同样可以支撑 RL，但**本文没有做 RL**，留作未来工作。这点值得注意：这不是一个新的训练算法（对比 [[on-policy-distillation]] 这种 on-policy、教师打分蒸馏），而是"离线拒绝采样 + SFT"这条更朴素的路线——胜负手在**环境/数据构造的规模和质量**，不在算法本身。

## 实验与结果

**主结果（Table 4，vs base model）**

| Harness | 指标 | Base | SkillGym-Agent | Δ |
|---|---|---|---|---|
| Claude Code | GDPval-AA v2 (Elo) | 974 | 1173 | +199 |
| Claude Code | Terminal-Bench 2.1 | 39.33% | 58.43% | +19.10pp |
| Claude Code | SkillsBench v1.1（含 skill） | 23.34% | 51.47% | +28.13pp |
| Claude Code | SkillsBench v1.1（不含 skill） | 12.13% | 26.81% | +14.68pp |
| Codex | GDPval-AA v2 (Elo) | 942 | 979 | +37 |
| Codex | Terminal-Bench 2.1 | 10.11% | 46.07% | +35.96pp |
| Codex | SkillsBench v1.1（含 skill） | 5.33% | 33.02% | +27.69pp |
| Codex | SkillsBench v1.1（不含 skill） | 0.69% | 21.08% | +20.39pp |

**关键现象**：SkillGym-Agent **不给推理时 skill** 也超过 base 模型**给了 skill** 的分数（Claude Code：26.81% vs 23.34%；Codex：21.08% vs 5.33%）——作者据此论证"skill 里的过程性知识被内化了，不再依赖外部文本注入"。

**vs 同规模基线 Agents-A1**（35B，SFT + multi-teacher on-policy distillation 训练，Claude Code harness，Table 4）：SkillGym-Agent 领先 +189 Elo（GDPval-AA v2）、+14.61pp（Terminal-Bench 2.1）、+21.18pp / +13.44pp（SkillsBench 含/不含 skill）。

**vs 公开参考模型**（Table 4）：SkillsBench v1.1（含 skill）上 51.47% 超过 Claude Sonnet 4.6（47.2%）、GPT-5.4 Mini（41.4%）、DeepSeek V4 Pro Preview（50.1%），但仍落后 Claude Opus 4.8（54.1%）、GLM-5.1（58.4%）、Gemini 3.1 Pro（60.8%）；Terminal-Bench 2.1 上与 Claude Sonnet 4.6 基本打平（58.43% vs 58.5%），但落后 Opus 4.8（74.6%）、DeepSeek-V4-Pro-0813（87.9%）不少。

**消融：教师模型影响**（Table 5，Claude Code harness）：单教师 GLM-5.2 比单教师 DeepSeek V4 Pro 全面更强（1212 Elo vs 1106；45.50% vs 28.81% SkillsBench）；DeepSeek+GLM 混合优于任一单教师（除 Elo 略低于 GLM 单独：1161 vs 1212）；All Teachers（含 Codex 侧的 GPT-5.4/Nex-N2-Pro 轨迹）在 Terminal-Bench 和 SkillsBench 上进一步提升到 58.43%/51.47%/26.81%，但 GDPval-AA v2 Elo（1173）低于 GLM 单独（1212）——**混合更多教师提升执行类任务，但会拖累专业产出类任务**，两者存在权衡，论文没给出解释这种权衡的机制。Codex 侧同样的模式：GPT+Nex 混合全面优于任一单教师。

**数据规模与质量**（Table 1/2，第 3.3、4.1、4.2 节）：
- 2,756 个准入环境（12 大类、63 子类），其中 Skill-Dep. 1,081 个（39.2%），Verifier-Passed 备选 1,675 个（60.8%）。
- 平均环境构建耗时 4.5 小时/任务。
- 48,152 次采样试验中仅 8,364 条通过 outcome verifier，**总体采样成功率 17.4%**，作者强调这说明环境本身难度不低。
- 8,364 条成功轨迹平均 49.0 次工具调用、63.4k 文本 token、35.2 交互步；最长的单条轨迹 350 次调用、342.9k token、318 步。
- 轨迹中**显式调用 target skill 的比例只有 36.8%**（跨 4 个 harness-model 配置在 17.1%–57.4% 之间浮动）——多数成功轨迹并不显式复述 skill 里的具体步骤，说明 verifier 通过率和"是否用到 skill 文本"是两回事。

## 局限与疑点

- **对比依赖性测试只是经验证据，不是必要性证明**：作者自己说"provides empirical evidence of dependency under the reference configuration, not proof that the skill is necessary for every agent"——Skill-Dep. 标签只对那一个参考 agent 配置成立，换个更强/更弱的 agent 结论可能不同。
- **只做了 SFT，没做 RL**：verifier 给的是 0/1 outcome reward，天然适合做 RL，但论文明确留作未来工作，目前的效果上限还没有和"环境/数据都一样、但换成 RL"的对照组比较过。
- **覆盖不均**：63 个子类里只有 62 个采到成功轨迹（culinary-arts 子类 1 个准入任务、0 条成功轨迹）；不同子类难度差异极大。
- **只训了一个规模（35B）**，没有和 >200B 级别模型做训练配方上的规模外推验证；论文里的"超过 Claude Sonnet 4.6/GPT-5.4 Mini/DeepSeek V4 Pro"是跟别人的 reported 分数比，不是同一套评测流水线下的严格复现（论文附注也说明 DeepSeek V4 Pro 是较早的 preview checkpoint、部分模型走 OpenHands、Gemini 走 Gemini CLI，评测 harness 不完全一致，可比性打了折扣）。
- **教师混合的权衡机制未解释**：All Teachers 在 execution 类任务（Terminal-Bench/SkillsBench）上单调变好，但在 GDPval-AA v2（专业产出类）上不单调（低于 GLM 单独教师），论文只报告现象没给出解释。

## 对我们的启发

1. **环境构造的成本结构可以直接对标**：平均 4.5 小时/任务的人工+agent 混合构建成本、17.4% 的采样通过率（48,152 次采样只留 8,364 条），这对我们评估"自建 skill-grounded 训练环境值不值"是一个可以直接拿来对比的基准量级——如果我们要做类似的 skill-to-task 流水线，光是"批量跑 reference agent 做准入校验 + 对比测试"这一步，对沙箱的**并发密度、单任务冷启动、批量隔离执行**就是硬需求（论文本身没披露并发规模和沙箱实现细节，是我们要自己填的坑）。
2. **对比 skill 依赖性测试是一个便宜的"环境质量过滤器"**，思路可以复用到我们自己筛 agentic RL 环境：不只是"跑得通就行"，而是"给不给某个关键信息/工具，结果差异显著"才算高质量样本。这比单纯看 pass/fail 更细粒度，值得在我们的环境生成/校验流水线里借鉴。
3. **"只显式调用 skill 的轨迹只占 36.8%"提醒我们**：验证器通过率不能代表"模型确实用了我们想教它的那套流程"，如果我们做类似的 SFT/RL 数据管线，光看 outcome reward 可能会漏掉"抄近道绕过工作流但结果凑巧对了"的轨迹，需要额外的过程性检查（论文里的 anti-shortcut check 是这个思路的一个具体实现，但细节没展开，值得去读代码仓库）。
4. **跟进 follow-up**：① 论文明确留了 RL 没做，作者的 GitHub/HF 已经放出全部环境和轨迹（CC BY 4.0），值得后续评估"同样环境换 RL 训练"能不能进一步提升，这对我们判断 SFT vs RL 在 skill-grounded 环境上的性价比有直接参考价值；② 沙箱/执行环境的具体实现（Docker 化、$\rho_i$ 运行时约束怎么落地）代码仓库应该有细节，值得单独去读一遍补充"工程要点与数字"部分目前的空白。
