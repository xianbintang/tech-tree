# ROLL: Reinforcement Learning Optimization for Large-Scale Learning

> 阿里出品的大规模 RL 训练库：单控制器编排 + Parallel Worker 抽象 + Rollout Scheduler 做样本级生命周期管理，在 200B+ MoE、数千 GPU 上稳定训练两周不中断，并原生支持 agentic RL 的环境/奖励 worker。

## 元信息

机构：Alibaba / 发表时间：2025-06-06（arXiv v1，16 页）/ 链接：[arXiv](https://arxiv.org/abs/2506.06122) · [Code](https://github.com/alibaba/ROLL) / 对比基线（定性讨论，无量化数字）：[[hybridflow]]（veRL）、OpenRLHF、NeMo、StreamRL、RLHFuse、ReaL、PUZZLE

## 要解决的问题

RL 训练 LLM 需要协调多个模型（Actor/Critic/Ref/Reward）与多阶段流水线（生成→推理→训练），不同用户群体对系统的诉求并不相同：手握大集群的团队要**成本、可扩展性、容错**；产品团队要**灵活路由样本到不同 reward/environment、灵活映射资源**；算法研究者要**在有限 GPU 上快速试错、细粒度控制训练流程**。已有框架（NeMo、OpenRLHF 按阶段划分独占资源；[[hybridflow]]/veRL、RLHFuse、ReaL、PUZZLE 支持 colocate；StreamRL 做训练/生成异步解耦）各自解决了部分问题，但论文认为还没有一个库同时兼顾这三类用户群体，尤其是原生支持 agentic RL 的多轮环境交互。

## 方法

**架构**（Figure 2a）：用户定义 RL dataflow 图 + 配置 → 分布式 executor/scheduler 编排 worker → AutoDeviceMapping 模块把 worker 绑定到 Resource Pool 里的资源。

核心模块：

- **Parallel Worker**：以 Ray 的 `PlacementGroup` 为基础的资源持有者，`Cluster` 表示一组担任同一角色（如 actor 训练、critic 推理）的 Worker 便于统一管理。具体类型：Actor Worker（可兼任 Actor 或 Ref）、Critic Worker、**Reward Worker**（支持 rule-based 验证、sandbox 执行、LLM-as-a-Judge 三种奖励计算方式）、**Environment Worker**（负责 agent 与环境的多轮交互）。
- **Parallel Strategy**：训练侧集成 Megatron-Core + DeepSpeed，支持 DP/PP/TP/CP/EP 5D 并行 + ZeRO2/3/offload；生成/推理侧集成 vLLM + SGLang。
- **Rollout Scheduler**：把生成阶段的调度粒度从"批"降到"单个样本"，可以按资源可用性和生成进度动态 add/abort 单条请求，是支撑 dynamic sampling（过采样后按 accuracy∈{0,1} 过滤无效梯度样本）的关键机制：① **异步 reward 计算**——完成的样本立即送去算 reward，不等整批生成完；② **动态 add request**——持续监控 worker 完成状态，按需补发新样本；③ **abort request**——一旦达到目标有效梯度样本数，主动终止其余在途生成，减少浪费。
- **Data Transfer**：复用 [[hybridflow]]（HybridFlow/veRL）提出的 Transfer Protocol 做跨阶段 resharding；`ModelUpdateGroup` 基于 NCCL 做训练→生成/推理阶段的快速参数同步，colocate 场景下也适用。
- **AutoDeviceMapping + Resource Pool**：支持用户自定义设备映射，允许单个设备被多个阶段的模型共享（而非 OpenRLHF/NeMo 那种阶段间资源互斥）；论文强调这不要求 colocate——训练与推理可以不部署在同一批设备上，仍能靠 `ModelUpdateGroup` 做参数同步。

**agentic RL 专项设计**（§3.4）：受 RAGEN 启发的可扩展多轮 agent-环境交互、按输入样本规模弹性伸缩环境（sample-wise scalable environments）、环境执行与 actor 生成异步并行（降低 GPU 空闲）。

## 实验与结果

- **RLVR 多域任务**（数学/代码/通用推理，采样比例 40/30/30%）：Qwen2.5-7B-Base 平均准确率从 0.18 升到 0.52（2.89×），数学 0.20→0.53，代码 0.13→0.41；Qwen3-30B-A3B-Base（MoE）从 0.27 升到 0.62（2.30×），训练中波动更大但无 model collapse。
- **Agentic 任务**：Sokoban（Qwen2.5-0.5B-Instruct）成功率 16.8%→26.0%；FrozenLake 验证成功率 12.9%→23.8%（Figure 5、6）。规模都很小（0.5B 模型 + 经典网格世界环境），只验证了"跑得通、有提升"，不是高难度 agentic benchmark。
- **大规模训练**：论文反复强调的旗舰结果——**200B+ 参数 MoE 模型，数千 GPU 上连续训练约两周无中断**，并配有"高效 checkpoint 与恢复机制，可用较小工程代价重启任务"。但全文**没有给出具体 GPU 数量、吞吐（tokens/s）、故障注入实验或恢复耗时的量化数字**，是一句话的规模声明，而非可复现的性能报告。
- **与基线的关系**（全部是定性描述，论文未给出吞吐对比表）：相对 [[hybridflow]]（veRL）"允许更灵活的跨阶段设备映射"；相对 OpenRLHF"支持跨阶段共享设备提升利用率"（OpenRLHF 阶段间资源互斥）；相对 NeMo"提供比其互斥资源模型更友好的映射方式"；相对 StreamRL"StreamRL 做训练/生成解耦，ROLL 提供更灵活、可选共享或独立资源分配的配置"；相对 PUZZLE"同时支持 colocation 和 disaggregation"。

## 局限与疑点

- **旗舰的"200B+、数千 GPU、两周不中断"缺乏量化支撑**：没有吞吐数字、没有具体 GPU 规模、没有故障率或平均恢复时间，无法评估这个容错机制在实际生产中的可靠性边界，只能当作"工程上可行"的存在性证明。
- **与基线的比较全部停留在特性列表层面**：不像 [[hybridflow]] 论文那样给出 128×A100 下 1.53×~20.57× 的实测吞吐对比，ROLL 论文没有和 veRL/OpenRLHF/StreamRL 跑同一 benchmark 的直接数字对比，读者无法判断"更灵活的设备映射"是否真的带来了更好的端到端效率。
- **agentic 实验规模偏小**：Sokoban/FrozenLake 是经典网格世界、模型只有 0.5B，与"多轮 agentic 场景需要处理慢环境、稀疏奖励、复杂工具调用"的生产场景差距较大，不能验证 Environment Worker 在真实复杂环境（如代码沙箱、浏览器）下的表现。
- Dynamic sampling 的 abort/add request 机制描述停留在设计层面，没有给出它相对"整批粒度调度"的具体吞吐提升数字（对比之下 [[async-rl-training]] 笔记里 AReaL 给出了 interruptible generation 贡献 12%–17% 生成吞吐这类量化拆解）。
- 论文本身没有 Limitations 一节的详细讨论，只在结论里笼统提到"架构可能仍需针对特定领域任务优化""未来可以改进 dynamic sampling 的过滤效率"，都是方向性表述，没有具体指出当前实现的已知短板。

## 对我们的启发

1. **样本级 Rollout Scheduler 的 add/abort 机制值得对照我们自己的沙箱调度器**：ROLL 把"一批 prompt 的生成"拆到单个请求粒度管理，配合 dynamic sampling 主动放弃已经不需要的在途生成（abort）——这跟我们平台做抢占式调度、及时回收无效沙箱资源的诉求是同一类问题，可以参考它"达到目标有效样本数就主动终止其余生成"的策略,而不是等整批完成再统一回收。
2. **"不要求 colocate 也能做资源共享"的设计取舍要具体验证**：ROLL 强调 AutoDeviceMapping 允许训练/生成不部署在同一批设备上仍可用 `ModelUpdateGroup` 同步参数，这与 [[hybridflow]] 的 3D-HybridEngine（靠共享同一份权重做零冗余 resharding）走的是不同技术路线；两者对我们"要不要在同一沙箱节点上混部训练和 rollout worker"这个调度决策给出了两种可行方案，但 ROLL 论文没给出这两种模式的吞吐对比，值得跑一次自己的 benchmark 再下结论。
3. **"数千 GPU 跑两周不中断"这类容错声明不能直接采信为生产可用性证据**：论文没给故障率、恢复时间、checkpoint 频率的任何数字，我们评估任何号称"大规模容错"的训练框架时，应该把这类没有量化支撑的规模声明列为需要自行验证的假设，而不是可以直接采纳的结论。
4. Follow-up（可转 issue）：
   - 读 ROLL 的 GitHub 仓库（examples 目录下的 `rlvr_config.yaml`），核实 Rollout Scheduler 的 abort/add 机制具体如何和资源调度器交互，看能否移植其接口设计到我们自己的沙箱调度层。
   - 找 ROLL 和 [[hybridflow]]/veRL 的直接吞吐对比数字（若官方后续发了 benchmark 报告或社区有独立评测），补全本文缺失的量化对比。
   - 追踪 ROLL 的 Environment Worker 是否已经支持接入类似代码沙箱这样的复杂、慢速、有状态环境，而不只是 Sokoban/FrozenLake 这类轻量网格世界。
