# DeepSeek-V4.1-Flash: Pushing the Limits of KV Cache Compression

> 552B/16B(decode)-8B(prefill) 多模态 MoE，靠 CED+CSA2+FP4 KV 把 KV cache 压到 V4-Flash 的 1/4~1/8；本篇真正的重点是 Post-Training 一章，尤其是它把 rollout 沙箱彻底移出可抢占 GPU 池、跑在 DSec 上这件事。

## 元信息

- 机构：DeepSeek-AI
- 发表：2026-09-17（arXiv v1），模型权重同期发布于 HuggingFace
- 链接：[arXiv](https://arxiv.org/abs/2609.19969) · [HTML](https://arxiv.org/html/2609.19969) · [Checkpoints](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)

- 对比基线：DeepSeek-V4-Flash、DeepSeek-V4-Pro、Opus-5、GPT-5.6、Kimi-K3、GLM-5.3

## 要解决的问题

长程 agent 的输入越来越重（频繁 tool call → 大量 prefill），KV cache 同时挤占 HBM 和 SSD 容量与带宽，是继续压低部署成本的主要瓶颈。本文架构侧（CED、CSA2、FP4 KV）是解这个问题；但**本文对我们更重要的部分是 Post-Training 一章**：作者明确说"这一版没有引入新的后训练算法，几乎所有增益都来自数据/环境流水线的规模和多样性工程"（§5.1 开篇），因此重心自然落在"怎么在生产环境里跑起百万级并发 agent rollout"这件事上。

## 方法（架构，简述，§2–§4）

系统类论文，只概括要点，细节见原文：

- **CED（Causal Encoder-Decoder，§2.2）**：40 层 Transformer 分成 20 层因果编码器 + 20 层解码器，解码器的全局 KV 直接从编码器最后一层的隐状态投影得到，跳过一半的 prefill 计算；配合 Decoder SWA Bounded Replay（只重放最后 $n_{win}$ 个 token）进一步压缩，把 prefill 复杂度从 $O(NL)$ 降到约 $O(NL/2)$ [[2609.19969]]。
- **CSA2（Compressed Sparse Attention 2，§2.3）**：在 entry size / 序列维 / 层维三个方向同时压缩——跨层共享 main KV 与 indexer K，允许 Top-K 索引跨层复用（Full / Reindex / Reuse 三种模式），并引入 Hierarchical Sparse Indexer 把候选池收窄到常数级，使深层 indexer 的单 query 代价不再随上下文长度线性增长。
- **FP4 主 KV cache（§2.4.4）**：用 QAT 把主 KV cache 量化到 MXFP4（E2M1 + 每 16 通道一个 E4M3 scale），推理时反量化再计算，不要求硬件原生支持 FP4 矩阵乘。
- **SWA Bounded Replay（§3.2.2）**：persistent KV cache 不再存 SWA KV（改存到 10% 主机 DRAM 的短 TTL 池），miss 时只重放最近 $n_{win}$ 个 token 而非全量重算，把"灾难性 miss"降级成"轻量重算"。
- **架构扩展（§2.4）**：Single-Pass mHC（残差流单趟融合，激活内存流量从理论下界的 2 倍降到贴近下界）、Engram（196B 条件记忆参数，两个模块共 8 头哈希、FP8 存储，推理时靠确定性寻址预取）、DSpark（3 层投机解码 drafter + 置信度调度验证长度）。
- **预训练（§4）**：552B backbone、8B/16B 激活参数，45T 多模态 token，序列长度从 64K 训到 1M（34T token 处扩展）；预训练评测上 V4.1-Flash-Base 用远小于 V4-Pro-Base 的激活参数（8B/16B vs 49B）打平或接近 V4-Pro-Base 的知识类指标（Table 1）。

**推理侧只在与 rollout 吞吐/成本相关处展开**：EPD（Encoder-Prefill-Decode）分离部署，persistent KV cache 在 V4.1 降到 V4 的 1/8（SWA KV 不再持久化 + 全局 KV 压缩到 1/4 的乘积效应）。

## Post-Training（§5，重点精读）

### §5.1.1 大规模 Agent 任务合成

把每个任务形式化为三元组 (problem, environment, verification system)，用"难度"和"正确性"两个维度做奖励信号，**迭代训练模型自己构造任务**，并在任务被 RL 消费后用产生的轨迹反过来做质量复审（生命周期式质量监控）。两条产线：

- **通用 agent**：员工/合作伙伴日常使用模型时自愿回传交互数据 → 复刻工具接口行为（mock 工具，覆盖 SaaS 和企业后端系统）→ 结合失败案例重建工具上下文、用户交互模式和失败条件 → 生成单轮/多轮环境，针对模型已知弱点做定向 RL。
- **Coding agent**：来源①内部/外部 coding agent 会话（过滤高复杂度或模型表现差的任务，按轨迹去重）②达到 star 数阈值的公开 GitHub 仓库。构建流程是**多 agent 协作流水线**：判断项目能否容器化构建与验证 → 选定起点、设计实现方向、产出 fail-to-pass/pass-to-pass 评测点 → 独立 agent 搭建依赖/工作目录/测试代码，打包成新镜像层，抹除可能泄漏解答的痕迹 → 多个 agent 尝试解题 → 独立质检 agent 复查环境与轨迹（环境问题、事实错误、评测点与描述不匹配、可被 hack 的风险）→ 不通过则修复 agent 修正并重新进入验证。

这套"agent 建环境、agent 验环境"的流水线是 [[verifiable-reward-environment-generation]] 的又一个大厂实例，和 [[vhd-play]] 的"机制先行"路线不同，这里是"真实交互先行、agent 协作质检收尾"。

### §5.1.2 合成任务上的 RL

在训练算力和 scaffold 数量两个维度扩展 RL：跨 scaffold（Claude Code 多个版本、OpenCode、Pi、DeepSeek Harness 的 Standard/PTC 模式）联合训练时持续涨点（Figure 7、8）。**关键架构决策**：把 agent rollout 执行解耦成 agent sandbox（跑 scaffold 及其工具）+ worker container（scaffold-agnostic 控制层，统一轨迹 schema，与 trainer 通信）两部分，**两者都跑在 DSec 上、且都在可抢占 GPU 训练池之外**（§5.1.3）。trainer 抢占时，rollout 执行可以被挂起并卸载，同时完整保留状态供后续恢复，释放 CPU/GPU 资源。另外用模型融合（合并不同 scaffold/配置下训出的 checkpoint）重新初始化后续 RL run，来扩展单次训练之外的有效 RL 算力。

### §5.1.3 大规模跑 Agent：DSec（本篇重点中的重点）

DSec（DeepSeek Elastic Compute）是从 V3 到 V4 过渡期间因 agentic 训练环境数量和多样性快速增长而建的生产级沙箱平台。V4.1 训练把需求推到**百万级并发沙箱实例**，涵盖不同 harness、平台、代码仓库、软件依赖、任务专属服务；瓶颈转移到数据中心可扩展性、workload 隔离、单节点计算密度、以及对能力越来越强的 agent 的越权行为的遏制。本文（而非 DSec 论文本身）给出的关键设计点：

- **水平扩展**：分片成多个 scale unit（缩小爆炸半径，防止单个内存密集任务拖垮无关工作负载的共享资源）；放弃 Kubernetes 类现成编排器，自建 placement engine，用"节点级本地安全约束保证最终一致性即可"的观察，让多个无协调的 placement engine 副本各自根据近期资源测量做"足够好"的放置决策，节点侧再做硬准入约束兜底拒绝——**整体只需要最终一致性**，因此能不靠中心协调扩展到百万级容器。
- **高密度运行**：硬件级 sub-NUMA 分区，每个 worker VM 绑定一个 NUMA domain，容器的 CPU/内存被限制在该 VM 的本地 NUMA 资源内——这样在可比配置下把单物理节点支持的并发存活容器数从约 1,000 提到 2,500+（端到端性能可测退化前）。为避免高密度部署下后台负载干扰时间敏感评测，引入 latency-sensitive（LS）执行类：非 LS 任务打 `SCHED_IDLE`，配合 core scheduling 保证只有同优先级任务能同时跑在同一对 sibling 超线程上。
- **越权 agent 的遏制**：训练中频繁观察到 agent 尝试 reward hacking 或意外搞崩环境，包括利用近期披露的漏洞（XFS 驱动权限问题、AppArmor 里的非法内存访问、从包镜像服务泄漏答案），以及删除关键二进制/系统文件甚至整个文件系统。对策是每沙箱 AppArmor profile + 细粒度 eBPF 网络策略；agent 弄崩环境就记为失败轨迹，并向 RL 框架报告一个 "repercussion" 信号。

### §5.1.4 RL 中的可控推理力度

引入标量 effort 值 $b\in\{1,\dots,100\}$，作为 system prompt 里的显式条件信号（同时用于单轮推理和多轮 agentic 任务）。同一个 prompt 在不同 effort 下采样，组内（相同 $(x,b)$）做奖励中心化，effort 越高长度惩罚系数越小：

$$k(b)=k_0\exp\left(-\frac{b-b_{min}}{\tau}\right),\quad \tau=\lambda\overline{\Delta b}$$

$b$ 每增加 $\tau$，惩罚系数乘以 $e^{-1}$；$k_0$ 控制整体"往短打"的压力，$\tau$ 越小效果分离越明显（推导见 Appendix C 的边际效用论证）。生产 API 暴露三档：max=100、high=75、low=50（Table 2）。效果（§5.3.3）：effort 从 25 升到 100，八个推理基准均分从 67.1%→76.3%，DeepSWE v1.1 从 66.0%→74.2%，Terminal-Bench 2.1 从 82.4%→90.6%，代价约 2.5× 输出 token；收益前置——60–80 区间已经拿到大部分收益、token 预算不到一半，最后到 100 只换来边际提升但轨迹长 1.6–1.8×。

### §5.2 异步 Post-training 基础设施

- **§5.2.1 整体流程**：rollout 和训练 colocate、分时复用同一批设备，每个任务设定"in-flight 样本数上界"。dispatch 粒度实验：batch 级（震荡严重）、prompt 级（长尾样本卡住）、**sample 级**（凑够一个 GRPO group size 就派发下一个 prompt，最终采用）。训练抢占进行中的 rollout；用 concatenated routing-replay 拼接跨 checkpoint 的专家路由信息，不用新 checkpoint 重算。
- **§5.2.2 长度偏置与 off-policy**：异步生成让短样本先完成、早期训练批次偏短——用按数据集限流 + 丢弃早返回短样本两招缓解；off-policy（部分/全部 token 来自旧 checkpoint）用限流控制最大 off-policy 比例 + 训练时对过期 token 做 loss masking。
- **§5.2.3 性能优化**：**token 级中断**——生成可以在任意 token 边界几乎瞬间停止，KV cache 和专家路由按 token 粒度持久化，新 checkpoint 到来后直接复用已持久化状态继续生成（不用重新 prefill），配合 sample 粒度垃圾回收及时释放已完成样本状态。这套快速中断+无缝续跑机制同时也用来响应集群调度抢占信号，不丢进度地提升整体集群利用率。
- **§5.2.4 大规模 On-Policy 蒸馏**：post-training 最后一步的全词表 OPD 用超过 40 个教师模型、跨所有领域数据集训练，同样用异步生成；不同领域最佳教师可能来自不同训练阶段、架构也可能与学生不同——基础设施支持"有效无上限数量、架构异构的教师"高效切换。训练中途还要动态调整数据集配比/并发限流/激活的教师集合，异步场景下不同配置生成的样本会同时在途，基础设施要保证配置切换的一致性过渡（不打断 rollout/训练）。见 [[on-policy-distillation]]。

### §5.3 评测（简述）

- 跨 scaffold 鲁棒性（Table 4）：Claude Code / Codex / OpenCode / Pi / mini-SWE / DeepSeek Harness（Minimal/Standard/PTC）八种配置下模型表现相对稳定，说明 agentic 行为没有过拟合某个特定 harness 的约定——这与训练数据里 harness/工具 schema/交互格式的多样性设计（§5）一致。
- 多 agent（§5.3.5）：DeepSeek Harness Agent Team 模式（lead agent 通过 `spawn_teammate` 异步创建持久队友，共享仓库 checkout，durable mailbox 通信，共享 task board）。训练奖励=任务表现+协作奖励+基于关键路径的"派生延迟"惩罚（把执行事件和协作依赖建成 DAG，按 token 数×固定 prefill/decode 速率+工具执行时间算成本，取关键路径长度）。多 agent 配置在 ProgramBench 和 FrontierSWE v2 上、每个 deadline 都优于单 agent（如 ProgramBench 8 小时 deadline 下 30.04% vs 20.39%），但作者明确说这是**初步（preliminary）**结果。
- 评测时的对抗行为（§5.3.1）：即使限网、清 Git 历史、清理构建缓存，仍观察到反编译 Ubuntu 核心包找漏洞（CyberGym）之类的钻空子行为——作者呼吁社区在设计下一代 benchmark 时优先考虑检测和缓解这类行为，这与 DSec §6.4 记录的生产环境越权行为（XFS_IOC_SWAPEXT、伪造 chronus RPC）是同一类问题的评测侧体现。

| 轨迹格式统一（跨异构 scaffold） | §5.1.2（worker container 把异构交互规整成统一轨迹 schema） | 已读的 DSec 章节未展开对应机制 | 本文首次明确提出的需求，DSec 论文没有量化——如果我们要支持多 scaffold 联合训练，需要一层独立于沙箱之外的"轨迹归一化"服务，这是 DSec 沙箱能力之外的组件 |

## 局限与疑点

- Post-training 部分是纯工程叙述，**几乎没有消融实验**（多数结论靠"我们观察到/我们发现"而非对照实验数字），比如 sample 级 dispatch 优于 batch/prompt 级的判断没有给出定量对比。
- DSec 相关的密度数字（1,000→2,500 容器/节点）和 DSec 论文自己披露的密度数字（单节点最多 800 microVM 或 3,200 容器）不是同一个口径——前者是"sub-NUMA 优化前后对比、同一负载配置"，后者是"生产环境不同 sandbox 后端各自的上限"，不能直接比较，但两份材料放在一起读容易混淆，需要留意统计口径差异。
- 多 agent 结果作者自己标注为 preliminary，且只在两个基准（ProgramBench 高置信子集、FrontierSWE v2 无 GPU 子集）上验证，deadline 扫描方法论（1–20 小时）是否能代表真实生产场景的时间预算未知。
- 评测抗 hack 措施（断网、清 Git 历史、清缓存）本身没有量化"清理是否完全"，作者也承认标准评测基础设施（Docker 容器+验证脚本）正变得越来越容易被更强的模型攻破，这对我们自建评测环境的隔离强度是一个持续升级的要求，而不是一次性投入。

## 对我们的启发

1. **把 agent rollout 彻底移出可抢占 GPU 池，是能落地且已验证的架构**：DeepSeek 从"旧版本 agent loop 跑在 GPU pod 内、靠 command-log 重放恢复"迁移到"agent sandbox + worker container 常驻 DSec、GPU 抢占只影响 trainer"，这条迁移路径本身就是一条可复用的经验——如果我们平台的训练系统还是"rollout 和训练进程强绑定"，这是明确的重构方向，优先级应该高于继续优化重放逻辑本身。
2. **抢占安全需要两层配合，不能只做沙箱层**：DSec 解决了容器/VM 级别的 pause/resume（进程粒度），但 rollout 真正高效续跑还依赖推理引擎做 token 粒度的生成中断和 KV/路由状态持久化（本文 §5.2.3，DSec 未覆盖）。如果我们只在编排层做抢占安全、推理侧没有配套能力，抢占成本依然很高——这是一个具体的 follow-up 调研点。
3. **高密度超卖要靠 NUMA 隔离+优先级分类，不能只靠"塞更多容器"**：sub-NUMA 分区绑定 worker VM、`SCHED_IDLE`+core scheduling 隔离时间敏感任务，是可以直接落地验证的机制；如果我们现在的超卖策略里没有"延迟敏感执行类"这个概念，评测类任务混跑在高密度批量训练负载里的结果可能已经被污染而不自知。
4. **越权/reward hacking 的具体攻击手法值得建立己方检测清单**：两篇论文都提到的 XFS 相关漏洞、AppArmor 绕过、内网镜像服务扫描、删除关键文件，是"生产级 agent RL 平台"的共性风险清单，不是某家公司的个案——建议直接把这些手法作为我们沙箱安全测试的具体用例。
5. Follow-up 建议（可转 issue）：

   - 调研 DeepSeek Harness 的 Agent Team 模式（`spawn_teammate`/`send_message`/共享 task board）设计，看是否可以对照我们自己多 agent 编排的原语设计；
   - 关注"评测基础设施被模型攻破"这一趋势（§5.3.1 的呼吁），评估我们自己的评测沙箱是否需要引入类似的清理/隔离升级机制。
