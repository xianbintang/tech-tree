# 嵌套虚拟化

## 一句话定义

在一个已经是 VM 的环境（*L₁*，从 host hypervisor *L₀* 租来）内部再跑一层 VM（*L₂*），常见需求是"在 IaaS 云租来的 VM 里再跑一个能承载安全容器的 guest hypervisor"；核心难点是内存虚拟化——从 *L₂* 虚拟地址到 *L₀* 物理地址需要三级地址转换，而硬件（Intel EPT/AMD NPT）只支持两级页表，多出来的一级要么靠 *L₁* 软件维护影子页表（SPT-on-EPT），要么靠 *L₀* 把两级 EPT 压缩合并（EPT-on-EPT，业界标准做法）[[2023-huang-pvm]]。

## 为什么对我们重要

这是 dsec-refs 阅读清单 B 类"隔离运行时/microVM"里母论文 [[2609.22978]]（DSec）§9 点名的第三种隔离范式（与 microVM、VM 套容器并列），代表一种和 [[microvm-sandbox]] 不同的能力边界：**它是为"没有 host hypervisor 控制权"这个约束设计的**——当沙箱平台需要跑在租来的公有云 VM 上而非自己控制的裸机时，Firecracker 式 microVM 通常需要宿主开放 `/dev/kvm` 或 root 权限,拿不到时嵌套虚拟化（尤其是 [[pvm]] 这类不依赖硬件支持、对 *L₀* 透明的软件方案）是候选出路。但要注意 DSec 自己的评测态度：§8.1 明确写"排除嵌套虚拟化，让 microVM 直接跑裸机"，把嵌套虚拟化视为需要主动规避的额外开销来源,而非自身架构会采用的路线。

## 核心机制 / 主要变体

- **三级地址转换的根本约束**：单层虚拟化只需要 GVA→GPA（guest page table）→HPA（EPT/NPT）两级；嵌套虚拟化需要 *L₂* GVA → *L₂* GPA（*L₂* 自己的页表）→ *L₁* GPA（多出来的一级）→ *L₀* HPA 三级，但硬件 MMU 只支持注册两张页表,必须用软件手段压缩或维护第三级 [[2023-huang-pvm]]。
- **SPT-on-EPT**（软件影子页表方案）：*L₁* 用软件维护一张影子页表（SPT12），把 *L₂* GVA 直接映射到 *L₁* GPA,*L₀* 仍用硬件 EPT 做最后一级转换。代价极高——*L₂* 的每次缺页/页表更新都要先陷入 *L₀*、再转发给 *L₁* 处理,最坏情况（n 级页表）一次缺页触发 `4n+8` 次 world switch、`2n+4` 次陷入 *L₀* [[2023-huang-pvm]]。
- **EPT-on-EPT**（业界标准做法，KVM 默认）：*L₂* 自由更新自己的页表（不陷入 *L₀*）,*L₁* 维护 EPT12（*L₂* GPA→*L₁* GPA）,*L₀* 把 EPT01 与 EPT12 压缩合并成 EPT02（*L₂* GPA→HPA）直接给硬件用。比 SPT-on-EPT 更高效（一次缺页 `2n+6` 次 world switch、`n+3` 次陷入 *L₀*）,但仍然重度依赖 *L₀*：4 级页表下最多 14 次 world switch、7 次陷入 *L₀*,且需要 *L₀* 深度参与 VMCS/EPT 维护,增大 host hypervisor 复杂度与攻击面 [[2023-huang-pvm]]。
- **PVM-on-EPT**（[[pvm]] 提出的第三条路）：把 *L₂* 的内存虚拟化完全收敛在 *L₁* 内部处理,*L₀* 只需要像对待普通 VM 一样维护一层 EPT、对嵌套的存在无感知。切换次数只略少于 EPT-on-EPT（`2n+4` vs `2n+6`）,但**关键差异是单次 world switch 成本降低一个数量级**（0.179μs vs 1.3μs）,因为切换收敛在同一特权环境内、不经过硬件 root/non-root 模式切换 [[2023-huang-pvm]]。这是一个可迁移的通用洞察:优化"陷入-处理"路径时,"减少次数"和"降低单次成本"是两个独立的杠杆,后者的天花板可能更高。

## 工程要点与数字

- World switch 成本对比：单层硬件辅助虚拟化 0.105μs,嵌套虚拟化 EPT-on-EPT 1.3μs（贵一个数量级）,PVM-on-EPT 0.179μs（把这个数量级的代价基本收回）[[2023-huang-pvm]]。
- 内存密集型并发工作负载下,嵌套虚拟化（EPT-on-EPT）相比单层虚拟化最多慢两个数量级；PVM-on-EPT 把这个差距收窄到与单层虚拟化同一数量级 [[2023-huang-pvm]]。
- 生产验证：[[pvm]] 已在阿里云日均承载 10万+ 安全容器、40万+ vCPU,证明纯软件、不依赖硬件嵌套虚拟化支持的方案可以在生产规模下替代裸机实例 [[2023-huang-pvm]]。
- 兼容性约束：许多公有云不支持或严格限制租户 VM 内的硬件嵌套虚拟化,且与 AMD SEV、Intel TDX 等机密计算特性不兼容——这是 PVM 选择"不依赖硬件支持、对 *L₀* 透明"这条设计路线的直接动机 [[2023-huang-pvm]]。

## 争议与矛盾

- **嵌套虚拟化本身是否值得采用,DSec 与 PVM 立场不同**：PVM 论文证明了嵌套虚拟化经过软件优化可以在生产环境下接近单层虚拟化性能;但 DSec（[[2609.22978]] §8.1）在自己的评测设计里明确"排除嵌套虚拟化,microVM 直接跑裸机",把嵌套虚拟化当作需要主动规避的开销来源。两者并不矛盾——DSec 有能力控制裸机,不需要在"VM 里再跑 VM"这个约束下工作,所以没有采用嵌套虚拟化的必要;但这提示嵌套虚拟化的适用前提是"host 没有 hypervisor 控制权",而不是普适的隔离方案 [[2023-huang-pvm]]。

## 开放问题

- PVM 是唯一一篇精读的嵌套虚拟化生产系统论文,论文提到的 Turtles、NestCloud、SVT 等早期/同期学术方案（§6 Related Work）尚未精读,这些方案的具体取舍与 PVM 的对比留待后续。
- 嵌套虚拟化与 [[microvm-sandbox]]、[[kata-containers]] 等路线在同一评测环境、同一工作负载下的直接对比数据缺失,目前只能分别参照各自论文的生产数字。
- 我们自己的沙箱平台是否存在"需要在无 host 权限的租用 VM 里提供强隔离"的实际场景,尚未评估;如果不存在,嵌套虚拟化对我们可能只是背景知识而非可落地选项。
