# 过程式评测（Process-based Evaluation）

## 一句话定义

不只看任务最终结果，而是把长程任务拆成有顺序依赖的子目标/步骤，逐步判定是否推进、是否完成，从而定位智能体具体在哪个环节失败的评测范式；思路源自数学领域的 PRM-800k、ProcessBench，[[osworld-pro]] 把它系统化地搬到了 [[computer-use-agent]] 评测上 [[2609.24890]]。

## 为什么对我们重要

结果导向评测（只看最终产物）无法区分"差一点成功"和"完全没做"，也测不出中间过程里的低效和 reward hacking。过程式评测给出的子目标级信号，天然对应我们关心的"可验证奖励的工程实现"——如果能把这类信号做成训练时的 process reward，直接影响 RL 训练系统的设计（需要更高频、更细粒度的打分基础设施）。

## 核心机制 / 主要变体

- 与数学领域 PRM-800k / ProcessBench 的差异：数学推理步骤通常是线性单一路径，而 CUA 任务开放度更高（同一目标可以有多种操作路径），因此 OSWorld-Pro 采用"子目标"而非"步骤"作为过程监督的最小单位，且子目标之间保留**顺序依赖**（区别于一般 rubric 里彼此独立的条目）[[2609.24890]]。
- 落地方式是 LLM-Judge：给定完整轨迹，判定每一步 Target（打向哪个子目标）→ Feasible（该子目标当前是否可行）→ Progress（是否推进）→ Complete（是否完成），后一层只在前一层判定正确时才计入，形成依赖链评估 [[2609.24890]]。
- LLM-Judge 在客观性更强的维度（Target、Complete）上能力接近人类，但在主观性更强的维度（Feasible、Progress）上明显偏弱——这两个维度本身人工标注者之间的一致性也更低（Cohen's κ 0.847/0.869 vs 0.940/0.987），说明差距部分来自任务本身的模糊性，不完全是模型能力问题 [[2609.24890]]。

## 工程要点与数字

- 过程式评测的实现成本显著高于结果导向评测：需要人工标注 67000+ 条子目标级判定（>5000 人时），或者用能处理长轨迹+多图输入的 LLM 做评委（当前只有 OpenAI GPT-5.6 系列能承受单次请求的 payload 规模）[[2609.24890]]。
- 推理力度（reasoning effort）越高，LLM-Judge 对"任务可行性"的判定越容易产生系统性偏差（倾向于低估不可行的比例），这是过程式 LLM-Judge 设计中一个具体的坑 [[2609.24890]]。

## 开放问题

- 过程式评测信号能否高效接入 RL 训练循环作为 process reward，对训练吞吐/成本的具体影响如何，[[osworld-pro]] 只是提出方向未做实验，是否可行、代价多大是开放问题 [[2609.24890]]。
- LLM-Judge 在 Feasibility 判定上"推理力度越高越低估不可行"的现象，是否是通用的 LLM-as-judge 陷阱（不限于 CUA 场景），值得后续验证。

## 相关概念

[[osworld-pro]]、[[computer-use-agent]]、[[trace-mined-behavior-benchmark]]（都是"不只看最终结果"的评测范式，但切法不同：前者逐子目标打分完整轨迹，后者只在单个决策点切一刀评测下一步响应，不需要重放完整轨迹）
