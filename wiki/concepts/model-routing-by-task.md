# 按任务路由到不同模型

## 一句话定义

在推理时按任务类型/复杂度/延迟要求把请求分派给不同规格的模型或 agent（而不是所有任务都过同一个大模型），是 agent 系统里在推理时间做的调度决策，用来平衡成本、延迟与效果。

## 为什么对我们重要

这本质上是一个**调度问题**：把异构的请求（规划 vs 批量代码生成 vs 简单意图分类）分派到异构的执行资源（大推理模型 vs 高吞吐模型 vs 便宜模型）。这和我们平台在调度系统里做的"任务分类 → 资源分派"是同构的，只是发生在推理服务层而不是训练/沙箱资源层。也和训练侧的 [[category-aware-expert-training]]（按类别拆专家训练）在思路上呼应——一个是训练时间的策略分化，一个是推理时间的模型选择，都是"不要用一个模型/策略应付所有类别"的具体实例。

## 核心机制 / 主要变体

- **按 agent 角色配置不同模型**：如 OpenCode 的 `opencode.json` 里给 `plan`（规划/架构分析）和 `build`（代码生成）分别指定不同的 Bedrock 模型，切换只改配置字符串 [[2026-09-26-amazon-bedrock-open-weight-coding-agent]]。
- **路由器架构（router architecture）**：意图分类 → 低成本模型；代码生成 → 中层开放权重模型；复杂推理 → 高阶推理模型，三级分派 [[2026-09-26-amazon-bedrock-open-weight-coding-agent]]。
- **生产案例 Ethara.AI**：用编排层（Oh-My-OpenAgent）按任务类别（规划、执行、代码审查、架构分析、知识检索、多模态理解、基准测试）维护专门优化过的 agent 队列，工程师"请求能力"、系统负责选模型/agent，并提到会基于执行轨迹持续优化各队列的技能与行为（属于厂商转述的产品案例，细节未披露）[[2026-09-26-amazon-bedrock-open-weight-coding-agent]]。

## 工程要点与数字

- 路由带来的具体成本/延迟收益**没有量化数字**，博文只给了定性论断（"降低 TCO"），没有对比实验 [[2026-09-26-amazon-bedrock-open-weight-coding-agent]]。
- 分派粒度是"任务类别"而非单个请求内部的细粒度调度——没有看到关于路由决策延迟本身的开销数据。
- 与 [[category-aware-expert-training]] 的关键区别：后者的类别路由发生在**训练时**（决定哪些样本进哪个专家的训练集，需要标签系统 SWE Labeler），成本是训练迭代成本；本概念的路由发生在**推理时**（决定每个请求打到哪个已经训好/部署好的模型），成本是推理调用的路由决策开销，两者不是同一层但思路互相印证。

## 开放问题

- 路由决策本身用什么做（规则、分类器、还是 LLM 做意图判断），文中完全没提，这是该模式落地时最关键的实现细节缺口。
- 路由错误（把复杂任务分给便宜模型导致效果差、需要重试）的代价没有讨论，这在我们自己设计类似调度逻辑时需要额外考虑重试/降级路径。
