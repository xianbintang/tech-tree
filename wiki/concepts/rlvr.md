# RLVR（Reinforcement Learning from Verifiable Rewards）

## 一句话定义

用可以程序化、确定性验证的规则（答案是否匹配、代码是否通过测试用例）直接作为 RL 奖励信号，不依赖训练出来的神经网络奖励模型——DeepSeek-R1-Zero 证明这类奖励在数学/代码/逻辑等"易验证域"足以单独驱动大规模 RL、涌现出复杂推理行为 [[2501.12948]]。

## 为什么对我们重要

RLVR 是把"验证"这件事从"训练一个奖励模型"变成"跑一段代码/匹配一个答案"，这直接把奖励计算这一步变成了我们沙箱平台能接入的标准工作负载——规则奖励模块本质上就是一个高频调用的代码执行服务。理解 RLVR 的边界（哪些任务能用、哪些不能）能帮我们判断"可验证奖励的工程实现"这个研究方向里，哪些工作负载真正需要沙箱执行能力，哪些只是文本匹配不需要。

## 核心机制 / 主要变体

- **两类规则奖励的组合**：$Reward_{rule}=Reward_{acc}+Reward_{format}$——准确率奖励（数学验证最终答案格式是否匹配参考答案；代码竞赛题用编译器+预定义测试用例跑通判定）+ 格式奖励（强制输出按 `<think>...</think><answer>...</answer>` 结构包裹，提升可解释性）[[2501.12948]]。
- **刻意放弃神经奖励模型**：作者明确说明不对推理任务使用任何神经网络奖励模型（无论是 outcome-based 还是 process-based），理由有二：大规模 RL 下神经 RM 容易被 reward hacking；重新训练 RM 本身消耗大量算力、增加流水线复杂度 [[2501.12948]]。
- **语言一致性奖励是对纯规则奖励的必要补丁**：纯规则奖励只约束"对不对"，不约束"可读性"，DeepSeek-R1-Zero 出现中英文混杂；引入 $Reward_{language}=Num(Words_{target})/Num(Words)$ 直接加到最终奖励缓解，但消融显示这会轻微拉低任务表现——说明"可验证"和"符合人类阅读习惯"在奖励设计上是两个可能冲突的目标 [[2501.12948]]。
- **RLVR 并不排斥与奖励模型混用**：DeepSeek-R1 第二阶段 RL 对推理数据继续用规则奖励，对通用数据（helpfulness/safety）改用奖励模型，两者按 $Reward=Reward_{reasoning}+Reward_{general}+Reward_{language}$ 加总——RLVR 更准确的定位是"在有规则可验证的子域里替代/补充奖励模型"，而非完全取代 RLHF 式的奖励模型 [[2501.12948]]。
- **冷启动与多阶段流水线是工程必需品，不是可选项**：纯 RLVR（R1-Zero）涌现出推理能力但可读性差；加入人工对齐的冷启动 SFT 数据 + 拒绝采样 + 两阶段 RL 的完整流水线（R1）才能同时兼顾推理能力和人类偏好对齐，纯规则奖励本身不解决"输出要让人满意"这个问题 [[2501.12948]]。
- **两条曾经尝试但失败的替代路线**（Appendix G.2）：Process Reward Model（PRM）——细粒度推理步骤难以显式定义、中间步骤正确性难标注、一旦模型化就会被 reward hacking；Monte Carlo Tree Search（MCTS）——token 级搜索空间远大于棋类游戏，价值模型难以训练到能指导精细搜索。两者都在大规模训练中失败，印证了"规则可验证"这个约束本身的价值：它换掉了一个需要被训练、可能被 hack 的组件（RM/价值模型），代价是只能覆盖"规则可验证"的任务子集 [[2501.12948]]。MCTS 并非天生无效——AlphaGo Zero 用"MCTS 自我对弈 + 策略迭代"在围棋上取得了超越人类的效果（[[self-play-policy-iteration]]），但围棋是状态空间有限、规则可完美模拟、验证近乎零成本的领域；token 级生成的动作空间和验证成本结构都不同，这正是 DeepSeek-R1 这里复现失败的根本原因，而不是 MCTS 方法论本身过时 [[2017-silver-alphago-zero]]。
- **前代实践：执行反馈先用于 SFT 数据过滤，而非 RL 奖励**——Llama 3（2024-07）的代码合成数据生成已经用"静态分析 + 容器化单元测试执行 + 错误反馈迭代自我修正"来验证约 100 万条合成代码对话的正确性，约 20% 的解答最初错误但通过执行反馈自我纠正成功；但这套反馈只用来**过滤/修正 SFT 训练数据**（离线、一次性判定"是否收录"），并未作为在线 RL 的奖励信号驱动策略更新。DeepSeek-R1（2025-01）把同样"用执行结果验证正确性"的思路往前推进一步，直接把它变成 RL 训练循环里持续计算的奖励——这是"执行反馈"从数据构造工具演变为训练算法组件的关键一步 [[2407.21783]]。

## 工程要点与数字

- **规则奖励模块的系统定位**：在 DeepSeek-R1 的 RL 框架里，规则奖励模块不需要把模型加载进 GPU 显存，但执行本身耗时（代码编译、跑测试用例），因此用异步调度把它的执行和 Rollout/Inference 模块重叠、隐藏延迟——这是 RLVR 落地时的核心系统设计点，不是训练算法层面的问题 [[2501.12948]]。
- **Reward hacking 的实测反例**：第二阶段 RL 引入 helpful RM 后，RM 打分持续上升，但 Codeforces 实测分数同步下降（Appendix B.5, Figure 6）——这是"奖励信号质量退化"而非 RLVR 本身的问题（这里用的是模型化奖励），但反向印证了作者"规则奖励更难被 hack"这一设计假设的动机；作者的应对是只给通用数据（用 RM 打分）最后 400 步训练窗口。
- **训练成本**：DeepSeek-R1-Zero 纯 RLVR 训练用 64×8 H800、约 198 小时（101K GPU 小时）；完整 R1 多阶段流水线总计 147K GPU 小时（≈$294K，按 $2/GPU 小时估算）[[2501.12948]]。
- **代码类规则奖励的测试用例构造成本**：Codeforces/AtCoder 原始平台不公开完整测试用例，作者用 DeepSeek-V2.5 生成候选测试用例 + 两阶段过滤（用正确提交剔除产出错误输出的无效用例 → 用错误提交筛选出真正能区分对错的用例子集）自建可靠测试集，这是代码类 RLVR 规则奖励能落地的前置工程工作，论文给出了方法但未披露具体人力/算力成本 [[2501.12948]]。
- **适用边界**：数学（最终答案可匹配）、代码（可编译+跑测试用例）、STEM 选择题（选项可匹配）、逻辑题是 RLVR 的天然适用域；写作、开放域问答等缺乏确定性标准答案的任务无法直接套用，DeepSeek-R1 对这类任务退回奖励模型路线 [[2501.12948]]。

## 开放问题

- 规则奖励模块与 Rollout/Inference 模块异步重叠隐藏延迟的具体收益（延迟分布、重叠率）论文未给数字，是可以自己测的工程空白 [[2501.12948]]。
- RLVR 目前验证的都是"结果可验证"（最终答案/测试用例通过与否），尚未看到过程级规则验证（如中间推理步骤的正确性）在大规模 RL 里落地的实证——PRM 的失败经验说明这条路不好走，但"规则化的过程验证"（而非神经网络化的 PRM）是否可行，论文未探讨。
- 工具调用场景（搜索引擎、计算器）下的规则奖励如何设计，作者在 Limitation 里承认留给下一版，目前没有实现细节。
