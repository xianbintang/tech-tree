# 测试难度分级奖励（Test-Difficulty-Driven Reward）

## 一句话定义

针对代码类可验证奖励任务的稀疏奖励问题：不再要求"通过全部测试用例才给奖励"的粗粒度 0/1 规则，而是把测试用例按（多模型 rollout 得到的）通过率聚类成不同难度分组，模仿 IOI（国际信息学奥赛）的分组评分规则，让模型在高难度题目上也能拿到部分分、获得密集学习信号 [[2505.07608]]。

## 为什么对我们重要

这是奖励设计与判题（沙箱执行）基础设施的直接交叉点：要支持这类分级奖励，判题服务不能只返回单条 pass/fail，还需要能对同一题目的大量候选解做批量统计，吐出"每条测试用例在多个 rollout 上的通过率"这类聚合数据——如果我们要给客户/内部团队提供 RL 训练环境搭建服务，这是判题 API 设计阶段就要考虑的字段，而不是训练侧事后能弥补的 [[2505.07608]]。

## 核心机制 / 主要变体

- **动机**：对困难的算法题，"全部测试通过才有奖励"的规则会导致模型长期拿不到任何奖励信号，既学不到东西也拖慢 dynamic sampling 的采样效率（通过率恒为 0 的 prompt 会被判定为退化组，见 [[grpo]]）[[2505.07608]]。
- **测试难度分组**：用多个模型对同一题目做多次 rollout，统计每条测试用例在所有生成解上的通过率，通过率越低代表该测试越难，据此把测试用例聚类成不同难度层级 [[2505.07608]]。
- **严格奖励（Strict Reward）**：解法必须通过某一难度层级的全部测试**以及所有更低难度层级的全部测试**，才能拿到该层级对应的分数 [[2505.07608]]。
- **软性奖励（Soft Reward）**：每个难度层级的总分平均分摊到组内每条测试用例上，最终奖励是所有通过的测试用例得分之和，不要求组内全部通过 [[2505.07608]]。
- 两种方案都不依赖模型架构或具体 RL 算法，是一个可以直接嫁接到任何"代码任务 + 单元测试验证"RL 流水线上的奖励函数改造，与 [[verifiable-reward-environment-generation]] 讨论的"环境构造"是不同层面的问题——环境/测试用例本身不变，只改变从测试结果到标量奖励的映射函数。

## 工程要点与数字

- 论文只给出 Figure 5 的定性对比（严格 vs 软性 vs 无分级奖励的基线曲线），未披露最终评测分数的量化差异，也未说明两种方案在什么条件下互有优劣 [[2505.07608]]。
- 依赖前置基础设施：需要"用多个模型对同一题目批量 rollout + 统计每条测试用例通过率"的能力，这本身要求判题服务能高效执行大批量单元测试（论文提到"an online judge environment that enables parallel execution of extremely high-volume unit tests"，但未披露该判题环境的具体吞吐/延迟数字）[[2505.07608]]。
- 与 [[grpo]] 的 dynamic sampling 是互补关系：dynamic sampling 解决"整组退化"的问题（组内奖励方差为零时丢弃该组），测试难度分级奖励解决"单题奖励本身过于稀疏"的问题，两者可以同时使用（MiMo 就是这样做的）[[2505.07608]]。

## 开放问题

- 严格奖励与软性奖励在不同难度分布的题目集上是否有一致的优劣排序，还是需要按数据集调参，论文未给出系统性比较。
- 测试用例的难度分组依赖"多模型多次 rollout 统计通过率"这一前置步骤本身的成本（需要多少次 rollout、多少个模型才能得到稳定的难度分组）未量化。
- 该方案是否能推广到"代码" 之外的其他可分解验证任务（如多步数学证明按步骤给分），论文未讨论。
