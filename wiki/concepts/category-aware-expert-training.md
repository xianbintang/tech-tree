# 类别感知专家训练

## 一句话定义

先按任务类别把训练集拆开、各训一个 RL 专家，再用蒸馏把多个专家整合回一个部署策略，用来规避"池化联合训练时某些类别进步、另一些类别退步"的问题。

## 为什么对我们重要

我们平台上跑的 agent 训练任务往往覆盖多个差异很大的子域（不同代码库、不同任务类型、不同语言）。如果只看聚合分数做池化 RL，可能存在同样的"类别跷跷板"——分数在涨但某些子类在悄悄退化。这类方法给了我们一个**诊断思路**（按类别拆开看分数）和一个**训练范式**（专家化 + 蒸馏），但也带来了明确的基础设施要求：训练中需要频繁、低成本地对全量任务重新评估。

## 核心机制 / 主要变体

- **问题现象——类别跷跷板**：在池化 RL（pooled RL，如 SWE-RL 的做法）下，某些任务类别的收益与其他类别的退步同时发生，但聚合指标会掩盖这种内部此消彼长的重新分配 [[2609.23377]]。
- **SWE Labeler**：多轴、证据驱动的分层标签系统，用两条语义轴（任务类型、仓库领域）+ 三条序数轴（修改范围、认知复杂度、预计解决时间）把任务路由到可训练的类别 [[2609.23377]]。
- **Refresh-Repair-Expand（RRE）循环**：每轮三阶段——① Refresh：在当前 RL 集上重估通过率，识别退化/已掌握实例；② Repair：对掌握度低的实例做加权采样，用自生成、验证通过的轨迹做 SFT 修复；③ Expand：把下一轮训练集扩展为"当前边界样本（未完全掌握）∪ 历史证明可解但当前 pass 率为 0 的样本" [[2609.23377]]。
- **专家训练不引入外部教师轨迹**：所有类别专家从同一个基础模型出发，完全靠可执行 Agentic RL 塑造类别行为 [[2609.23377]]。
- **整合回单策略**：靠 [[on-policy-distillation]]（MOPD）用 ReLU 门控奖励外推把多个专家的"变好方向"蒸馏进一个部署模型。
- 与已有跨域专家融合方法（如 Branch-Train-Merge）的区别：BTM 等方法多用于数学/代码生成等**跨领域**场景，本方法是在**单一 SWE 域内**做类别级专家化 [[2609.23377]]。

## 工程要点与数字

- 用 SWE Labeler 把 [[swe-bench-pro]] 审计子集 Pro-618（618/731 任务）路由为三个操作类别：Pro-A 服务/数据/安全（221）、Pro-B 用户面应用（201）、Pro-C 系统/工具/运行时（196） [[2609.23377]]。
- 训练数据池约 3.2 万条可执行候选任务；SWE Labeler 在三个基准上共标注 1531 个实例做验证 [[2609.23377]]。
- 最终 MOPD 整合策略：Pro-618 从基线 52.64% 提升到 58.04%（+5.39pp），[[swe-bench-multilingual]] 从 56.22% 提升到 59.00%（+2.78pp） [[2609.23377]]。
- **RRE 的计算成本未量化**：Refresh 阶段需要对当前训练集做全量重新评估，多轮迭代下来的总开销论文没有披露 [[2609.23377]]。这对沙箱/执行环境的**批量 rollout 吞吐和冷启动速度**提出了隐含要求。
- 三分类是启发式划分，不是从数据聚类得出的最优切分，换任务分布未必成立 [[2609.23377]]。

## 开放问题

- 何时该把一个任务域拆分成多个类别专家、何时该保持池化训练，论文没有给出判据 [[2609.23377]]。
- 整体分数提升不代表所有类别收益都被蒸馏保留下来——MOPD 整合后可能仍有部分类别收益丢失，作者自己承认这一点 [[2609.23377]]。
- RRE 循环的诊断性重估在更大规模任务池上是否能摊销成本，尚不清楚。
