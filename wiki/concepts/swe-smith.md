# SWE-smith

## 一句话定义

一套"环境优先、任务后生"的自动化流水线：给定任意 Python 仓库，先建一份共享执行环境，再用四种自动化策略（LM 改写、AST 程序化变异、PR 逆向、任务组合）批量合成破坏现有测试的 bug 任务，从 128 个仓库产出 50,137 个可执行任务，存储仅 295GB，微调出的 32B 模型在 SWE-bench Verified 达 40.2%（当时开源 SOTA）[[2504.21798]]。

## 为什么对我们重要

它是"SWE 训练环境规模化"路线里目前工程细节最完整、成本数字最全的公开样本：四种 bug 合成策略各自的产出率/成本/训练效果都有量化对比，"环境优先"架构给出了镜像存储从 TB 级压到百 GB 级的具体做法，防作弊质量门槛也是纯执行式、零 LLM 判分——三者分别对应我们评估"自建任务规模化流水线值多少钱、怎么设计存储、怎么把质量门槛做便宜"三个直接问题 [[2504.21798]]。

## 核心机制 / 主要变体

- **架构反转：环境优先、任务后生**：与 [[swe-gym]]/SWE-bench"每个任务独立建执行环境"相反，SWE-smith 先给一个仓库在最新 commit 上建唯一一份可执行环境（Docker 镜像），再在同一份环境里批量合成成百上千个任务，任务间共享环境镜像，这是存储从 SWE-bench 式 50-150TB（论文估算值）压到 295GB 的根本原因 [[2504.21798]]。
- **四种自动化 bug 合成策略**（产出率/成本见下表）：
  - **LM Modify**：给函数体，提示 LM 直接改出 bug。
  - **LM Rewrite**：只给函数签名 + docstring，要求 LM 重新实现整个函数。
  - **Procedural Modification**：解析 AST，随机施加 13 种预定义代码变换（去条件分支、改操作符等），零 LM 成本。
  - **PR Mirror**：收集仓库历史 PR，用 LM 在当前版本上尝试撤销该 PR 的修改，还原"引入 bug 前"的状态，最接近真实 SWE-bench 分布但成本最高。
  - 外加 **Combine Bugs**：把同文件/模块内的多个候选聚合成更复杂的复合任务，几乎零成本、产出率最高（96.9%）[[2504.21798]]。
- **执行式质量门槛（零 LLM 判分）**：候选 patch 应用后跑测试套件（单条限时 2 分钟），唯一准入标准是"至少破坏 1 个原本通过的测试"（Fail-to-Pass）。这与 [[swe-gym]] 的"gold patch 通过测试数 > 原始代码"门槛是同一思路的镜像版本——SWE-smith 反向构造 bug、SWE-Gym 正向验证修复，两者都用确定性测试执行代替人工/LLM 审阅 [[2504.21798]]。
- **问题陈述生成**：把 patch diff、随机抽取的 F2P 测试源码、测试执行输出一起交给 LM 生成 GitHub issue 风格描述；消融显示 LM 生成的效果与真实 PR 原文相当，优于固定模板（固定模板会让轨迹里独特动作数减少 31%）[[2504.21798]]。

## 工程要点与数字

- **产出与成本（Table 1）**：128 个仓库 → 50,137 个任务，整体产出率 50.1%，总成本 $1,360（$1,000 生成 bug + $160 自动装环境 + $200 生成 1 万条 issue），折算约 $2.32–2.54/条；人工投入约 20 小时（解析安装指令 + 写测试解析器）+ 18 小时环境安装人工审查（128 个仓库）[[2504.21798]]。
- **各策略产出率/成本对比**：Combine 96.9%/$0（10,092 条）、LM Modify 56.0%/$0.38（17,887 条）、Procedural 40.2%/$0（15,641 条）、LM Rewrite 35.0%/$3.93（4,173 条）、PR Mirror 33.8%/$5.53（2,344 条，最贵最接近真实分布）[[2504.21798]]。
- **存储对比（Table 2）**：[[swe-gym]] 2.4k 任务/11 仓库/6TB、[[r2e-gym]] 4.6k 任务/10 仓库/4TB（对应 R2E-Gym 一手论文里的 R2E-Gym-Subset，见 [[2504.07164]]）、**SWE-smith 50k 任务/128 仓库/295GB**——环境优先架构下存储不随任务数线性增长 [[2504.21798]]。
- **模型效果（Table 3）**：约 5,016 条轨迹（每任务限 3 条）微调出的 SWE-agent-LM-32B，SWE-bench Verified pass@1 **40.2%**、Lite 30.7%，无推理时扩展，为当时开源 SOTA [[2504.21798]]。
- **同规模直接对标（§4 末，控制轨迹数为 500）**：SWE-smith-32B 28.2% Verified，对比 [[swe-gym]]-32B 20.6%（+8.2pp）、[[r2e-gym]]-32B 27.5%（+0.7pp，注意这一数字是控制轨迹数后的对标值，与 R2E-Gym 一手论文里未控制轨迹数的 34.4% 口径不同，见 [[r2e-gym]]）——说明规模之外，任务合成质量本身也带来独立增益 [[2504.21798]]。
- **Bug 策略消融（Table 4，控制 507 条成功轨迹）**：PR Mirror 9.2% Verified 最优，Procedural 8.6%、LM Rewrite 8.8% 具竞争力，LM Modify 5.7% 最弱——零成本的 Procedural 能打平昂贵的 LM 策略 [[2504.21798]]。
- **仓库多样性 vs 单仓库特化（图5）**：固定 700 样本，覆盖仓库数从 4 增到 100，性能对数增长；反过来单用 SymPy 700 样本微调，SymPy 子集上 42.4%（远超全仓库训练 33.3%），但整体泛化性能仅微降 [[2504.21798]]。

## 开放问题

- 难度分档（专家标注 58.6%/41.0%/17.0%）与学生模型实际解决率（12.4%/10.8%/13.6%/12.2%，几乎不随难度单调变化）不一致，论文未解释，如果难度打分本身不可靠，可能影响下游课程学习类应用 [[2504.21798]]。
- 流水线以 Python `ast` 库为核心，作者称"收集策略可迁移到其他语言"但未给出实现或验证；迁移到 Go/Java/Rust 等语言的 Procedural Modification 规则集需要重新设计。
- 18 人工小时/128 仓库的环境安装审查是否随仓库数线性增长、能否进一步自动化，论文未讨论；这是"环境优先"架构里唯一仍需人工的环节。
- 合成 bug（尤其 LM Modify/Procedural）与真实 GitHub issue 的自然性差异未做人工评审或图灵测试式校验，只靠下游训练效果反推质量，是否存在系统性偏差未知（follow-up，见 [[2504.21798]] 笔记）。
