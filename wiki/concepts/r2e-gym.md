# R2E-Gym

## 一句话定义

用程序化合成（SweGen：自动筛选真实提交 + 反向翻译生成问题陈述）把 SWE 可执行训练环境从 [[swe-gym]] 的 2,438 个扩到 8,135 个，并提出"执行型 + 无执行型"混合验证器（Hybrid Verifier），把推理时扩展的天花板从两种验证器各自单独饱和的 ~43% 拉到 Best@26 51.0%，是当时开源权重 SWE agent 首次在 SWE-Bench Verified 上逼近部分闭源系统 [[2504.07164]]。

## 为什么对我们重要

它同时回答了我们关心的两个问题：一是"环境构造能否脱离人工标注规模化"——SweGen 的反向翻译（用测试失败输出反推问题描述）是一个可能迁移到我们自己合成训练任务场景的低成本数据增广模式；二是"验证器要多贵才够用"——混合验证器的"先用便宜的无执行判分粗筛、再用真实沙箱执行精排"两阶段设计，直接对应我们如果要做"验证器即服务"时的成本/准确率折中方案 [[2504.07164]]。

## 核心机制 / 主要变体

- **SweGen 环境与任务合成流水线**：用 SEART GitHub 搜索定位高提交量 Python 仓库 → 规则 + LLM 启发式过滤提交（单提交 ≤5 个非测试文件、≤100 行编辑、补丁 ≤2000 字符）→ Docker 化"搜索型依赖解析"构建可执行环境（迭代探测版本冲突，半自动尝试直到成功）→ 收集/补充 Fail-to-Pass 测试作为执行式准入门槛 [[2504.07164]]。
- **反向翻译（backtranslation）生成问题陈述**：核心创新——人写的 GitHub issue 通常本身包含失败测试和报错堆栈，于是反过来把 F2P 测试的执行输出当 prompt 素材，让 LLM 反推生成问题陈述，从而不再依赖必须存在高质量人工 issue 的提交，使可用数据源扩大约 2.5 倍；消融显示合成问题陈述训练效果与真实 PR 描述几乎等价（27.8% vs 28.0%，400 轨迹控制变量）[[2504.07164]]。
- **混合验证器（Hybrid Verifier）**：执行型验证器（EB，32B 测试代理为每题生成 10 个额外边界测试，Eq. 1 按回归测试通过数打分）与无执行型验证器（EF，14B 模型输出 YES/NO token 概率打分，逻辑与 [[swe-gym]] 的 ORM 一致）各自单独饱和于 ~43%；混合公式 $s_k^H = \mathrm{Top}_n(s_k^{EF}) + s_k^{EB}$（Eq. 2）先用 EF 分数排前 n 名做粗筛，再叠加 EB 精排分数，抑制"毒性测试"（通过错误补丁但让正确补丁失败的测试）对最终排序的污染 [[2504.07164]]。
- **EF 验证器的隐藏偏差**：过度依赖 agent 的"思维轨迹"而非最终补丁本身——只喂 patch（去掉轨迹）Best@26 从 42.8% 掉到 37.6%，注意力可视化证实模型把最高权重放在思维文本而非代码 diff 上，提示这类验证器可能在学"听起来自信"的代理信号而非真正核验正确性 [[2504.07164]]。

## 工程要点与数字

- **数据集规模对比**（Table 1）：SWE-Bench(train) 19,008 条不可执行；SWE-Gym Raw 66,894 条不可执行；[[swe-gym]] 2,438 条可执行；**R2E-Gym 全集 8,135 条可执行**（13 个仓库）；R2E-Gym-Subset（与 SWE-Bench 仓库无重叠）4,578 条、2,048 个去重环境——这一数字与 [[swe-smith]] Table 2 存储对比表中"R2E-gym 4.6k 任务/10 仓库/4TB"互相印证 [[2504.07164]] [[2504.21798]]。
- **同基座直接对标 SWE-Gym**（Table 3，SWE-Bench Verified Pass@1，Qwen2.5-Coder 系列）：7B 19.0%（对比 SWE-Gym 10.6%，+8.4pp）、14B 26.8%（对比 16.4%，+10.4pp）、**32B 34.4%（对比 20.6%，+13.8pp）**——是 [[agentic-rl-environments]]、[[gef-loop]] 已引用的"环境规模化"量化链条 SWE-Gym 20.6%→R2E-Gym 34.4%→SWE-Smith 40.2% 的中间点 [[2504.07164]]。
- **混合验证器推理时扩展**（Table 4）：纯 EB 饱和 ~43.7%、纯 EF 饱和 ~42.8%，**混合 Best@26 达 51.0%**（全文最高分），逼近/部分超过 Claude-3.5-Sonnet（49.0%）、o1+Agentless（49.2%），但仍落后 Claude-3.7-Sonnet Best@Any（70.3%）[[2504.07164]]。
- **消融**：去掉 agent 思维轨迹训练，32B 从 34.4% 降到 30.4%；用训练出的 agentic 测试代理（51.0%）优于不训练的静态 Agentless 式测试代理（48.8%）；加 Top_n 过滤（51.0%）优于不加（49.8%）[[2504.07164]]。
- **训练规模**：Claude-3.5-Sonnet-v2 拒绝采样收集 3,321 条成功轨迹（每条 ≤40 步、≤32K token）SFT Qwen2.5-Coder 7B/14B/32B；测试代理另采 2,203 条轨迹，32B LoRA rank=64；训练上下文截断 20K token（论文明确写"due to computational constraints"）[[2504.07164]]。
- **规模化倍数的表述口径**：引言称"increasing the number of executable environments by over 33 times"，这是相对论文引用的更早期基线（246 个可执行环境），并非相对 SWE-Gym（2,438 个，相对 R2E-Gym 全集实际约 3.3 倍）——引用这个"33 倍"数字时需注明对比对象，避免误传为"比 SWE-Gym 大 33 倍" [[2504.07164]]。
- **论文未披露环境构建的具体人工/算力成本**：仅承认 Docker 依赖解析"semi-manual and challenging to scale"，没有给出类似 [[swe-gym]]（200 人工小时+10,000 CPU 核心小时/2,438 实例）或 [[swe-smith]]（$1,360+38 人工小时/128 仓库）那样的量化数字——这是三篇 SWE 环境合成论文里成本透明度最低的一篇，我们无法据此估算自建同类流水线的投入 [[2504.07164]]。

## 争议与矛盾

（暂无跨来源分歧；与 [[swe-gym]] 是直接迭代关系——同基座同规模对标显示 R2E-Gym 全面胜出；与 [[swe-smith]] 是同一"环境规模化"故事线上的相邻节点，三者共同构成 20.6%→34.4%→40.2% 的量化证据链，具体优劣取决于评测口径：R2E-Gym 靠混合验证器把 Best@26 推到 51.0%，是三者里唯一给出"验证器规模化"完整实验的一篇，但基础 Pass@1 的 32B 数字 34.4% 低于 SWE-Smith 的 40.2%/28.2%（视轨迹数对标口径而定），说明"环境规模化"与"验证器规模化"是两条相对独立的增益来源）

## 开放问题

- 环境构建的人工/算力成本完全未披露，无法直接估算把 SweGen 流水线搬到我们自己仓库池上的边际成本，需要我们自己动手复现小规模样本来测（follow-up）。
- EF 验证器依赖思维轨迹而非结果本身的偏差是否可以通过训练时的输入消融（强制只看补丁）来缓解，论文未做这个实验；这对我们设计任何"轨迹+结果"联合判分的验证器都是一个值得预先测试的风险点（follow-up）。
- 执行型验证器生成的测试里 <20% 真正有区分度（Figure 5），如何提高生成测试的信噪比（比如让测试生成本身也做拒绝采样/自我过滤）论文未展开。
- 混合验证器的 Top_n 中 n 的具体取值及其敏感性分析论文未给出（只给出了消融"加/不加 Top_n"的二元对比），实际部署时如何调这个超参数不明确。
