# SWE-Gym

## 一句话定义

首个面向 SWE agent 训练的可执行环境：2,438 个真实 GitHub issue 任务，每个都配好了可运行的 Python 仓库依赖环境 + 单测，用于策略（agent）与验证器（ORM）的训练与推理时扩展 [[2412.21139]]。

## 为什么对我们重要

它是"code/SWE agent 训练环境如何从零构造"这一问题最早给出完整工程细节的公开工作：从仓库筛选标准、依赖配置的人工/CPU 成本，到镜像发布规模，都是我们评估"自建同类环境值多少钱"的直接参照系；同时它的 ORM 验证器训练与推理时扩展实验，是易验证域（代码）里"验证器规模化"的一个完整闭环样本 [[2412.21139]]。

## 核心机制 / 主要变体

- **三级数据集**：SWE-Gym Raw（64,689 条，358 个仓库，无可执行环境，仅供未来做环境/任务自动合成研究）→ SWE-Gym（2,438 条，11 个仓库，半人工配置可执行环境 + 执行式验证）→ SWE-Gym Lite（230 条，按 SWE-Bench Lite 过滤规则挑出的简单子集，便于快速迭代）[[2412.21139]]。
- **仓库筛选与去污染**：用 SEART GitHub 搜索按"2022-07 前创建、500+ star、300+ 行代码、500+ PR、100+ 贡献者"筛出 358 个 Python 仓库；这批仓库刻意与 SWE-Bench 的仓库集合不重叠，避免评测污染 [[2412.21139]]。
- **执行式验证准入门槛**：唯一质量门槛是"人类提交的 gold patch 通过的单测数必须严格多于原始代码通过的单测数"，用 SWE-Bench 的验证脚本执行式检查，而不是人工/LLM 审阅——简单但有硬保证 [[2412.21139]]。
- **Agent 训练**：两种 scaffold 对照——通用 ReAct 式长程 prompting（OpenHands CodeAct）用拒绝采样微调；人工分阶段的 specialized workflow（MoatlessTools）用在线迭代拒绝采样做自我提升，并引入 **per-instance capping**（每任务最多保留 N 条成功轨迹，实验取 2）来对抗"重复采样下成功率长尾分布"导致的简单任务过采样偏差 [[2412.21139]]。
- **验证器（Outcome-Supervised Reward Model, ORM）**：给定 (问题描述, agent 轨迹, 当前 diff)，微调模型输出单 token `<YES>`/`<NO>`，用其归一化 log 概率当标量奖励，训练数据混合 on-policy（当前策略自采样）与 off-policy（更强闭源模型采样）成功/失败轨迹并配平；推理时对同一任务采样 k 条轨迹，用 ORM 选 Best@k [[2412.21139]]。

## 工程要点与数字

- **构造成本**：2,438 个验证通过实例耗费约 200 人工标注小时 + 10,000 CPU 核心小时，折算约 4.1 CPU 核心小时/实例；公开发布 Docker 镜像共 6 TB，约 2.5 GB/实例 [[2412.21139]]。
- **任务难度对比 SWE-Bench**（Table 2）：SWE-Gym 平均 gold patch 编辑 69.8 行 / 2.5 文件 / 4.1 函数，显著高于 SWE-Bench test（32.8 行 / 1.7 文件 / 3.0 函数）；仓库分布长尾，pandas 占近 1/3 任务，bokeh 约 1% [[2412.21139]]。
- **Agent 微调效果**：仅用 491 条拒绝采样轨迹微调 Qwen2.5-Coder-32B（OpenHands scaffold），SWE-Bench Verified 解决率 7.0%→20.6%（+13.6pp），Lite 3.0%→15.3%（+12.3pp）；SWE-Gym-32B 的这一 20.6% 数字被 [[2511.09586]] 用作"环境规模化"的量化基准点之一（对比 R2E-Gym-32B 34.4%、SWE-Smith-32B 40.2%，见 [[gef-loop]]、[[agentic-rl-environments]]）[[2412.21139]] [[2511.09586]]。**[[r2e-gym]] 论文用完全相同的 Qwen2.5-Coder 系列做了逐规模直接对标**（7B/14B/32B 全部同基座并排比较），32B 上 R2E-Gym 34.4% vs SWE-Gym 20.6%（+13.8pp）——是三篇环境论文里唯一给出这种全规模一一对应对标表格的一篇 [[2504.07164]]。
- **推理时扩展上限**：OpenHands + 32B agent + 32B ORM，Pass@16 达 42.8%，Best@16（ORM 选优）达 32.0%——是全文最高分，也是当年开放权重 SWE agent 的 SOTA；Pass@k 与 Best@k 之间 10.8pp 的差距反映 ORM 远非完美验证器 [[2412.21139]]。
- **验证器规模影响 scaling 行为**：7B ORM 在 k=4 后饱和，32B ORM 到 k=8 仍在提升；ORM 用 LoRA 微调（29.8@8）反而比全参数微调（27.2@8）更好，作者猜测是正则化效应 [[2412.21139]]。
- **自我提升（拒绝采样版）在这个环境上失败**：用微调后策略自采样 868 条 on-policy 轨迹混入原 491 条 off-policy 轨迹重新训练，SWE-Bench Lite 解决率反而从 15.3% 跌到 8.7%，作者认为需要更强策略优化算法（如 PPO）而非简单拒绝采样 [[2412.21139]]。
- 论文**未披露**镜像分发/冷启动耗时、并发评测的具体资源开销——这是我们评估能否直接复用这套环境到自己调度系统时的已知缺口 [[2412.21139]]。
- **验证器规模化的后续对照**：SWE-Gym 的 ORM 训练/推理时扩展实验（Best@16 32.0% vs Pass@16 42.8%）之后被 [[r2e-gym]] 直接接力——R2E-Gym 提出"执行型 + 无执行型"混合验证器，把类似的推理时扩展上限从两种验证器各自单独饱和的 ~43% 推到 Best@26 51.0%，说明 SWE-Gym 观察到的"验证器远非完美"这一局限，在换用混合设计后有实质性改善空间 [[2504.07164]]。
- **与 SWE-Smith 的同规模直接对标**：[[swe-smith]] 论文在控制轨迹数为 500 条（两篇工作都报告过的规模）时直接对比，SWE-Smith-32B 达 28.2% Verified，比 SWE-Gym-32B 高 +8.2pp——说明在排除"轨迹量不同"这一变量后，SWE-Smith 的任务合成质量/多样性本身仍有独立增益，不只是规模堆量的效果 [[2504.21798]]。SWE-Smith 同时把"每任务独立建环境"反转为"环境优先、任务后生"，把类似规模所需的镜像存储从 SWE-Gym 的 6TB/2,438 实例压到 295GB/50,137 实例，是对 SWE-Gym 存储瓶颈的直接回应 [[2504.21798]]。

## 开放问题

- 200 人工小时/2,438 实例的环境配置成本几乎全靠人工，论文未给出自动化这一步的方案；后续 R2E-Gym（程序化合成，8,135 任务）在此基础上把规模扩大了一个数量级以上。**SWE-Smith 已给出这一自动化流水线的具体细节**（四种 bug 合成策略 + 环境优先架构，见 [[swe-smith]] [[2504.21798]]），此项开放问题已部分解决，剩余缺口是"环境安装审查"这一步仍需 18 人工小时/128 仓库、尚未自动化。
- ORM 训练数据消融显示 on-policy + off-policy 混合最优，但论文未系统探究混合比例的最优点，也未讨论 ORM 本身的系统性偏差是否会在长期 RL 训练中被放大。
- 6TB 镜像规模下的存储/分发/去重策略完全未讨论，是否可以用分层镜像大幅压缩，需要我们自己动手验证（follow-up，见 [[2412.21139]] 笔记）。SWE-Smith 的"环境优先"架构给出了一种压缩思路（同库任务共享镜像，295GB/50,137 任务），但未讨论是否可用 OverlayFS 等镜像分层技术进一步压缩（follow-up，见 [[2504.21798]] 笔记）。
