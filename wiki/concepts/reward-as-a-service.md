# Reward-as-a-Service

## 一句话定义

把多任务 RL 训练里"规则奖励函数 + 多个模型奖励"统一封装成低延迟 HTTP 服务，由 reward router 按查询的任务类型动态分发到对应奖励计算逻辑的架构模式，而不是把奖励计算耦合在 rollout/训练循环内部 [[2506.03569]]。

## 为什么对我们重要

我们的研究方向明确关心"agent 轨迹数据、环境构造与可验证奖励的工程实现"以及"训练系统与 GPU 调度"。当一次 RL 训练要同时消费多种奖励来源（规则判分、多个专用奖励模型、人类偏好奖励模型）时，奖励计算本身就是一个独立的、异构的、可能成为瓶颈的子系统——这和我们平台里"沙箱执行结果反馈进训练循环"的场景高度同构：验证器/沙箱执行也需要按此模式做成可独立扩缩容的服务，否则最慢的一类反馈会拖慢整个批次的策略更新节奏。

## 核心机制 / 主要变体

- **MiMo-VL 的实现（MORL 框架下）**：在 verl（HybridFlow）RL 训练框架基础上，把 RLVR（视觉推理、文本推理、图像/GUI grounding、视觉计数、时序视频 grounding 五类规则奖励）和 RLHF（文本/多模态两个 Bradley-Terry 奖励模型）统一注册为奖励服务；reward router 按每条查询的任务类型动态选择对应的奖励函数或奖励模型；各奖励模型独立部署为可横向扩展的 HTTP 服务，目标是近零延迟；所有奖励统一归一化到 [0,1]，训练中不额外叠加格式奖励 [[2506.03569]]。
- **动机**：MORL 要在同一个 [[grpo]] 训练循环里混合 5+ 类任务域的奖励信号，若奖励计算逻辑直接写死在训练循环里，每新增一类任务/奖励模型都要改动训练主流程；RaaS 把"奖励是什么"和"怎么训练"解耦，训练循环只需要按任务类型请求奖励服务、拿到归一化分数 [[2506.03569]]。

## 工程要点与数字

- 论文**未披露** RaaS 的具体延迟、吞吐、奖励模型服务的资源占用（GPU 数量、QPS、P99 延迟等）数字，只给出了架构描述和"近零延迟"这一定性目标，是这个模式目前最大的信息缺口 [[2506.03569]]。
- 训练框架依托 verl/HybridFlow，并叠加 MiMo-7B 报告里的 Seamless Rollout Engine，但两者与 RaaS 之间具体如何交互（同步阻塞请求 vs 异步批量拉取）未详细说明 [[2506.03569]]。

## 开放问题

- RaaS 在生产环境下的延迟/吞吐基准完全空白，无法评估这类架构在更大规模（更多任务域、更高 rollout 并发）下是否仍能保持"近零延迟"，需要额外调研或自行复现验证 [[2506.03569]]。
- 奖励服务本身的扩缩容策略、故障降级（某个奖励模型服务不可用时训练如何应对）未讨论，是把这个模式搬到我们自己平台前需要补的设计点。
